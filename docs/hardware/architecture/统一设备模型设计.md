## 1. 现状：有什么、缺什么

### 1.1 已有的（实测，可直接复用）

| 能力 | 落在哪 | 读法 |
|---|---|---|
| PCI 设备枚举 | `kernel/src/bus/pci.rs` | `pci::init()` 填静态表，`MAX_DEVICES=64`，ECAM 优先/CAM 回退 |
| 设备身份（原始字段） | `bus/pci.rs` 的 `Dev` | `bdf` / `vendor` / `device` / `cfg08` / `hdr` / `bar0` |
| 类别解码 | `Dev::class()` / `subclass()` / `progif()` / `revision()` | 按 `cfg08` 字节序，`KT_PCI` 用四台设备钉过 |
| 按类找设备 | `pci::first_of_class` / `first_of_triple` / `count_of_class` | 后者专治"class 0x01 有两台、槽位序会挑错" |
| 中断能力读数 | `Dev::irq_caps()` | INTx pin/line + MSI + MSI-X，带跳数上限与坏链归因 |
| 资源认领 | `kernel/src/driver/mod.rs` 的 `DriverCtx` | `map_mmio` / `alloc_dma` / `request_irq`，全是 `槽号+世代号` |
| 用户态只读出口 | 31 号 `SYS_PCI_ENUM` + shell 的 `lspci`/`lsdev`/`devctl status` | ADR-136 / ADR-149 |

### 1.2 真正缺的（未实施）

**没有"设备对象"这一层抽象。** 今天的形状是：每个驱动自己调
`DriverCtx::for_device(MOD_X, dev)`，自己决定 BAR 号、自己决定要不要 IRQ。
`DriverCtx` 携带的是 `(ModuleId, Dev)` 两个值——它是**令牌**，不是设备句柄。

具体缺三样：

1. **没有设备状态**。一台设备是"认领了/失败了/没驱动"——今天读不到。
   `devctl status` 只报**类别计数**（`class 0x01 count=1`），不报单台设备的状态。
2. **没有匹配器**。哪个 vendor/device 归哪个驱动，散在各驱动的 `claim()` 里
   （`ahci::claim` 用 `first_of_triple(0x01,0x06,0x01)`，`virtio::bind_one` 用 vendor 0x1AF4）。
   没有一张能单测的表。
3. **没有"驱动清单"与设备的对应登记**。`devctl status` 答不出"这台设备为什么没人管"。

## 2. 设计：三层，不用 trait 对象

### 2.1 为什么不引入 `trait Driver`

见 [总设计 §3.1](../Aurora-OS-硬件驱动体系总设计-V1.0.md)。三条独立理由：

1. 与 **ADR-030 决定 5** 冲突：「首期只做被用到的方法……先把没人调的方法摆进 trait，
   就是把目录当成实现」。`trait Driver { name/probe/initialize/shutdown }` 里
   `name` 与 `shutdown` 今天**零调用者**。
2. 违反 `AGENTS.md` 硬约束 2（不创建没有真实调用者的空 trait）。
3. `&mut self` 在这个内核里**没有落脚点**：驱动状态住在静态 `UnsafeCell` 里
   （`driver/mod.rs` 的 `TABLE`、`bus/pci.rs` 的 `TABLE`、`driver/virtio.rs` 的 `NetCell`），
   没有"驱动实例"这块内存。

### 2.2 三层结构

```text
第 1 层  DeviceInfo（值，Copy）
         { dev: pci::Dev, class: u8, subclass: u8, progif: u8, revision: u8 }
         —— 只加"解码后的三件套"，不新建设备树对象

第 2 层  匹配器（纯函数，无分配，可单测）
         match_device(&Dev) -> Option<DriverId>
         表 1: IdMatch    { vendor, device, driver }        —— 精确 ID
         表 2: ClassMatch { class, subclass, progif, driver } —— 类别三件套

第 3 层  状态表（定长静态）
         DeviceState { Unclaimed, Probing, Active, Failed(&'static str), Released }
         set_state(dev_bdf, next) -> Result<(), DriverError>   // 非法迁移 → Denied
         state_of(dev_bdf) -> Option<DeviceState>
         occupancy_by_state() -> [usize; 5]
```

**落点**：全部进 `kernel/src/driver/mod.rs`（已在环 A 里，加东西不改 SCC）。

### 2.3 匹配顺序（必须是这个顺序）

```text
1. 按 ID 精确匹配（vendor+device）     ← 最具体，优先
2. 按类别三件套（class+subclass+progif）
3. 都没有 → Unclaimed（这不是错误，是读数）
```

**为什么不能只按 class**：`bus/pci.rs` 的 `first_of_triple` 注释记了实测——
多挂一块 virtio-blk 之后 class 0x01 有两台设备，而 virtio-blk 的槽位（06.0）
排在 ich9-ahci（1f.2）**前面**，扫描顺序决定结果。"只按 class 找"会挑错设备。

### 2.4 状态迁移表（非法迁移必须被拒）

| 从 | 到 | 允许 | 说明 |
|---|---|---|---|
| Unclaimed | Probing | ✅ | 匹配器给出了驱动 |
| Probing | Active | ✅ | `claim()` 返回 Ok |
| Probing | Failed | ✅ | `claim()` 返回 Err（**必须带名字**） |
| Active | Released | ✅ | 显式释放 |
| Active | Failed | ✅ | 运行期故障 |
| Failed | Probing | ✅ | 重试（真机热插拔/复位后） |
| Unclaimed | Active | ❌ | `Denied("跳过了 Probing")` |
| Active | Probing | ❌ | 必须先 Released |
| Released | Active | ❌ | 必须先 Probing |

非法迁移返回 `DriverError::Denied(&'static str)`，**理由写成字符串**——
压成一个 `Io` 就没法归因（这条与 `driver/mod.rs` 里既有 13 个错误变体的口径一致）。

## 3. 判据

### 3.1 正向

| 判据 | 形状 | 判定 |
|---|---|---|
| `t_match_device` | 喂 `Dev` 三种形状（命中 ID / 命中类别 / 都不命中），断言 `Some(a)/Some(b)/None` | 全对才 true |
| `t_state_machine` | 走完 6 条合法迁移 + 3 条非法迁移，断言非法都返回 `Denied` | 全对才 true |
| `t_device_occupancy` | 认领一台设备后 `occupancy_by_state()` 的五格和 == 设备总数 | 和相等才 true |

### 3.2 负样本（必须各造一条）

| 负样本 | 做法 | 期望 |
|---|---|---|
| 匹配器空转 | `match_device` 恒返 `None` | `t_match_device` 红 |
| 状态机放行非法迁移 | 去掉 `Unclaimed → Active` 的拒绝 | `t_state_machine` 红 |
| 占用计数漏一台 | 只在 `Active` 时 +1，`Failed` 时不加 | `t_device_occupancy` 红 |

**每条负样本要"先红后绿"各跑一次**（`AGENTS.md`：量具自己也会错）。

### 3.3 宿主机第二台仪器

本设计**单台仪器就够**：匹配器与状态机是纯逻辑，没有硬件参与。
不需要 pcap / PPM / pmemsave 那类第二台仪器——这一点要说清，
否则会有人为了"对齐纪律"去硬造一个没信息量的对账。

## 4. 容量与约束（会直接限制设计）

| 约束 | 实测值 | 影响 |
|---|---|---|
| `MAX_DEVICES` | 64（`bus/pci.rs`） | 够；但 `truncated` 必须可见 |
| `MMIO_SLOTS` | 8（`driver/mod.rs`） | **一个驱动 1 格，`probe()` 还会临时多占 1 格** |
| `DMA_SLOTS` | 8 | 同上，一个驱动 1..2 格 |
| 中断向量 | 16（`arch/x86_64/trap.rs` 的 `VEC_IRQ_BASE=32`/`VEC_IRQ_LAST=47`） | `irq/mod.rs` 的 `SLOTS=16`；**且没有 `occupancy()`，余量读不到** |
| 堆单次上限 | 2048（`memory/heap.rs` 的 `LARGE_MAX`） | 状态表必须定长静态，不能 `Vec` |

> **这两条 8 格是本文档要推动的第一件事**：设备模型不做容量，但
> "能接几台设备"由它决定。见 [总设计 §11](../Aurora-OS-硬件驱动体系总设计-V1.0.md)
> 的 AHE-01。

## 5. 与既有模块的关系

| 关系 | 方向 | 是否新增依赖边 |
|---|---|---|
| `driver` → `pci` | 读 `Dev` | **已存在**（`driver/mod.rs` 已 `use crate::pci::Dev`） |
| `driver` → `irq` | 认领中断 | **已存在**（`request_irq`） |
| `driver` → `memory` | DMA | **已存在** |
| `driver` → `boot` | 新增（读启动模式判断可选设备） | **新增 1 处**，站点数会进棘轮 |

最后一行要注意：ADR-044 的棘轮要求**环内边站点数只许减不许增**。
本轮重构后 `driver->boot` 已经是 1（实测），若设备模型再加一处就要
**先改基线**——那意味着要写 ADR 或至少记一条"为什么这条边必须长"。
