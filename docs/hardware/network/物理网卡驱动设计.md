## 1. 为什么物理网卡排在 TCP 之前

这一条与直觉相反，理由要写清（见 [网卡驱动设计](网卡驱动设计.md) §3.2）：

| | 物理网卡 | TCP |
|---|---|---|
| 判据 | **可复用现有 pcap 对账** | 需要新的判据（握手/序号/重传） |
| 新 syscall | **不需要** | 需要（48 起，要裁决） |
| "通过"今天能定义吗 | **能** | 不能（要先有 Socket API 形状） |

**先做不要裁决的那一半。**

## 2. 能用同一套判据的根据

`virtio-net` 的第一帧判据是（判定表第 32 行）：

```text
内核：打印 seq/长度/哈希
宿主机：pcap 里找 0x88B5 的包，用 build_net_frame 独立重算，逐字节比
```

这套东西**与驱动无关**：只要物理网卡能让**同一帧**上线，判据就能复用。
需要改的只有两处：

1. `aurora.py` 的命令行要挂**两种设备**（`virtio-net` 或 `e1000e`），
   且 pcap 的来源仍是 `filter-dump`（对 e1000e 同样有效，它是 QEMU 的 netdev 层抓包）；
2. 内核侧要能"选一台网卡"——今天 `Net` 是单设备静态量（见 VirtIO-Net 设计 §6）。

**第 2 条是前置**：物理网卡与 virtio-net 同时挂会撞 `NET_DEV`。
所以**先做 net 的设备表化**（照 `MAX_VBLK=4` 的形状）。

## 3. e1000e（82574L）：第一台

### 3.1 为什么选它

- QEMU 模型成熟（`-device e1000e`，已核实存在）；
- 寄存器面比 igb 小（igb 有多队列、RSS、更复杂的描述符）；
- 它是**真 Intel 网卡**（82574L 是真实芯片），所以在 QEMU 上做对的东西
  有真机对照价值。

### 3.2 结构要点（按 Intel 82574 数据手册的形状，**未在本机验证**）

```text
BAR0：寄存器（CTRL / STATUS / IMS / IMC / RCTL / TCTL / RDBAL / RDLEN / RDH / RDT / …）
BAR1：Flash / 扩展
EEPROM/NVM：MAC 地址（通过 EERD 寄存器读，或从 RAL/RAH 读预置值）

RX 描述符环：16 字节/条（buffer_addr + length + status/errors）
TX 描述符环：16 字节/条（buffer_addr + length + cso + cmd + status）

收：RDT 告诉设备"这些描述符可用"；设备写回 status 的 DD 位
发：TDT 推进；设备写回 status 的 DD 位
```

**必须强调**：上面这些偏移与位定义**本文未在本机读回验证**。
按本仓库纪律（`ADR-029` 的原话"手册上的偏移表必须由设备自己作证"），
实现的**第一步是取证**：

```text
读 CTRL 的已知默认位 → 打印
读 STATUS 的 LINK_UP 位 → 打印（QEMU 的 netdev 是 up 的）
读 RAL/RAH → 与 QEMU 的 `mac=` 参数对账
```

对着 QEMU 的 `mac=` 参数对账 MAC，是**最便宜的第一条判据**：
它证明"我们读到了设备"，不依赖任何后续路径。

### 3.3 五片

```text
E-1  PCI 识别 + 寄存器读取 + MAC 对账
     判据：MAC 与 QEMU `mac=` 参数逐字节相同（宿主机第二台仪器：
           命令行参数就是期望值，不需要额外工具）

E-2  复位与初始化（CTRL.RST、清 IMS、设 RCTL/TCTL）
     判据：复位后 STATUS 的位形状符合手册；RCTL/TCTL 写下去读得回来

E-3  RX 环建立 + 收第一包
     判据：宿主机从 pcap 里看到"对端发给我们的包"，且内核读回的字节与之逐字节相同
           （需要一个对端发包的机制：可用 QEMU slirp 的网关，或用第二块 netdev）

E-4  TX 环建立 + 发第一帧
     判据：**复用判定表第 32 行**（pcap 逐字节）

E-5  中断（IMS/IMC + MSI-X 或 INTx）
     判据：两本账（`irq::counts`）+ `-d int` 宿主机对账
```

**E-3 的困难要提前说**：virtio-net 的收方向判据靠"设备回我们的 ARP 请求"
（QEMU slirp 会回）。物理网卡同样能这么做——
**但前提是 E-4 已经能发**。所以实际顺序常常是 E-4 先于 E-3 完成，
而 E-3 用"发一个 ARP 请求，收回包"来完成。这个顺序倒置要写清，
否则会被当成"跳过 E-3"。

## 4. igb（82576）与 rtl8139

| 芯片 | 加什么难点 | 为什么还做 |
|---|---|---|
| **igb**（82576） | 多队列（RSS）、更复杂的描述符、需要选队列 | 它是真机常见的服务器级芯片；多队列是"驱动形状能不能扩"的检验 |
| **rtl8139** | 老式设计（C 模式寄存器、早期 RX 环是共享的） | **不同厂商的驱动形状能共存**——这是"设备模型"是否真的抽象的一次检验 |

**rtl8139 的特别价值**：它的寄存器面与 Intel 完全不同（没有"每个队列一对
RDBAL/RDLEN/RDH/RDT"，而是单个 `RBSTART` + `CAPR`）。
如果它也能塞进同一套 `DriverCtx` 与匹配器，说明抽象是对的；
如果塞不进，说明抽象只对 Intel 有效——**那个结论比"多支持一个芯片"更重要**。

## 5. 判据与第二台仪器

| 判据 | 第二台仪器 | 复用还是新增 |
|---|---|---|
| MAC 对账 | QEMU 命令行 `mac=` 参数 | **新增**（最便宜的一条） |
| 第一帧上线 | `filter-dump` pcap + `build_net_frame` 独立重算 | **复用**（判定表第 32 行） |
| 协议往返 | pcap 里同一个包再解一遍 | **复用**（判定表第 33 行） |
| 中断两本账 | `irq::counts` + `-d int` | **复用**（判定表第 25 行） |
| 覆盖率/错误计数 | 无 | 计数可见即可 |

**注意**：`filter-dump` 抓的是 **QEMU netdev 层**的包，与驱动无关——
所以它对 `e1000e`/`igb`/`rtl8139` **同样有效**。这是"复用判据"成立的技术根据。

## 6. 真机必须重测的项（QEMU 观测不到）

这些必须进 `docs/hardware/bringup.md`（本文不改那个文件，只列出）：

1. **MAC 来源**：QEMU 给的 MAC 是参数；真机可能是 EEPROM、可能是固件预置、
   可能是随机生成（某些 OEM）。**三种来源要分别处理**。
2. **DMA 地址宽度**：32 位 BAR 限制 vs 64 位描述符。QEMU 通常给低地址，
   真机可能给 4 GiB 以上 ⇒ **必须验高半**。
3. **MSI-X 表大小**：QEMU 给的与真机不同；表大小不足时的降级路径要能走。
4. **链路状态语义**：`STATUS.LINK_UP` 在真机上可能是异步的（网线插拔），
   而 QEMU 恒 up。
5. **EEPROM 读时序**：某些芯片的 EERD 读要等 ready 位，QEMU 可能立即就绪。
6. **多队列的实际队列数**：QEMU 与真机不同。

## 7. 硬约束

| 约束 | 规则 |
|---|---|
| 偏移必须由设备作证 | 不按手册写死；每个寄存器先读回再写（ADR-029 的口径） |
| 有界等待 | 环的 DD 位等待必须带超时（照 `wait_u16` 的形状） |
| DMA 缓冲不交切片 | 走 `DriverCtx::dma_*`（ADR-030 决定 4） |
| MSI 消息由核内算 | `irq_message` + 写后读回（照 `KT_IRQ_AHCI`） |
| 一个驱动一个文件 | 进 `kernel/src/driver/`，并加进 `DRIVER_MODULES` |
| 不冒认协议 | 判据帧仍用 `0x88B5` |
