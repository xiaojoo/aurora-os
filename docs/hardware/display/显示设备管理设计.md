## 1. 今天的显示栈（分四层，边界清楚）

```text
④ 会话与浮窗     fbcon 的窗口树（每会话一扇可裁剪浮窗、标签栏、下拉、设置页）
                 ADR-092/094/095/099/100/101/103/104
③ 文本终端       fbcon::Term（栅格、字形、滚动、光标、行规程）
                 ADR-088/089/093
② 像素           frame::Frame（几何、掩码、越界、双缓冲）
                 ADR-083
① 设备           Limine framebuffer（memmap 的 Framebuffer 段）
                 —— **这一层没有"设备对象"，是本文要补的**
```

**这个分层今天是成立的**：`fbcon.rs` 零 `unsafe`，所有像素写入经 `Frame::put`。

## 2. 已实施的能力（实测）

| 能力 | 在哪 | 判据 |
|---|---|---|
| 文本输出（44 号 `SYS_FB_TEXT` / 45 号 `SYS_FB_CLEAR`） | `sched/user.rs` 分派 → `fbcon` | ADR-153；判定格接受"done / no fb"两种明确回答 |

## 3. 缺的三件（本文档要补的）

### 3.1 缺一：没有"显示设备对象"

今天的形状：`Frame::init()` 直接去 `limine::framebuffer()` 拿**一份**
几何 + 掩码，映射到自己那块窗口。**没有"设备"这个概念**：

- 读不到"这台机器有几个显示设备"（`limine.rs` 读 `framebuffers[0]`）；
- 读不到"当前模式是什么"（除了 `geom()` 与 `masks()` 三格）；
- `devctl status` 里显示设备只算一个 **class 计数**（`class 0x03`），
  没有"分辨率/格式/是否可用"。

**设计**（与 [统一设备模型设计](../architecture/统一设备模型设计.md) 对齐）：

```rust
pub struct DisplayInfo {
    pub width: u32, pub height: u32, pub pitch: u32,
    pub bits_per_pixel: u16,
    /// 三通道的 (宽度, 移位)。**不用枚举**——掩码是设备给的（见 Framebuffer 设计 §1.3）
    pub masks: [(u8, u8); 3],
    pub framebuffer_size: usize,
    /// 双缓冲是否真的启用（几何超 BACK 容量时为 false）
    pub double_buffered: bool,
}
```

**注意这里刻意不用 `PixelFormat` 枚举**：与 Framebuffer 设计 §4 同一条理由。

### 3.2 缺二：没有模式管理

**第一阶段明确不做**（写进里程碑会让"通过"永不达成）：

| 项 | 为什么不做 |
|---|---|
| 分辨率切换 | UEFI GOP 的 `SetMode` 要 Runtime Services；本内核**没有** Runtime Services 调用路径 |
| 刷新率管理 | 与分辨率同源 |
| EDID 读取 | I²C over DDC；需要 GPU 驱动的 I²C 控制器，或 DDC 的 GPIO 位bang |
| 多显示器 | `limine.rs` 只读 `framebuffers[0]`；多显示器要先有多设备模型 |
| 热插拔 | **UEFI GOP 没有热插拔语义**。这五个字今天写进设计就是空话 |

**替代方案（若将来真要做）**：走 GPU 驱动（见 [VirtIO-GPU驱动设计](VirtIO-GPU驱动设计.md)），
由 GPU 设备自己提供模式设置——那是 GPU 驱动的职责，不是 framebuffer 的。

### 3.3 缺三：显示与输入的第二台仪器不在链里

这是本文档最该说清的一条（与 [Framebuffer设计](Framebuffer设计.md) §2.2 同一事实）：

- `tools/aurora.py` 里 `screendump` **零命中**、`input-send-event` **零命中**；
- 相关脚本全在 `.scratch/`，而 `.scratch/` **零个文件被跟踪**；
- 判定表 **74 行里没有一行**是显示或输入的宿主机对账。

**后果**：整个显示栈（4968 行 + 295 行）**今天只有内核自证**。
`main.rs:244` 的注释把流程写得很清楚（"取证跑用 `framebuffer,handles,resident-init`，
宿主机轮询到标记再发 QMP `screendump`"），但**宿主机那一半从未进 `aurora.py`**。

**这一条比"加功能"重要**：没有它，任何显示相关的改动都只能靠人看截图。

## 5. 硬约束

| 约束 | 规则 | 违反的表现 |
|---|---|---|
| 像素写入只经 `Frame` | `fbcon.rs` 零 `unsafe` | `check-driver-ctx` 不管它，但破坏边界会让越界检查失效 |
| BACK 不进堆 | `static mut [u32; 1280*800]` | 堆上限 2048 ⇒ OOM |
| 越界不夹边界 | 返回 `OutOfBounds` | 夹了就是把调用方 bug 藏起来 |
| 滚动用 `put_raw` | 不用 `put` | 二次打包 ⇒ 窄字段面板画糊 |
| 冻结后写入是 no-op | `freeze_band()` | 取样时刻不确定 ⇒ 对账莫名红 |
| 宿主机 dump 前必须等落盘 | `screendump` 返回 ≠ 文件已写 | 读到上一版 PPM（实测满屏 `?`） |
