# ADR-083：显示子系统第一刀——Limine 帧缓冲按物理区间自己映射，画面由宿主机 screendump 独立取证

状态：**已采纳**（2026-11-13）
关联：ADR-070（HHDM 与双棵树）、ADR-044（环内引用棘轮）、ADR-082（产品启动路径与 20/21 号控制台 ABI）、
  BACKLOG §229（S6 原始切片定义）、§239（`ensure_image` 不刷新用户产物那条量具缺陷）

## 背景

S6 要"framebuffer 终端 + PS/2 键盘"。§229 二里写的路线依据是一句 **"Limine 已给 framebuffer"**——
勘察发现它在代码里**不成立**：`kernel/src/limine.rs` 只声明了 BOOTLOADER_INFO / HHDM / MEMMAP / RSDP / MP
五个请求，`LIMINE_FRAMEBUFFER_REQUEST_ID` 从未被登记，`limine.conf` 也没有任何 `video_mode`。
所以本 ADR 的第一件事是把这句话从"预期"变成"实测过的代码"。

## 决策

### 1. 声明 Limine 的 framebuffer 请求，但**不使用它给的地址**

`framebuffer()` 只返回一份**纯数值**摘要（`FbInfo`：宽高/pitch/bpp/内存模型/掩码 + 原样地址）。
可写窗口由 `frame::Frame::init()` 拿 **memmap 里 `MemmapType::Framebuffer` 那段物理区间**
经 `hw::MmioRegion`（底下是 `mm::map_mmio`，`PageFlags::DEVICE` ⇒ UC 不缓存）自己开。

**依据是实测，不是推理**（run-973 与后续各跑）：

```text
frame: 几何 宽=1280 高=800 pitch=5120 bpp=32 掩码=红(8,16) 绿(8,8) 蓝(8,0)
frame: 地址 memmap基址=0x80000000 长度=0x3e8000 limine=0xffff800080000000
       我们的窗口=0xffff800020560000 limine==HHDM+pa=true 在我们页表里映着=false
```

即：**Limine 的地址数值上就是 `HHDM + pa`，但它在换过 CR3 之后的那棵树里没有映射**
（我们的 HHDM 只覆盖到 RAM 顶，而帧缓冲在 2 GiB）。直接用它会在第一次像素写入时 #PF。

**并且不去 deref 它"试试看"**：§236 记过顺着页表叶子 deref 把内核打挂的现场（run-943）。
这一格的答案由 `mm::is_mapped()` 问页表要，不问硬件要。

### 2. 整个特性挂在 `framebuffer` 档，默认档一行代码都不变

`resident`/`handles` 的先例是"新能力进新档"。这里更进一步：连 **Limine 请求本身**也用
`#[cfg(feature = "framebuffer")]` 门控。理由：请求一旦声明，引导器就必须提供帧缓冲，
这等于给**所有**变体新增了一条"引导可能失败"的依赖——而现有变体的启动行为是已实测的既有结论。

因此默认/handles/resident 各档的 ELF **不含**这个请求。副作用是新增的 ~150 行会移动行号，
所以**不能用 ELF 哈希当"默认档没变"的判据**（哈希必然不同）；改用的判据是
**串口日志逐行归一化后与 HEAD 那跑一致**：run-971 与 run-974 均 880 行、内容相同、
`判定=PASS`、ktests 82/82，唯一差异是启动状态区在轮换（`槽=2 seq=3` vs `槽=1 seq=2`）。

### 3. 像素写入全部走 `MmioRegion` 的带检查访问器 ⇒ `frame.rs` 零 unsafe 站点

`put/get` 把偏移交给 `write32/read32`，由它判对齐与区间。**越界返回错误，不夹到边界**
（夹了就是把调用方的 bug 藏起来）。代价是每像素一次边界检查，对本片够用。

新增的 unsafe 全部落在 `limine.rs` 读启动信息那一层（4 处 U2，白名单已按七项论证登记）——
**把"必须解引用 bootloader 写的裸指针"这件事集中到一处**，而不是散在绘制代码里。

### 4. 画面的判据是**宿主机的 PPM**，不是内核的写后读回

`build/s6a-screen-dump.py`：QMP `screendump` 取 PPM，按**串口报的几何**独立算采样点、独立解释像素。
负样本证明了这条仪器不是装饰——把 `pack()` 的通道顺序反过来：

| 观测 | 结果 |
|---|---|
| 内核自己的写后读回 | `读回不符点数=0`（**仍然绿**：读写共用同一个错公式） |
| 宿主机 PPM 采样 | 下左红 `期望=ff0000 实际=ff00ff`、下右蓝 `期望=0000ff 实际=ff0000` ⇒ **FAIL** |

⇒ **"字节还在窗口里"与"设备显示了它"是两件事**，前者永远证不了后者。夹具另配一格**反空转**：
在绿带位置问一次"是不是红色"，必须**不等**；少了这格，"四点全对"可能只是根本没在比颜色。

### 5. 键盘（S6c）复用 21 号 `console_read`，不开新 syscall 号

裁决口径：PS/2 解码出的字符并入控制台输入源，用户态仍用同一个 Console 句柄的 `console_read` 读。
`console_read` 的**输入源语义**从"只有串口"变成"串口或键盘"——这是本 ADR 记录的变更点；
20/21 号的编号、权限检查与句柄形状都不动。

## 备选方案

- **直接用 Limine 给的 `address`**：否。决策 1 的实测已经把它证伪（我们页表里没映射）。
- **Bochs DISPI 编程模式（PCI BAR0 + 索引口 0x1CE/0x1CF）**：本片不做。设备确实在总线上
  （`ktests/driver.rs:186` 钉着 `0x1234:0x1111`），但要新增驱动模块并扩 `check-driver-ctx` 的扫描清单，
  而默认分辨率已经能出画面。留作"第二台仪器"或需要改分辨率时再做。
- **UEFI GOP**：否。本内核在 Limine 之后不再持有 boot services，仓库里也没有先例。
- **把 `frame` 挂进 `pci` 逻辑模块**：否。它不是 PCI 设备，挂进去会新增 `pci->boot` 边，
  并把 `pci->memory` 的环内引用从 9 顶到 12——ADR-044 的棘轮只许减。改为新开 `display` 逻辑模块。

## 影响

- 新文件 `kernel/src/frame.rs`（零 unsafe）、新逻辑模块 `display`、新特性 `framebuffer`。
- `limine.rs` 新增 4 处 U2 ⇒ 白名单 `limine U2=14`，普查总计 **409**（U1 75 · U2 108 · U3 13 · U4 131 · U5 46 · U6 36）。
- **串口仍是权威判据通道**：本切片只新增日志行，没有改动任何既有行的字节与顺序。
- 不改锁序、不新增锁、不新增 syscall 号、不拆 crate。

## 验收与负样本

- 实测：`framebuffer` 档 `verdict: PASS`、`qemu_rc=33`；PPM 1280×800 与串口几何一致；
  四个采样点（上左黑 / 下左红 / 下中绿 / 下右蓝）逐位相同；反空转格成立。
- 负样本：`pack()` 通道序反转 ⇒ 宿主机红、内核读回仍绿（决策 4 的表）。
- 顺带修掉一个真实潜在缺陷：`pack()` 原来没把通道掩到 8 位。在这块 8/8/8 的屏上
  "不掩"恰好也得对（每个字段写进去的是原值的高位前缀，OR 起来仍是原值——四个采样点逐位相同），
  但换 5/6/5 面板就会串色，而**串色不会让任何判据变红**。已补 `& 0xFF` 并写明理由。

## 迁移与回滚

- 回滚：关掉 `framebuffer` 特性即回到"不请求、不映射、不画"，默认档与既有各档一字不变。
- 不可回滚部分：无（没有落盘状态、没有 ABI 变更）。

## 未决

1. **fbcon（S6b）与画面稳定性**：图案一旦有第二处写入就没有静止可取的时刻，
   需要一条"冻结带"或"到此不再镜像"的契约，否则 PPM 对账会与串口输出抢时间。
2. **键盘注入通道（S6c）**：走 QMP `sendkey`。但 §235 记的 "serial-rx-probe 与 QMP 组合被拒" 与
   §237 记的 "resident 产物 × socket chardev 间歇挂" 都还没解决，S6c 的取证接线要避开那一格。
3. `framebuffer` 不在判定表里 ⇒ **没有 durable 矩阵行**，像素判据目前只活在一次性夹具里。
4. 非 8/8/8 面板、非 32bpp、多帧缓冲（`count>1`）都走"明确拒绝"，没有实测过真实硬件。

## 补记（2026-11-13）：S6b —— 文本→像素的机制与**冻结契约**

### 7. 冻结契约：画面要有"确定的静止时刻"，靠一次性闸门而不是靠时机猜

正文区一次性画满之后，`fbcon::Term::freeze_band()` 把 [`BAND_TEXT`] 写进底部两行里的首行，
然后**永久关上** `FROZEN` 闸门；之后任何 `print_line`/`put_cell` 都是 no-op。
内核紧接着在串口打 `fbcon: 已冻结 …`，宿主机**以这行为准**才 `screendump`。

为什么不能像 S6a 那样"画完就等着"：只要画面还会被写第二次，"可以取 PPM 的那一刻"就不存在，
对账会莫名其妙地红（或更糟：忽红忽绿被当成抖动）。所以契约的两端都是可测的——
串口少了这行 ⇒ 夹具等不到就绪；画面还在变 ⇒ 同一张 PPM 两次采样不一致。

闸门用原子量而不是锁：本模块只在启动阶段单线程用，而"冻结之后不许再写"这件事
不该依赖调用顺序正确才对得上。**不新增锁 ⇒ 不动 `lock-order.md`。**

### 8. 字形是"两边同算的确定性函数"，**不是可读字体**（这条不许含糊）

`fbcon::glyph(ch) -> [u8; 8]` 由码点算出，ADR 把公式写死，宿主机夹具照着**独立实现一遍**。
于是本片验的是**栅格、寻址、pitch、颜色、越界、覆盖度**——这些是真会错的地方；
**"字形好不好看、是不是可读的 ASCII 字体"不在判据里，也没假装在**。
可读字形是下一步（要字体资产 + 逐字形验收）。

### 9. 本片交付了什么、没交付什么

交付：8×8 字符栅格（由几何推导列数行数，**不写死分辨率**）、`put_cell`/`print_line`、
底部冻结带、闸门自证、宿主机逐像素对账 + 两条反空转格。
**没交付**：滚动（`scroll_up` 我写了第一版但调的是不存在的 API，与其留个半错的实现，
删掉并写在这里）、真日志镜像（`serial::line` 一行都没动 ⇒ 串口日志契约与 S6a 逐字节相同）。

### 10. 实测

- 内核（`framebuffer` 档，elf `632696a44ab5`）：
  `fbcon: 栅格 160x100 正文行=98 冻结带首行像素=(0,784) 带宽字符=28 文本=AURORA S6B FREEZE 0123456789`、
  `fbcon: 冻结后再写无效=true（带首像素 0x00ffffff vs 0x00ffffff）`、`判定=PASS`、`qemu_rc=33`。
- 宿主机（`build/s6b-freeze-check.py`）：PPM 1280×800 与串口几何一致，
  **28 字符 × 64 像素逐位相同（不符点数=0）**；反空转 A 带里有 717 个前景像素；
  反空转 B 出现 5 种互不相同的格子；覆盖度交叉核对"内核报 28 / 宿主机比对 28"。
- **负样本**：把内核 `glyph()` 的阈值 `2` 改成 `3` ⇒ 宿主机 **357 处不符、FAIL**。
  这一格同时证明了两件事：判据会咬，**且两边真是各算各的**（若共用实现，这个变异会一路绿到底）。
- **夹具自己也被证了一次**：第一版夹具用 `文本=(\S+)` 抓期望串，遇到 `BAND_TEXT` 里的空格
  只抓到前 6 个字符，于是"比对了 6 字符"却报 PASS。已改成抓到行尾并加了那行**覆盖度交叉核对**
  ——少了它，这种"只验了四分之一"的错误会长期看起来像全绿。

### 11. S6b-2：滚动的像素证人与取证时机

滚动**逐像素搬**（新增 `Frame::put_raw`：搬已打包的原生值，不走 `put` 的二次打包路径）。
判据形状由 `fill_body` 的定义给出，宿主机独立复算"滚动后第 r 行 == 滚动前第 r+1 行"，
并带一条**反空转**（按"根本没滚"去比必须不符）。负样本 M=去掉 `scroll_up` 调用 ⇒
正文第 0/50 行各 4711 处不符、反空转格翻到 0（两者互斥地动，不是同一条件写两遍）。

**取证时机的结论有普适性**：冻结标记之后串口只剩 `verdict:`+`qemu-exit=`（几毫秒），
宿主机 20 ms 的轮询周期根本等不到 ⇒ 取证跑必须让系统**活着等**，本仓库现成的机制就是
`resident-init` 的 park。⇒ 于是这类跑里 `HANG(-1)` 是正常形状，**退出码不作判据**。
另一条同族教训见 BACKLOG §242 第四节：画面文本一律用引号包住，字段后面还有字段时禁止"抓到行尾"。

### 12. S6b-3：日志逐行镜像——**边方向是决策**，环归日志层而不是归显示层

第三次尝试才做对的那一件事：镜像字节环**住在 `serial`（`diagnostics` 逻辑模块）**，
`fbcon`（`display`）只读它，画图由 `main` 的 tail 阶段驱动。

理由是一条纯结构的事实：`fbcon` 自己要用 `log_info!` ⇒ `display -> diagnostics` 这条边本来就在。
第二版把环放在 `fbcon` 里、让 `Sink::write_str` 反向调进来，于是多出一条 `diagnostics -> display`，
两两条合成**真环**，被 `check-module-interfaces` 的 `baseline.known_scc` 拦下。
**没有把 `display` 塞进 `known_scc` 让门禁变绿**——那是把真环合法化，正是基线存在的目的。
倒过来之后只剩单向边，登记 `display.dependencies += diagnostics` 与
`diagnostics.allowed_callers += display` 即可，棘轮一格未放宽。

⇒ 教训：**旁路挂钩先问"这条边会不会成环"，再问"代码写在哪方便"**。

三条实测细节（都是"跑起来才暴露"的那类，见 BACKLOG §243/§244）：
- 行尾不经过 `Sink`（由 `putb` 直接写串口）⇒ 必须由 `line()` 调 `mirror_note_break()` 单独通知；
- 环必须**循环覆写**（"填满即弃"留下的是最老字节，与"最后 N 行"正好相反），
  且绕回处窗口开头那一截是残行，必须丢掉；
- 消费端**不许开 `Vec`**（堆上限 2048，8 KiB 分配直接 39），用两遍扫描 + 栈上 200 字节行缓冲。

判据：画面正文**末行** == 串口上"冻结标记之前最后一条日志的正文"（剥 `[级别] 序号` 前缀；
前缀不经过 `Sink` 所以从没进环），由宿主机照 `glyph()` 公式独立复算逐像素比；
配**反空转**（末行等于倒数第二条必须不符）与**负样本**（不开 `fbcon-mirror` 档 ⇒ 末行必须不符）。
"上一行"那条比对**不作判据**：shell 直写串口会与内核前缀粘在同一物理行、且 `{:?}` 跨行打印，
用"按换行切串口文件"复现环的行结构本身是个未证的模型——不拿未证模型当判据。
