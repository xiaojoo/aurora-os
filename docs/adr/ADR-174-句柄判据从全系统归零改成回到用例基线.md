# ADR-174：`t_fat32_exec` 的句柄判据从「全系统归零」改成「回到本用例基线」

状态：已采纳（2026-11-20）
关联：AGENTS.md「用例必须自足」、§442（第一次实例）、§457（第二次实例）、ADR-173

> 这是「单跑绿、整链红」的**第二个确定成因**，而且它比 ADR-173 那个更严重：
> 它是**判据本身写错了**，不是量具边界太紧。

---

> ## ⚠ 归因更正（2026-11-21，见 BACKLOG §463 三）
>
> **本文原来的归因是错的。** 它说 `live()==0` 红是因为「**启动任务的常驻句柄**」。
> 后续用 1027 个历史样本检验，**证据不支持**：
>
> | 检验 | 样本数 | 读数 |
> |---|---|---|
> | 魔数正确（容器真读到 ELF）**且** `表清空=false` | 1027 | **0 条** |
> | 魔数正确 **且** `表清空=true` | 1027 | **287 条** |
> | `handle-reap` 的 `live` 读数 | 1114 | **恒为 1** |
>
> 三条合起来的结论：
>
> 1. **容器正常跑完时 `live()` 恰好回到 0**（287 次）。若启动任务真有常驻句柄，
>    这 287 次里 `表清空` 应当恒为 `false`——实测一次都没有。
> 2. `handle-reap` 的 `live=1` 是**它自己刚 grant 的那个 `keep`**
>    （源码 `:1719`，判据 `live_after == 1` 就是写死等这一格），不是常驻句柄。
> 3. **决定性反证**：若启动任务有常驻句柄，`finish_sweep` 会在**每一条**用例边界
>    都报「仍有 1 个句柄没关」。实测 `run-8163` 只在 `t_fat32_exec` 起**连续 6 条**
>    报就停——那是**某条用例漏了一个句柄**，被后面的 `reset_for_test()` 清掉。
>
> **真因**：`run-8163` 里 `t_fat32_exec` 红是因为**容器没读到 ELF**——
> `魔数=Some(0xdeadfffc)` 是垃圾值，正确的 ELF 魔数是 `0x464c457f`。
> 那一格单独就能让它红，**不是** `live()==0` 的顺序依赖。
> 而「容器读不到自己的页」是 §461/§465 的账。
>
> ## 改法不变，叙事变
>
> `live()==0` → `live()==h0` **仍然是对的**，但理由要换：
>
> - **原来写的理由**（启动任务有常驻句柄）—— **不成立**；
> - **真正的理由** —— 判据的语义该是「**本用例**授出的句柄回到基线」，
>   而不是「全系统归零」。后者会把**别人的**泄漏算到本用例头上。
>
> **天然实证**：`run-2602`/`run-2603` 里 `t_vmo_syscalls` 报 `live=2` 判红，
> 而泄漏实际来自**前面**的 `t_fs_rw_syscall23`（那一跑每个边界都报「仍有 2 个句柄
> 没关」）。`t_vmo_syscalls` 什么都没做错，却被记了别人的账。
>
> **所以本文的标题「句柄判据从全系统归零改成回到用例基线」是对的，
> 而「一、现场」里那个归因是错的。** 读本文时以本节为准。

---

## 一、现场

整链 chain7 里 `fat32-exec` 跑了 5 次，**同一份 ELF（`4a98b5407b7a`）有时绿有时红**。

红的那次（`run-8163`）：

    elfdisk: 判据 同长=true 走链=true 字节同=true 段表同=true 跑通=false \
             元数据说大被拒=true 截短被拒=true 收尾干净=true 句柄路径=true ring3句柄=false ⇒ false
    [fatal] 用例收尾不变量破坏：test=t_fat32_exec 之后仍有 1 个句柄没关（close 或 revoke_task）

而 `ring3 句柄` 那一行的细节：

    elfdisk: ring3 句柄 魔数=Some(0xdeadfffc) done=Some(310383693381) 句柄值=0x110000 表清空=false ⇒ false

**七项全过，只有 `ring3句柄=false`**，而它由三格合成：

    let table_clean = crate::handle::live() == 0;
    let ring3_ok = h_magic == Some(0x464c_457f) && h_done == Some(...) && table_clean;

---

## 二、根因：`live() == 0` 要求全系统句柄归零

同一份日志里另一条用例的读数说明了问题：

    handle-reap: drained=true state=Free live=1 revoked=2 死者句柄都没了=true **启动任务句柄还在=true** ⇒ true

**`live=1` 是启动任务自己的常驻句柄**，设计上就该存在（`t_handle_reap` 自己都把它
当成正确状态）。

所以 `live() == 0` 这条判据的意思是「**全系统一个句柄都不能有**」——
而它想证的是「**用户程序 close 之后，我们授出的那个句柄没了**」。**两件事。**

### 为什么单跑绿、整链红

| 顺序 | `live()` | `table_clean` |
|---|---|---|
| 单跑 `fat32-exec`（`handle-*` 还没跑） | 0 | 侥幸 true |
| 整链（`fat32-exec` 排在 `handle-*` 之后） | ≥1（启动任务） | **必然 false** |

**这是「判据依赖用例顺序」，AGENTS.md 明令禁止的那一类。**
`.ktests` 的顺序由链接器决定，所以这条判据在单跑里绿得毫无意义。

---

## 三、修法：比基线，不比 0

`handle` 模块只提供 `live() -> usize`（全系统总数），**没有按句柄值查的函数**。
加一个新 API 会动 `handle` 的契约（AGENTS.md：改契约先问），而这条判据不需要它。

改用**基线差值**——与本用例 `clean_up` 那条 `reservation_count` 同一手法：

    let h_before = crate::handle::live();     // 用例开头
    ...
    let table_clean = crate::handle::live() == h_before;

### 基线必须记在用例开头（这一版踩过一次）

第一版我把 `h_before` 记在 ring3 那段之前（第 864 行），而**句柄路径测试在第 737 行**。
若那段泄漏，基线已经包含了泄漏后的值 ⇒ 判据看不见。

**基线必须记在「本用例授出任何句柄之前」**，所以移到用例开头、
与 `let before = mm::reservation_count()` 同一位置。

### 为什么这不是放宽

`ring3_ok` 仍要求：

- `h_magic == 0x464c_457f`（用户程序**真的读到了 ELF 魔数**）
- `h_done == 0x4844_4f4e_45`（用户程序**真的写完了 done 标记**）
- `live()` 回到基线（**真的 close 了**）

**若用户程序漏 close，`live()` 会比基线多 1，仍然红。**

## 四、负样本

| 判据 | 负样本 | 红在哪 |
|---|---|---|
| 用户漏 close | 让用户程序跳过 `close` | `live() = h_before + 1` ⇒ `table_clean=false` |
| 用户没读到 ELF | 把 ring3 的读权限去掉 | `h_magic != 0x464c_457f` ⇒ `ring3_ok=false` |
| 基线记晚 | 把 `h_before` 移回 ring3 之前 | 句柄路径那段泄漏时判据看不见（**本 ADR §三 记的就是这次**） |
| 顺序依赖复发 | 让本用例排在 `handle-*` 之前跑 | 应仍绿（基线法不依赖顺序） |

## 六、这一条与 ADR-173 的区别（值得记）

| | ADR-173（`q2` 兜底） | ADR-174（`table_clean`） |
|---|---|---|
| 性质 | **量具的边界太紧** | **判据本身写错了** |
| 表现 | 判定级 `HANG`（用例没红） | 用例红，且给了误导性的 `ring3句柄=false` |
| 修法 | 调大兜底 | 改判据的**语义** |
| 危险度 | 中（归因错） | **高**（判据绿得毫无意义，掩盖了真问题） |

**ADR-174 这一类更危险**：它在单跑里是绿的，所以「新写一条判据、单跑验一下就收工」
会把它当成已验证。**判据必须在自己那个域的完整顺序里验过。**

## 七、未决

1. **还有没有别的判据用 `live()==0`**：本轮只改了 `t_fat32_exec` 这一处。
   应当全仓搜一遍同类形状（`== 0` 的全系统计数）。
2. **`0xdeadfffc` 的来源未查**：源码里没有这个常量，它是用户程序崩溃/未写时
   留下的旧内存值。**这不影响本 ADR 的结论**（`table_clean` 单独就能让它红），
   但「用户程序为什么没读到」值得单独看——本次是 `live()` 判据先红，掩盖了它。
3. **`handle` 缺按值查的 API**：加 `live_of(h) -> bool` 会让这类判据更直接。
   但那是改契约，需先问。
