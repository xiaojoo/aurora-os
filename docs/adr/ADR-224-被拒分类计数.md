# ADR-224：`read_at` 被拒的分类计数

状态：**已采纳**（2026-11-23：分类计数已接进判据日志）

关联：ADR-223（它把「被拒 41613 次」当成调度饥饿，**那个判断是错的**）

> 给「读用户页被拒」加分类计数。**顺手纠正了 ADR-223 的一个误判。**

## 纠正 ADR-223

ADR-223 把 `被拒=41613` 解释成「调度饥饿」—— **错了**。

`被拒` 的实际来源是 `user::read_at_refused()`，即 `peek_u64` 返回 `Err` 的次数，
**与调度器无关**。

正确的症状链是：

```
内核读容器数据页失败（NotMapped）
  => 读不到 DONE 哨兵
  => 窗口超时
  => 所有信箱槽读到 0
```

**是「读不到用户页」，不是「探针没被调度」。**

ADR-223 里那句「探针任务被调度了 4 万多次却一次都没真正跑起来」是错的 ——
`rounds` 是**内核窗口里的轮询次数**，不是调度次数。

## 交付

```rust
pub fn read_at_refused_by_kind() -> (u64, u64, u64, u64, u64)
// (不在用户区, 没映射, 不共享, 不可写, 太长)
```

五个计数器分开数，对应 `PtrError` 的五个变体。

判据日志多一行：

```
fs-open-ring3: 被拒分类 不在用户区=0 没映射=41613 不共享=0 不可写=0 太长=0
```

## 为什么必须分类

`PtrError` 的五个变体**处置方向完全不同**：

| 变体 | 含义 | 该查什么 |
|---|---|---|
| `NotUserRange` | 地址在低半区之外 | 调用方传错了 |
| `NotMapped` | 页表链某一级 P=0 | 映射丢了 / 被回收 |
| `NotSharedWithUser` | 有映射但 U/S=0 | 权限设错 |
| `NotWritable` | 可读但不可写 | W^X |
| `TooLong` | 超过 `COPY_MAX` | 容量边界 |

只知道「被拒 41613 次」等于什么都不知道。

## 分类计数立刻兑现了价值

接上之后第一次抓到失败，日志说：

```
窗口前后 换人 0→8 tick 6→13 rounds=3688 served=34 被拒=0
FAIL t_sdkdemo
```

**`被拒=0`，`t_fs_open_ring3` 这次是好的** —— 失败的是 `t_sdkdemo`（`va=0x100002000 没映射`）。

若没有分类与总计数并列，我会继续以为 `t_fs_open_ring3` 在偶发。

## 一个新读数

`t_sdkdemo` 的偶发**只在 `fs-open` 档出现**：

| 档 | 4 次跑 |
|---|---|
| `handles` | **4/4 全绿** |
| `handles,fs-open` | 6 次里 1 次 `t_sdkdemo` 红 |

两档的差别是 `MAX_HANDLES`（131072 vs 16384）⇒ **`.bss` 布局不同**。
这与 ADR-207 修 `t_sdkdemo` 那次是同一类（布局耦合），但这次是 `fs-open` 档特有的。
