# ADR-238：启用页缓存让失败率从 4/20 涨到 7/20（**已回退**）

状态：**拒绝**（2026-11-23：实测 7/20 vs 4/20，已回退）

关联：ADR-219（缓存接入）、ADR-221（当初回退的理由）、ADR-222（`XFER` 锁序已修）

> ADR-221 因为 `XFER` 锁序违规把 `read_chunk` 回退到不缓存版。
> ADR-222 修好了 `XFER`，所以本 ADR 重新试 —— **失败率反而上升。**

## 前提已满足，但结果更差

锁序前提：

| 项 | 值 | 判定 |
|---|---|---|
| `XFER` | `RANK_GROW(4)`（ADR-222 修好）| ✅ |
| `CACHE_LOCK` | `RANK_GROW(4)` | ✅ 同 rank，但不嵌套 |
| `cached_read` 结构 | 锁内查表 → **放锁** → 读盘 → 锁内写回 | ✅ 不重叠 |

**锁序完全合法**（`handles` 回归 `FAIL=0`，无锁序违规）。

但：

| 档 | 失败率 |
|---|---|
| `handles,fs-open`（**不缓存**）| **4/20** |
| `handles,fs-open`（**缓存**）| **7/20** |

## 为什么缓存让情况变坏

缓存改变了两件事：

1. **读路径的时序** —— 命中时不碰设备，比未命中快几十微秒；
2. **`CACHE_LOCK` 的获取/释放** —— 每次读多两把锁（查表 + 写回）。

而那条既有竞态（ADR-228~237：探针自己的页在被回收后仍被读）**对时序极度敏感**：

- ADR-227：加 `log_info!`（几十微秒）⇒ 偶发消失；
- ADR-233：多取一次 `RUNQ` 锁 ⇒ 偶发消失；
- **本 ADR：加缓存（时序变快）⇒ 偶发增加**。

**同一个竞态，三种不同的时序扰动，三个不同的失败率（0/20、0/20、7/20）。**

## 这给出一个重要的推论

> **那条竞态有一个「最坏时序点」。** 让它变快、变慢、加锁、写串口，都可能落在
> 那个点的两侧 —— 于是失败率忽高忽低。
>
> 这也解释了为什么它这么难复现：**任何观测都在改变它离最坏点的距离。**

## 为什么回退

1. **缓存是性能优化，不是正确性修复** —— 不能用稳定性换；
2. **7/20 是可测量的退化**（虽然样本量不足以做严格统计，但方向明确）；
3. **那条竞态修好之后再启用才有意义**。

## 保留的成果

`read_chunk` 的注释现在写清了完整的三段历史：

1. ADR-221：因锁序回退；
2. ADR-222：锁序修好；
3. ADR-238：锁序合法但实测退化，仍回退。

**下一次有人想启用缓存，不必重走这三步。**

## 读数

| 项 | 结果 |
|---|---|
| `check` | **21/21** |
| `handles`（缓存版）| **FAIL=0**（锁序合法）|
| `handles,fs-open`（缓存版）| **7/20** |
| `handles,fs-open`（不缓存）| **4/20** |

## 未决

1. **那条竞态（ADR-228~237）** —— 修好之前不要启用缓存
2. **7/20 与 4/20 的差异未做统计检验** —— 样本量不足，但方向与机制解释一致
3. **缓存的收益未测量** —— 本 ADR 只测了稳定性，没测「省了多少 I/O」
