> 写作纪律：已采纳 ADR 与有测试证据的事实优先于本文的目标设计；发现冲突先记差异，
> 不要为了让文档一致去改已经验证的结论。每条结论标「实测」或「推断」。

## 背景

要决策的是什么、现在的代码/实测事实是什么、为什么现在必须决定。
引用的数字要写来路（哪一跑、哪份日志、哪次 bench）。

## 决策

用可执行的语句写：谁拥有什么状态、谁只能通过什么接口访问、失败往哪一级升级。
涉及接口时写清：上下文（BOOT/KERNEL/IRQ_OFF/ISR_TOP/DEFERRED/USER_ENTRY/PANIC）、
资源所有权、错误分类（A 业务 / B 资源设备 / C 契约违例 / D 完整性）、是否可能阻塞。

## 备选方案

列出认真考虑过的方案与不选它的理由。不要写“没想到别的”。

## 影响

正面、负面、代价、对已有 ADR / 测试 / 基线的影响。不能只说好处。

## 验收与负样本

- 判据在哪一跑、哪一行日志、哪个宿主机对账项；
- 至少一条能让判据变红的负样本（变异证红）；
- 涉及硬件/存储/网络/签名的，写第二台独立仪器。

## 迁移与回滚

旧代码/旧接口怎么迁；回滚条件是什么；不能回滚的部分要写明。

## 未决

本 ADR 不解决的问题，以及需要哪份 ADR / 哪次实测才能关闭。
