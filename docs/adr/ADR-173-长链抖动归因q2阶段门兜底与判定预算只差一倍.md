# ADR-173：长链抖动的第一个确定成因——`q2` 阶段门兜底与判定预算只差一倍

状态：已采纳（2026-11-20）
关联：BACKLOG §383（该用例上一次调兜底的记录）、§458（本次现场）

> 长链抖动（"单跑绿、整链红"）干扰了至少三轮读数。**本文归因其中第一个确定成因**，
> 不声称归因全部。

---

## 一、现场（chain6 第 21 跑）

量具自己已经把话说清楚了：

    判定级停住现场：用时 120.0s / 预算 120s（**恰好等于预算** ⇒ 先怀疑预算与宿主负载，再怀疑 guest 死锁）
    跑过用例 64 条；最后一条 = t_cross_cpu_lock_contention -> ok（序号 0x00000325）
    ktests 收尾行 = **无**（没跑完）；退出行 = **无**
    串口最后一行 = [warn] 0x00000326 q2: 工人超时 走=60000092068 t0=0x31bf3a37b8
    红过的用例 = 无

`走=60000092068` ≈ **600 亿周期** —— 那正是 `q2_worker` 的**兜底上限**，
说明阶段门 `Q2_ARMED` 一直没开。

---

## 二、机制

`q2_worker` 的等门循环：

    while Q2_ARMED.load(Acquire) == 0 {
        if tsc::now().wrapping_sub(a0) > 200_000_000_000 { break; }   // 约 60 s
        spin_loop();
    }

而 `Q2_ARMED.store(1)` 在**spawn 完七条线程之后**（`sched.rs:2125`）。
两者之间是 spawn + `attach_thread` + 计时器探测。

**宿主机有累积负载时，那段准备能超过 60 秒** ⇒ 工人先撞兜底、置僵尸 ⇒
主线程随后在 `q2_sample` 里等不到人 ⇒ 卡到判定预算。

**注释里早就记过同一件事**：

> 合并日那次 43 s 的跑里，spawn 循环本身就烧掉 27e9 周期（宿主机停顿），
> 六条工人在"还没开始采样"时就撞上兜底收工，进程被提前置僵尸 ⇒ 后续 attach 失败、峰值读成 0（§383）

**43 秒已经离 60 秒兜底不远。** 整链跑到第 21 跑时宿主已有累积负载，就越过去了。

---

## 三、修法：只改量具的边界

| 兜底 | 原值 | 新值 |
|---|---|---|
| 阶段门（等 `Q2_ARMED`） | `200e9`（约 60 s） | **`1000e9`（约 300 s）** |
| 释放门（等 `Q2_RELEASE`） | `60e9`（约 19 s） | **`300e9`（约 90 s）** |

### 为什么这不是「调大超时掩盖问题」

1. **兜底的作用是「用例没走到时别永远占着槽」**（注释原话）。它的量级应当
   **远大于任何可能的准备阶段**，而不是"刚好够"。
2. **60 秒兜底与 120 秒判定预算只差一倍** ⇒ 宿主动一下就先撞兜底，
   表现为「用例没红、判定级 HANG」——**归因全错**。
3. **真死锁仍然会被抓**：新兜底 300 s **大于** 120 s 判定预算，
   所以判定级会先红。红的顺序变对了。
4. **不动 `ARMED` 的位置**：注释明写它必须在采样开始前开、不能在 spawn 前开
   （否则工人会在"还没开始采样"时就冲过释放门）。**改数值不动这个语义。**

### 负样本

| 判据 | 负样本 | 红在哪 |
|---|---|---|
| 真死锁仍被抓 | 让 `q2_sample` 永不返回 | 120 s 判定预算先红 ⇒ `HANG` |
| 兜底仍有界 | 删掉兜底判断 | 工人永远占槽 ⇒ 后续 `spawn` 报 `Unsupported` |
| 峰值判据不变 | 让一条工人提前收工 | `peak_live != ok_n` ⇒ 用例红 |

## 四、另一个独立的真问题：并发跑会互相抢镜像

复现长链抖动时**意外撞出来**的：

并发起 3 个 `aurora.py` 再跑 `virtio-blk`：

    判定=FAIL qemu_rc=35 用时=11.3s 启动产物=**fs-open/elf**

**启动产物是别的档的 ELF。** 根因：多个 `aurora.py` 共用
`build/aurora.img` 与 `build/image-info.txt`，互相覆盖。

**影响面**：整链是**串行**跑的，所以这不是长链抖动的原因。
但**它会让"我在后台跑整链、同时手工跑一档"这种操作给出错读数**——
本轮就撞到了（`fs-open` 覆盖了 `virtio-blk` 的镜像）。

**未修**（记进 §五）：修法要么加文件锁、要么按 PID 分目录。
那会改 `build/` 的布局，属于独立决定。

---

## 五、未决

1. **长链抖动是否只由这一个成因造成**：**不声称**。chain6 的 6 条不符合里，
   `探针几何` / `FS-03` 两条是 `FAIL` 而非 `HANG`，机制可能不同。
   chain7 跑完才能说这一条修掉了多少。
2. **并发跑的镜像抢占未修**：见 §四。今天靠"串行跑"规避。
3. **`q2` 的 spawn 段为何会慢**：本文只证"它慢过 60 秒"，**没证为什么慢**。
   宿主累积负载是推断，未单独测量。
4. **兜底值 300 s 是否够**：若某天 spawn 段超过 300 s，同样的形状会再来。
   那时应当先查"为什么 spawn 要 300 秒"，而不是继续加大。
