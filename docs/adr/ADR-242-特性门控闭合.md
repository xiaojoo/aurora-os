# ADR-242：特性门控闭合 —— 默认档从「两天编译不过」修回可编译（并补第 21 道门禁的规则 4）

状态：**已采纳并实测**（2026-11-23；默认档与 `handles` 档均编译通过，`check` 21/21，负样本证红）。
关联：ADR-176（声明的号必有臂 / 臂无条件存在）、ADR-186/187/180/191/204（引入这些引用的切片）、
BACKLOG §562。

> 写作纪律：已采纳 ADR 与有测试证据的事实优先。每条结论标「实测」或「推断」。

## 背景：一个被所有局部判据漏掉的洞

2026-11-23 复核 ADR-241 时按 §5 跑整链，第一步 `=== 正向 ===`（默认档、无特性）就构建失败：

    error: could not compile 'aurora-kernel' due to 29 previous errors

**实测**：`git blame` 把 29 条逐条点到 2026-11-22 的 `96c04ac` / `ad10746` / `3d87727` / `bbd0407` /
`8f55795`，**没有一条来自 2026-11-23**。同一份源码在 `--features handles` 下编译通过。

**根因（实测，一句话）**：`handles` 关掉之后 `crate::handle` 整个模块不存在
（`main.rs:109` 的 `#[cfg(feature = "handles")] pub(crate) use capability::handle;`），
而 14 条分派臂 + 8 处调用点**没有对应的 cfg**，仍然引用它。

**为什么两天没人发现（实测）**：

- 最后一次整链全绿是 2026-11-21 23:40（`build/matrix-lead-485b.txt`）。
- 之后 50 个提交（`f406480`…`dfb78e3`）**没有一次跑过整链**：ADR-228~241 每一轮只跑
  `check` + `handles,fs-open` 单档重复跑，而 `check` **不编译**（工具自己的注释写着「`check` 不编译」），
  单档跑又都带 `handles`。
- 于是「默认档」这个**唯一的整链入口**在无人使用时静默坏掉，而所有局部判据都是绿的。

这与 §441「一格新红被既有的红遮住」同类，但更隐蔽：**没有判据的地方坏了，不会有任何红**。

## 决策

### 1. 8 处调用点补 `#[cfg(feature = "handles")]`（无语义分歧）

| 位置 | 内容 |
|---|---|
| `sched/mod.rs` | `pub fn install_proc_of()` |
| `main.rs` | `sched::install_proc_of();` 调用点 |
| `main.rs` | `install_mac_of(..mac_for_retx)` 调用点（`mac_for_retx` 本身已是门控的）|
| `sched/proc.rs` | `proc_fd_table` / `proc_set_fd_table` |
| `sched/user.rs` | `ensure_stdio` / `preset_std_for` |
| `ktests/syscall/user.rs` | `ktest!(KT_FD_NUMBER, ..)` 注册（函数在 1326 行本就是门控的）|

这 8 处只是「引用了门控的东西，自己却没门控」，加同一条 cfg 即可，**不改任何行为**。

### 2. 14 条分派臂：**保留无条件存在，特性关时落 `nosys()`**

这是本 ADR 唯一有取舍的地方，也是**没有选 ADR-176 字面写法**的地方。

ADR-176 决策 3 明写「这些臂必须**无条件存在**」，理由是「给臂挂 cfg 会让门禁随构建配置时绿时红」。
那条理由今天仍然成立，**但它的实现方式必须换**：无条件存在 ≠ 无条件引用 handler。

    #[cfg(feature = "handles")]
    SYS_FD_INSTALL => sys_fd_install(frame),
    #[cfg(not(feature = "handles"))]
    SYS_FD_INSTALL => nosys(),

- **臂仍然无条件「存在」**（ADR-176 的意图达成：号在、功能不在）；
- 默认档真的回 **-18 ENOSYS**，而不是落 `_ => -1 EINVAL`（**这正是 ADR-176 要的**：
  用户看到的必须是「内核没写这个功能」，不是「参数错」）；
- 门禁的文本对账仍然看得见 `SYS_FD_INSTALL =>` 那一行（两种写法都匹配）。

**没选「只给臂加 `#[cfg(feature="handles")]`」**：那会让臂在该组合下**消失**，
恰好是 ADR-176 明确反对的形状 —— 默认档的 72/73/74/75/48–55 会落回 `_ => -1`，
把「功能不在」伪装成「参数错」，**归因方向相反**。这个 ADR 落地时实测确认过：
两种写法都能让默认档编译通过，所以**这个选择只由语义决定，不由能不能编译决定**。

### 3. `check-syscall-abi-arms` 补**规则 4**（这条是防止再犯的关键）

**实测：原有三条规则对这个问题完全失明。** 在坏树上跑原门禁，输出
`consts=77 arms=74 missing=[]` —— 全绿。因为规则 1/3 都是**文本对账**，只问「名字在不在」，
**看不见 cfg**。

规则 4（新增）：

> 一条 `SYS_X => handler(..)` 的臂，若 `handler` 的**定义**带 `#[cfg] `，
> 那么这条**臂自己**也必须带 `#[cfg]`。

它咬的是「条件性不一致」，**不规定用哪种修法** —— 上面两种写法都合法，只有
「handler 有条件、臂无条件」会被咬。

量具自证：解析出的门控函数少于 20 个 ⇒ 报「规则 4 在空转」（与规则 1/3 同一写法）。

## 备选方案

- **只给臂加 cfg（不落 nosys）**：能让默认档编译，但把「功能不在」伪装成「参数错」，
  与 ADR-176 直接冲突。不选。
- **默认档也挂 `handles`**：把 82 行判定表里「默认档」这一行取消，等于**删掉唯一的整链入口**，
  而那个入口正是这次发现问题的东西。不选。
- **什么都不改，只在 BACKLOG 记一笔**：默认档继续编译不过，整链继续跑不了，
  下一个人的每一轮都拿不到判定表读数。不选。

## 影响

- **正面**：默认档恢复可编译 ⇒ 整链恢复可跑；默认档的 72–75/48–55 从 `-1` 变成 `-18`
  （**语义更正确**，与 ADR-176 一致）；门禁多一条能咬的判据。
- **负面/代价**：14 个号各多一行 `#[cfg(not(..))]` 臂（共 +14 行）；规则 4 依赖
  「handler 定义前 5 行内找 cfg」这个文本启发式（**推断**：跨模块的 handler 不在作用域内，
  今天 14 个 handler 全是同文件局部函数；若将来 handler 搬到别的模块，规则 4 会静默失效，
  那时要改成解析 use 路径 —— 这条写在这里当欠账）。
- **对基线**：`handles` 档的 `.text` / `.data` 段**逐字节不变**（实测，见下），
  所以所有既有判定行与 ELF 摘要语义不受影响；变了的只有编译器匿名符号计数器。

## 验收与负样本

- **默认档 `build` rc=0**（修复前 rc=1，29 errors）。
- **`handles` 档 `.text` / `.data` 段逐字节相同**（实测：`f3cc294808e42b91` / `76aef8be0fdc8c16`，
  修复前后一致）。**整个 ELF 摘要会变**（`1923c5ee8d01` → `b5302bf56453`），
  但差异只在 `.rodata` 的 43 字节行号字段、`.strtab`/symtab 的匿名符号计数器、
  `.debug_info` —— **不是代码生成变了**。这一条必须写清楚，否则下一个人会以为
  「ADR-242 改了 handles 档的行为」。
- **规则 4 的负样本（确定性证红）**：把 `kernel/src/sched/user.rs` 换回 HEAD 的坏树，
  门禁报 **14 条**（逐条点名 `SYS_FD_INSTALL` … `SYS_SOCK_CLOSE`）；换回修复版，报 **0 条**。
  实测输出见 BACKLOG §562。
- **`check` 21/21**。

## 迁移与回滚

- 纯增量：8 处 cfg + 14 对臂 + 1 条门禁规则。回滚 = 反向删掉，默认档回到编译不过。
- **不能回滚的部分**：规则 4 一旦存在就不能「为了让某条臂过」而删 —— 删了就是回到
  门禁对这类问题失明的状态。

## 未决

1. **规则 4 是文本启发式**：跨模块 handler 会让它静默失效（见「影响」）。今天没有这种形状。
2. **`check` 仍然不编译**。这次的问题正是「门禁全绿但编译不过」，
   而根治它需要一道「真的编译一次」的门禁（代价：`check` 从 ~2 分钟涨到 ~5 分钟）。
   **本 ADR 不做**，因为那是量具预算的取舍，要单独裁决。
3. **整链读数**：本 ADR 落地后跑了一次整链，读数记在 BACKLOG §563。默认档从此可跑，
   但「50 个提交没跑整链」这个事实本身说明**纪律漏洞还在**（没人强制每轮跑整链）。

## 补记（2026-11-23，同日）：整链一跑又露出**两处**同类既有破损

§1/§2 修完默认档之后跑整链，又在两个**别的特性档**上撞到构建失败。两处都是 2026-11-22 的提交留下的，
与 ADR-241 无关，也**与「默认档」这个洞无关** —— 它们是同一个纪律漏洞的另外两个切面：
**没有任何门禁或整链覆盖那些档**。

### 补记 1：`virtio-net` 档编译不过（`DhcpReply` 类型根本不存在）

    error[E0425]: cannot find type `DhcpReply` in this scope
    --> kernel\src\network\dhcp.rs:203:27

**实测**：`git log -S DhcpReply` 只有 `e80e02b`（ADR-185）一个提交，**从引入那天起就是坏的** ——
那个提交把 `dhcp_apply(reply: &DhcpReply)` 写进 `#[cfg(feature = "virtio-net")]`，
而同文件的类型叫 `Reply`（`dhcp.rs:95`）。`DhcpReply` 在整个 `kernel/src` 里**一次都没有定义过**。

**为什么两周没人发现**：`virtio-net` 从来不是整链里的一条正向档（判定表用的是 `virtio-net-probe` 那条
**另一档**），`check` 又不编译 ⇒ 这个档从写下来那天起就没编译过一次。

**修法**：`DhcpReply` → `Reply`（`dhcp.rs:203`）。纯笔误，无语义分歧。
修后 `virtio-net` 与 `handles,virtio-net` 都 rc=0（实测）。

### 补记 2：`fs-rw` 档编译不过（ADR-221 给 `grant_vfs_file` 加了第 7 参，测试没跟上）

    error[E0061]: this function takes 7 arguments but 6 arguments were supplied
    --> kernel\src\ktests\storage\fs_rw.rs:174 / 181 / 200

**实测**：`bbd7e26`（ADR-221）给 `grant_vfs_file` 加了 `vol: u64` 参数、改了产品路径
（`user.rs:3988`），但 `ktests/storage/fs_rw.rs` 的**三个调用点没改**。
ADR-221 的提交信息里明写它只动了 `capability/handle.rs` 与 `sched/user.rs` ——
**测试文件不在它的清单里，所以它没被编译过**。

**修法**：三个调用点补 `vol`。取法与产品路径**同源**（不是随便传 0）：

    let vol = {
        let (d, _) = handle::disk_for(fs_rw::PORT, None);
        vfs_ro::volume_fingerprint_pub(&d, &log_cur.bpb())
    };

**为什么必须真算**：ADR-221 的注释写着「传 0 会让所有卷共用缓存槽，不同盘的同 LBA 直接串
（实测 `t_sdkdemo` 信箱魔数读到 0）」。测试里传 0 会让这一档**证的东西变味**
（它测的就不再是产品路径那条指纹）。

### 这两处说明的事（比修法更重要）

`check` 21/21 + 默认档能编译 + `handles` 能编译，**仍然不等于「所有档能编译」**。
本轮把 76 个特性**逐个单独 build** 了一遍：修前 **2 个红**（`virtio-net`、`fs-rw`），修后 **76/76 rc=0**。
这个 sweep 是**本轮临时做的，没有进 `check`** —— 要不要把它变成第 22 道门禁（代价：一次全档 sweep
实测约 9 分钟，比现在整个 `check` 还长），**需要裁决**。

在那之前，纪律上能做的是：**动 `#[cfg(feature = ...)]` 的提交，必须自己至少 build 一次那个档**。
ADR-221 与 ADR-185 都是没做这件事的样本。
