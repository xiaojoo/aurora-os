# ADR-164：推翻裁决 ⑥A，把安装器 / 硬件兼容矩阵 / 正式发行重新纳入范围

状态：已采纳（2026-11-20，使用者裁决）
关联：取代 `docs/Aurora-OS-未完成步骤审计-2026-11-19.md` 的**裁决 ⑥A**（D5 跳过）；
影响 `docs/hardware/testing/硬件兼容性矩阵.md`（该文档原标注"设计储备，非已立项交付物"）

> 本文记裁决，不含实施细节。

## 背景

审计文件第 32 行与第 153 行：

> **D5** 硬件矩阵与发行 | **未开始** | 安装器、兼容矩阵、正式发行（按裁决⑥A 跳过）
>
> 按使用者裁决 **④A / ⑤A / ⑥A 跳过**（无 xHCI、无 HDA、无安装器）。

⑥A 当时跳过了三件不同性质的事，**本文要分开对待**，因为它们的前置条件不同：

| 子项 | 性质 | 前置 |
|---|---|---|
| 硬件兼容矩阵 | **验证工作**，不是新代码 | 目标机型 + 真机待测项 |
| 安装器 | 新交付物 | 分区写入 + 引导配置 |
| 正式发行 | 流程与产物 | 版本号 + 包清单 + 签名 |

## 决策

**推翻裁决 ⑥A。三项重新纳入范围**，但**按依赖顺序**，且各自有硬前置：

### 1. 硬件兼容矩阵（先做，因为它不需要新代码）

`docs/hardware/testing/硬件兼容性矩阵.md` 已经写好了骨架：
三个维度（硬件部件 × 功能等级 H0..H7 × 证据等级 ⬜/🟦/🟨/🟩/⬛）、
每格必须带的四样证据。**它今天全部是 ⬜**，因为没有目标机型。

**硬前置**：`docs/hardware/bringup.md` §1 的七个字段必须填满
（机型/主板、CPU、BIOS 版本与模式、串口形态、盘控制器、内存、TPM）。
**没有机型，矩阵一格都填不了。**

### 2. 安装器

**硬前置三条**，缺一条都不做：

1. **写分区要有写方向判据**：今天 `filesystem` 的写方向判据是有的
   （判定表"FS写方向与可写卷对账"），但**整盘安装**要写 GPT + ESP + 系统分区，
   每一步都要有"写下去读得回来"的判据。
2. **引导配置生成**：`boot/limine.conf` 今天是静态夹具（`ktests/storage/vfs_ro.rs`
   里 `include_bytes!("../../../../boot/limine.conf")`）。安装器要**生成**它，
   那就需要一份能被独立校验的生成器 + 负样本。
3. **签名**：安装器产出的引导链要不要签名？若签，`security/sign.rs` 那条链
   必须在安装路径上真跑（今天它的调用点**全在 ktest 里**，启动路径零调用——
   这是审计文件 §三 第 2 条记的缺口）。**这一条要先定。**

### 3. 正式发行

**硬前置**：

1. **版本号策略**：今天没有。
2. **包清单与 SBOM 的一致性**：`docs/pkg/manifest.json` 与 `docs/release/sbom.json`
   已有，且 `check-pkg-manifest`/`check-sbom` 在对账。发行要在此基础上加
   "产物可复现"（同一份源码两次构建字节相同）。
3. **`.text` 128 KiB 上限**：已第六次扩容（20→24→32→40→48 KiB，ADR-155 到 128 KiB）。
   审计文件明写「根因是 shell 单二进制承载全部命令，**命令数继续增长会再次撞墙**」。
   **发行前必须解决**，否则发行版一加命令就编不出来。

## 备选方案

| 方案 | 不选它的理由 |
|---|---|
| 保留 ⑥A | 与"完整操作系统"目标冲突；而且"没有安装器"意味着用户无法安装它 |
| 只做矩阵，不做安装器/发行 | 矩阵是验证，安装器是交付；只做前者等于"证明了它能跑，但没人能装上" |
| 只做安装器，不做矩阵 | 装上了但不知道在哪些机器上能用——这正是今天最容易夸大的地方（`AGENTS.md` 硬约束 7） |
| 先做发行，后补矩阵 | 发行的含义是"对外承诺可用"，而承诺需要矩阵支撑 |

## 影响

**正面**：

- "完整操作系统"从"能启动的内核"变成"能被安装、能被验收、能被发布"；
- 矩阵的框架已经写好（证据等级五档），推翻 ⑥A 之后它可以开始填。

**负面 / 代价（这三项里，矩阵便宜，另两项很贵）**：

- **安装器会写用户的盘**。这是本仓库第一次做**破坏性操作**的交付物。
  必须有"干跑模式"与"写前确认"，且判据要能在不改真盘的前提下验证。
- **发行承诺会反向约束一切**：一旦发布，"这条判据今天红了"就变成对外问题。
- 审计文件 §四 第 2 条那个 `.text` 上限是**发行的硬墙**，
  而结构性解法（coreutils 拆成独立 ELF）依赖 A3 的 PATH 搜索——**未做**。

## 验收与负样本

| 子项 | 判据 | 负样本 |
|---|---|---|
| 矩阵 | 每格四样证据齐全（机型/日志/第二仪器/与 QEMU 的差异说明） | 缺"差异说明"⇒ 该格降级 |
| 安装器 | 干跑产出的分区布局与 `qemu-img` 读回一致 | 分区表写错一个字节 ⇒ 红 |
| 安装器 | 装完能从新盘启动 | 引导配置写错 ⇒ BOOT-INVALID |
| 发行 | 同一份源码两次构建字节相同 | 加一个非确定性时间戳 ⇒ 红 |
| 发行 | `.text` 在限额内 | 加一条命令 ⇒ 撞墙 ⇒ 红 |

## 未决

1. **安装器要不要签名**（见决策 §2 第 3 条）：这一条决定安装器是否依赖
   `security/sign.rs` 进启动路径，而那是审计文件记的既有缺口。**需裁决。**
2. **`.text` 上限的结构性解法**（coreutils 拆成独立 ELF + PATH 搜索）**未做**，
   而它是发行的硬前置。
3. **目标机型未定**，所以矩阵今天仍是全 ⬜。
4. **发行形态未定**：ISO？磁盘镜像？还是只发内核 ELF + 说明？
5. 本 ADR 只推翻"跳过"，不承诺完成时间。三项的规模差一个量级
   （矩阵是填表，安装器是数周，发行是流程建设）。
