# ADR-033: 更新包用一次性签名，锚点内置，但今天还不据此拒绝启动

状态：部分采纳（2026-11-06，M9-a①/② 已交付机制与判据；**接到启动决策那一半明确没做**，见"没做到的"）
关联：手册 §9.5（A/B 回滚与更新）、§9.2（`BOOT-INVALID(37)` 是"前提不满足"那一级）、§11.1
（"驱动、更新包签名 | M6"——这条排在 M6，实际到 M9 才有能验的东西）、§11.2（SBOM/可复现）、
ADR-011（可信持久存储：临时/正式/信任根）、ADR-031（状态区与"约定出来的分区"同一块空隙）、
BACKLOG 60/61

## 背景

M9 那一行是"显示、输入接口、安装、更新、签名、发布流程"，验收句"可发布候选版本"。
里面大部分条目站在今天还缺的层次上：安装/更新要有文件系统与块层通用化（M5 未完）、
输入要 xHCI/USB HID（M7 真机）、显示要 framebuffer 的第二台仪器。
唯一一条**现在就能被判**的是签名：它只需要一个哈希、一段字节、和一个能拒的判据。

签名这一列有两个陷阱，都不在"代码怎么写"这一层：

1. **常数表最容易凭记忆写错**。SHA-256 有 64 个轮常数 + 8 个初始值；Lamport 的锚点是 32 个字节。
   写错的表现不是崩溃，而是"自洽地错"——内核自己的每一条判据都照样绿（实测就是这么红过一次：
   改了 `σ1` 的一个旋转量，内核五格全真、判定仍是 `PASS(33)`）。
2. **"验过了"不等于"会拒绝"**。签名验在一条用例里，与"未签名的东西不许进系统"是两件事。
   把前者当后者宣布，就是给商业化埋一句假话。

## 决定

1. **哈希自己实现，零依赖、零 `unsafe`，并配三道互相独立的仪器**：
   ①`check-sha-primitives` 按**定义**重算 K/IV（前 64 个素数的立方根、前 8 个的平方根的小数前 32 位）
   与源码逐字对账；②`hashlib` 对 13 条长度向量各算一遍（矩阵第 25 行）；③内核五格只管
   "自我能看见的塌陷"（互不相同/幂等/雪崩/端序/形状）。长度向量专门踩补位的四个边界
   （55|56、63|64、111|112、119|120），因为那一格的错只在边界上露。
   为什么不用现成 crate：§11.2 要求 TCB 内依赖双人评审 + vendoring，而这里需要的只是 100 行
   可以被三道仪器钉死的东西 —— **能被审计的重复实现，比不能被打量的依赖更合适**。
2. **签名选 Lamport 一次性签名（OTS），不选 Ed25519**。理由按成本排：OTS 只需要已经验过的哈希，
   验证就是 256 次"哈希一下再比"，没有曲线常数、没有模幂、没有可配置的错误路径；
   Ed25519 在本机意味着引入一个 TCB 内的密码 crate 或自己实现一份**无法用同样廉价的方式打量**的东西。
   代价写在"没做到的"里：**一次一签**，所以必须轮换，而轮换、密钥保管、吊销今天都没有实现，
   锚点是定下来的测试种子导出的。
3. **锚点内置的是"整张公钥的摘要"（32 字节），公钥与签名随包交付**。顺序是硬规定的：
   先核 `sha256(pk) == PK_ANCHOR`，再逐比特验原像，最后才用载荷。反过来的话，
   换一张公钥就等于换一把钥匙（"攻击者自带公钥"是最省事的错法）。
   锚点由 `tools/esp_image.py::pkg_anchor()` 按导出式子算出来再写进内核源码，
   `check-sig-anchor`（第 **12** 道门禁）每轮重算对账 —— 包括那张九条的篡改表。
4. **钥匙由种子按定义导出**：`priv[i] = SHA-256(seed || "aurora-lamport" || u32be(i))`，
   `pk[i] = SHA-256(priv[i])`。这样宿主机与内核**各自都能重算**同一张，验签不需要把私钥交给内核，
   也不需要把 16 KiB 的公钥抄进任何源码。
5. **畸形输入判据的形状：两份实现必须给同一个答案，而不是"内核拒了就行"**。
   九种篡改（公钥首/尾字节、签名首/中/尾字节、载荷首字节、载荷长度高字节、公钥长度字段、魔数）
   各自必须走到一个**不同的分支**：`AnchorMismatch` / `BitMismatch(i)` / `PayloadTooLong` /
   `BadLen` / `BadHeader`。第一版把长度字段翻在低字节，得到的是 `BitMismatch(0)` 而不是界检查
   ⇒ 那条分支其实没被测到。这是"负样本要指到它点名的那一格"在签名上的重演。
6. **包放在状态区之后的同一段 GPT 未分配空隙**（LBA 67_664 起 113 扇区），生成时先断言
   "这一段现在全是 0"再写。与 ADR-031 那条"带 GUID 的分区条目还没做"是同一笔账，
   现在多了一个消费者，所以那笔账更贵了而不是消失了。

## 后果

- 判定链：矩阵 24 → **26 行**（第 25 = SHA 摘要对账，第 26 = 签名包两份实现同答案），
  静态门禁 10 → **12 道**（`check-sha-primitives`、`check-sig-anchor`）。
- 新变体 `sig-check`（`KT_SHA256` + `KT_SIG_PACKAGE`），四把尺子的构建都不带它 —— 这一包的读取
  要 15 次块读、串口多 3.2 KB，进基线就是把量具的开销算进产品（规则 2）。
- 56.5 KiB（57,856 字节） 的包只能走静态缓冲：**"按外部输入大小分配内存"这条约束第三次以同一形状出现**
  （前两见 `ELF_SCRATCH` 与分配器上限 2048 字节那条账）。
- "盘上现在的字节 == 内核验过的那份字节"第一次成为可判的事（手工改掉镜像里公钥的一个 bit，
  门禁同时报"宿主机自己验不过"与"第 2 条答案不同"）。这是更新流程真正需要的那条性质。

## 没做到的

- **验签没有接到启动决策**：今天它在一条用例里跑。"未签名/验不过 ⇒ `BOOT-INVALID(37)` 不启动"
  要等 ADR-011 正式方案 + §9.5 的槽位身份（谁签发、密钥在哪、失败回到哪一槽）。
- **生产钥匙**：种子是定下来的测试值，"一次性"意味着签第二个包就要换钥匙，而**轮换、离线保管、
  吊销、多锚点**一条都没有。现在的锚点只能证明机制对，不能证明信任根存在。
- 载荷是包里的字节，不是"将要执行的那份文件"；把验签接到镜像本身需要装载器交出字节或 FAT 读取
  （M5 的 VFS/FAT32 还没做）。
- 没有 CRL/时间戳/算法协商字段；`PkgError` 的四种理由是硬编码的分支，没有版本演进策略。
- 度量启动与 TPM 在 M7；SBOM 与可复现构建是 M9 的另一列（本次未做）。
