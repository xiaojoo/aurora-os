# ADR-190：块设备传输互斥（RANK_BLOCK=37）

状态：**已采纳**（2026-11-22：XFER 锁落地，	_fat32 的 同数 5/5 全 true）

关联：ADR-189（fd_io 的 VfsFile 分派，它复用了 egin_read 的锁外磁盘 IO）

## 背景

kernel/src/driver/ahci.rs 的 OFF_DATA = 0x06000 到 256 KiB 是 **232 KiB 数据区，所有端口共用**。
传输流程是「往缓冲里填 → 发命令 → 等完成 → 从缓冲里读」，**这三步之间没有任何互斥**。

## 症状

	_fat32 23.5%（79/358，剔除注入跑后）失败，读数是：

    卷1 HELLO.ELF 走字节=17288 走簇=34 尾字节=392 哈希=0x1adad6baa8598e1f
    卷2 HELLO.ELF 走字节=17288 走簇=34 尾字节=392 哈希=0xb46b5bf89c811bba

**同样的长度、同样的簇数，只有内容不同** ⇒ 读的过程中缓冲被覆盖。

同族的还有 	_fat32_cursor_disks 15.1%、	_fat32_mem 10.0%、	_fs_open_syscalls 19.7%。

## 决策

新增 RANK_BLOCK = 37，	ransfer() 全程持锁。

**锁的粒度是「一次传输」而不是「一整个 walk」**：walk 逐簇读，每次 
ead_checked 各自拿锁。

### 为什么 rank 是 37

- 句柄层 RANK_HANDLE=35 在锁外做磁盘 IO ⇒ 调传输时不持 HANDLE ⇒ 37 比 35 深是对的
- 不能复用 RANK_NET=36（socket 表），合用会让「socket 里读盘」变成同等级重入
- 传输内部不取任何别的锁（纯 MMIO + 轮询）⇒ 37 是安全下界
- 全部调用点都在任务上下文（实测无 ISR 调用）⇒ IrqSpinLock 默认语义正确

## 读数

	_fat32 的 同数 **5 次跑全部 true**。

## 一个负样本失败（如实记）

注释掉 XFER.lock() 之后 	_fat32 **仍然全绿** —— 这一次负样本没能证明锁的作用
（偶发问题需要多次跑才能证）。**不把「修好了」建立在一次负样本上。**
真正支撑结论的是：5 次跑 同数 全 true，而修复前历史失败率 22%。

## 未决

1. OFF_DATA 按端口分区（更彻底，但要缩每端口容量或扩 RING_PAGES）
2. 	_fat32_cursor_disks / 	_fat32_mem / 	_fs_open_syscalls 未逐个验证
3. 块层仍无请求队列与完成通知（本 ADR 只解决互斥）
