# ADR-024: per-CPU 化到哪一层，以及"我是谁"值 600 周期

状态：已采纳（2026-11-05，M3b-2b 实测）
关联：手册 §5.2 §6.5 §7.1（R16/R23/R25）§12.4.1（P1/P3/P5/P6）§13.1、ADR-020、ADR-021、ADR-023、里程碑 M3b（收尾）

## 背景

M3b-1/2a 放了 AP，但故意留了两处"只有 BSP 在用"的东西：运行队列（`SC` 一份全局表 +
`current` 一格）和计时表（`P3/P5/P1` 由 asm 直接写全局格）。当时的说法是
"AP 的中断走不建帧的快路径，所以它进不到这些地方"。M3b 收尾就要把这两处兑现，
而兑现的方式有两种，代价不同：

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| A 加锁 | 全局表 + 一把 `RANK_SCHED` 锁，ISR 里取 | 调度路径要为锁等别的核；而 `context_load` **永不返回**，守卫不会走 `Drop` ⇒ 锁必须手动释放，忘一次就是永久持有 |
| B 分行 | 每 CPU 一条队列 / 一张表，谁的 CPU 谁写 | 没有锁，但每个"我是谁"的查询都必须在热路径上 |

选 B，并顺手把 asm 里的记账整段搬到 Rust：asm 里要按 CPU 索引就得先知道自己在哪个 CPU，
而那一刻可用的寄存器全属于被打断的任务。

## 一、运行队列：每 CPU 一条，任务不迁移

`RQ[cpu] = { tasks[6], current, entries[6] }`，全局任务下标 `gidx(cpu, slot)`。
三条同时成立才是安全的（写在 `QueueCell` 的 SAFETY 注释里）：

1. 每条队列只由它自己的 CPU 读写；
2. `spawn` 只往调用者所在 CPU 的队列里放任务；
3. **任务不迁移** —— `pick_next` 的过滤条件是 `state == Runnable && on_cpu == 本 CPU`。

第 3 条现在没有反例可以打破，所以 `KT_PERCPU_QUEUES` 除了数"AP 自己换过人"，
还钉住两条不变量：`cpu_of(current_of(c)) == c`（两个核抢同一个任务 = 同一个异常帧被
`iretq` 两次，现场是随机的 #GP/三重故障），以及 `on_cpu_of(i) == cpu_of(i)`
（`gidx/cpu_of/slot_of` 这对新算术写错的直接后果就是这条不一致）。

实测：`aps_with_sched=3 switched=3 worked=3 bad_owner=0 misfiled=0 nonempty=9`，
每 CPU 的切换数 `[27, 43, 43, 42]`。

顺带更正 M3a 写在 `sched` 模块头的那句理由——"ISR 里拿锁就是自死锁"。它只对了一半：
临界区一律 `save_and_cli`，IF=0 时本 CPU 的 tick **进不来**，所以"同一 CPU 的 ISR 抢同一把锁"
构造不出来；真正的危险是跨 CPU，而那条路上能依靠的只有有界自旋 + 看门狗。
选 B 不是因为 A 一定死锁，是因为 B 不需要论证锁序。

## 二、P3/P5/P1 离开 asm，边界随之移动

`isr_common` 的入口取时与出口记账整段删除，改在 `aurora_trap_entry` 里做。**新边界**：

- 下界 = `aurora_trap_entry` 里第一次 `rdtsc`（不含异常桩的 15 次 GPR + CR2 保存）；
- 上界 = 同一次调用的出口记账（不含寄存器恢复与 `iretq`）。

这条必须写进 §12.4.1，否则新旧数字会被拿去比大小。移动之后实测：
`p3 resume min` 从 2164 → **199**，`p5 irq min` 从 7302 → **3486**，
`p1 percpu cpu0 min` 从 2603 → **735**。P3 那条量具自检仍然"符合"
（注入 `bench-pf-load` 之后 min = 223,824，比 >1000 倍），说明移动没有把尺子弄废。

记账改在 Rust 里还有一处必要的连带修正：`p5_last_vec` 原来在 asm 出口写，而**被抢占的那次
不经过出口** ⇒ AP 上每个 tick 都换人，于是 AP 那一行的 `last_vec` 恒为 0。
读数点提到入口之后：`cpu1..3 last_vec=0xf1` ✔ 这正是"AP 的 tick 进了 P5 表"的直接证据。

## 三、一次 MMIO 读值 600 周期（四轮排除法）

改完之后 BSP 那行 P1 的 `min` 从 M3b-1 的 462~987 涨到 2603~2784。我先后给过四个解释，
**前三个被自己的数据否掉**，这个过程比结论值钱，所以整段留在 ADR 里：

| # | 假设 | 实验 | 结果 |
| --- | --- | --- | --- |
| 1 | 四个核的样本混进同一个 `min` | 把 P1 表按 CPU 分行后只看 BSP 自己那一行 | **否**：仍是 2603 |
| 2 | 三个 AP 在跑工人循环，抢了宿主的 CPU | 同一构建里不建 AP 工人（AP 切换数 0/0/0，已验证） | **否**：BSP 那行仍 2759 |
| 3 | per-CPU 数组挤在同一条缓存行里伪共享 | 把 `NEED_RESCHED/TICKS/SWITCHES_FOR` 拆成每 CPU 一条缓存行（64 字节 + 填充） | **部分**：2759 → 2536（≈8%），方向对但不是主因 |
| 4 | 被测区间里多读了三次 UC- 的 LAPIC 寄存器 | 把槽位从异常入口传下来，`preempt_point` 内不再自查 | **是**：2536 → **735**，四核 735/951/768/834 |

于是得到一条可以直接用的数：**一次 `cpu::self_slot()`（读一次 LAPIC ID）在本机 QEMU 上
约 `(2536 − 735) / 3 ≈ 600` 周期**。它的用处不只是解释一张表：

* §7.1 的"中断路径上禁止分配/打印"从此有了同类可比的数量级——UC- MMIO 在 QEMU 上比
  一次缓存里的原子操作贵两个数量级以上，所以"顺手读一下我是谁"这种看似免费的动作，
  在中断里每次几百周期。
* 结构上定了这条约定：**槽位在异常入口取一次，往下传**，不允许在被测区间内部再查。
  `trap::mark_entry / note_last_vec / record_sample / p3_record_irq` 与
  `sched::preempt_point` 都收 `cpu` 参数，就是这个约定的形状。
* 也解释了为什么 `sync::cpu_token()` 用 LAPIC id 当锁令牌是可接受的：取锁时 IF 已经是 0，
  一次持锁只读一次，而锁的持有时长本来就是千周期量级。

## 四、AP 的 tick 改走异常帧

`VEC_CPU_TIMER(0xF1)` 从不建帧的快路径改成 `isr_stub_241 → isr_common`。不建帧就没有
续跑格式，AP 就永远不可能换人（`sched` 模块头第 1 条）。当初用快路径回避的"AP 样本
混进 BSP 的 P5"现在由**分行的表**解决，不再靠"不记账"回避。
`isr_stub_shootdown(0xF2)` **保持**不建帧：它的请求方正持锁等回执，处理路径上任何取锁
都会变成跨 CPU 死锁，而它也不需要抢占点（ADR-023）。

AP 开 IF 的同时必须立 `CPU_IF` 那块牌（`apic::open_cpu_window`），否则 ADR-021 的机制会
在第一次换入时把 IF 清零，那条 CPU 从此收不到 tick —— 这是 M3b-1 留在 `smp` 模块头的
缺口，本轮补上，并且是**先立牌再 `sti`** 的同一套顺序。

## 五、一条被自己的判据抓到的东西：跨核读 `current` 是快照

`KT_PERCPU_QUEUES` 最初的判据里写了"每个跑调度的 CPU，它的 `current` 状态必须是 `Running`"。
跑第一次是绿的，第二次就红了：

```
[fatal] percpu sched: cpu1 的 current=6 归属=1 状态=Runnable
[FAIL]  t_percpu_queues -> failed
```

**这不是内核的 bug，是判据的 bug。** `preempt_point` 在那条 CPU 上按顺序做四件事：
把空闲上下文 `Running → Runnable`、存帧、`current = next`、把下一个标 `Running`。
BSP 从另一条 CPU 去读，正好能落在"降级已发生、`current` 还没换"这两步之间——
那是**一次合法换人的中间态**，不是不一致状态。归属（`cpu_of(current) == c`）是原子里看不出这种
中间态的那一半，所以它仍然是硬判据；状态那一半只在**自己读自己**时成立，于是改成：

* 跨核：只断言归属正确 + 不是 `Free`（快照能支持的强度）；
* BSP 自读：仍然硬要求 `Running`（没有别人会并发改它）。

顺手把这条记成一条通用的评审话：**多核之后，任何"读别人的 per-CPU 状态"的断言都必须先问
一句"这个读能观察到几步之间的中间态吗"**。同一份代码里 `apic::cpu_ticks()`、
`trap::p_stats_all()`、`sched::state_of()` 都是这类快照读，它们今天的用法全是观测，
没有一处拿它做决定——这一点是设计约束，不是巧合，别在后续改动里破坏它。

## 补充（R35）：GDT / IDT / TSS / 异常栈为什么**成套** per-CPU

`trap::TABLES[slot]` 一槽一套（GDT + IDT + TSS + 本 CPU 的 #DF 栈），对齐到 64 字节。理由分三层：

1. **TSS 必须 per-CPU**：`rsp0` 是"这个 CPU 上正在跑的用户任务的内核栈顶"，`IST1` 指向
   **本 CPU** 的 #DF 栈。共享一份就意味着 A 核的 ring3 陷入会换到 B 核的栈上——那是内存破坏，不是性能问题。
2. **GDT 被 TSS 拖着走**：GDT 第 4 项的内容就是本槽 TSS 的地址，所以 TSS 一 per-CPU，GDT 就必须 per-CPU。
3. **IDT 本来可以共享**（运行时只读），但还是放进同一套里：把 TSS 的选择子放进**共享** GDT，
   等于让"哪张表属于哪个 CPU"变成一条隐式约定——本 ADR 的全部主题就是这类约定要变成可核对的事实。
4. **对齐 64** 有两个用途：相邻 CPU 的表落在不同缓存行（AP 初始化不会和 BSP 的写互相拖慢），
   更重要的是**没有人能在不知情的情况下写到别人的 TSS 里**——写坏别人的 `rsp0` 的表现是
   另一台核上的 ring3 陷入换到不存在的栈，那是最难归因的一类现场。

写的前提也写死：每个 CPU 只写自己那一槽，且发生在该 CPU 的 **IF=0** 阶段
（BSP 在 `kmain` 早期，AP 在 `ap_main` 第一步）；之后只被硬件读。
`cpu::reserve_ap_slot` 先把槽位分好且 id 不重复——那条由 BSP 单线程完成，是本节论证的前提。

## 后果与仍未做的

* M3b 的验收行闭合：`tools/aurora.py test` 9 行全"符合"，37/37 用例绿，
  `bench` 四道门禁符合（P4 重复性离散度 4.62%）。
* P5 现在有多核读数（AP 三个核各 50+ 样本，min 6715~8582 周期），"多核中断延迟分布"
  从空白变成有数——但仍是**同一台 QEMU、同一批任务**，跨机可比性照 §12.4.1 规则 2 只认比值。
* P4 的重复性离散度从 0.85~1.24% 涨到 2.86~5.15%：多核之后启动路径上多了三个核的
  bringup（每个 AP 一次 2 ms 标定窗），这个涨法是预期的，但**容忍度阈值还没重设**（BACKLOG）。
* 仍未做：任务迁移（要同步）、per-地址空间的 cpumask（M4 的用户地址空间一起做）、
  `schedule()` 主动让出（`loads_closed` 那条路径的触发源）、QEMU 观测不到的 TLB 陈旧性
  （ADR-023）、真机（M7）。
