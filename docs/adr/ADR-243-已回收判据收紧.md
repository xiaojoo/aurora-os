# ADR-243：收紧「已回收」的判据（Free 不等于资源已交回）—— 部分改善，未根治

状态：**已采纳，但只算部分修复**（2026-11-23）。判据更正已落地并实测有效，
但 `t_q2_workload_slots` 的偶发**没有消除**，如实记在「未决」。

关联：ADR-047 决策 2（持 RUNQ 不许 drop Mapping）、ADR-232/234（reap 观测）、
BACKLOG §562/§563/§564、§565（本轮记账）。

> 写作纪律：已采纳 ADR 与有测试证据的事实优先。每条结论标「实测」或「推断」。
> **本轮没修好，就不写修好了。**

## 背景：一个被三处复制粘贴的错前提

`kernel/src/ktests/common.rs` 的 `drained_or_free` 里写着：

> 槽已 Free 是充分证据：`reap` 是**先释放资源、再标 Free** 的，所以 Free 蕴含释放已发生。

**这条前提只对 `reap` 成立。** `terminate_task` 的顺序是反的（实测，`mod.rs`）：

    s.tasks[slot].state = TaskState::Free;   // ← 拿 RUNQ 时就标了（第 376 行）
    ...
    if on_cpu_now { REAP_PENDING[cpu].fetch_add(1) }   // ← 只是登记
    else { release_owned(cpu, slot) }                  // ← 放锁之后才真释放

而 `release_owned` 自己也是两段式（这是 ADR-047 决策 2 要求的，不是缺陷）：

    let n = core::mem::take(&mut s.tasks[slot].owned.n);   // 锁内：袋子搬走
    drop(bag);                                             // 锁外：真正的解映射/还帧

所以存在一个窗口：**槽是 Free、袋里还牵着映射**。`mod.rs` 的 `owned_of` 注释
（第 1308 行）早就写过这句话——「槽位是 Free 不等于资源回去了」——但**测试侧的三处
等价判据没跟着改**。

### 后果不是「等得久一点」，是**漏掉释放**

判据一返回 true，调用方就不再进 `drain_reap` 那个窗口。**而没有 tick 就没有抢占点，
没有抢占点 `REAP_PENDING` 就永远不消费** ⇒ 袋里的映射（内核栈 4 页 + 1 条 VA 保留）
再也没人放手。实测 `t_q2_workload_slots` 失败签名恒为：

    q2: 回滚不成立 f97424->97420(差 -4) va21->22(差 1) 收尸=4 回滚=0

## 决策

三处「Free 即已回收」的等价判据，全部收紧成「Free **且** 本任务袋子已空」：

| 文件 | 位置 | 改法 |
|---|---|---|
| `ktests/common.rs` | `drained_or_free` | `Free` → `Free && owned_of(g)==0`；`drain_reap()` → `drain_reap_for(g)` |
| `ktests/sched/sched.rs` | `t_q2_workload_slots` 的 `all_free` | 同上 |
| `ktests/memory/mm.rs` | `t_object_wait` 的 `drained` | 同上 |

新增 `drain_reap_for(g)`：等的**不是**全局 `reap_released` 涨（别的 CPU 上任何一次回收
都会让它涨，与本任务无关），而是**本任务自己的** `owned_of(g) == 0`。

**为什么不是「放宽」而是「收紧」**：原判据在「Free 但袋还满」时返回 true 是**假绿**；
新判据要求袋子真空，那才是释放已发生的直接证据。

## 实测读数（同一 ELF、同机、连续跑）

| 项 | 修前 | 修后 |
|---|---|---|
| `t_q2_workload_slots` 偶发率 | **8/14 红**（按 run 日志回溯统计）| **2/12 红** |
| 失败签名 | 恒 `差 -4 / va+1` | **不变**（同样的 -4/+1）|
| `check` | 21/21 | **21/21** |
| 默认档 build | rc=0 | rc=0 |

**但随后一轮 10 跑是 4/10 红**，与修前 8/14 在统计上**分不开**。
所以准确的说法是：**判据更正了，偶发没有消除**。两个批次的差异不足以声称改善。

## 备选方案（试过并**回退**的）

**用 `kstack_lo == 0` 当判据**：`release_owned` 在 `drop(bag)` **之后**才清零 `kstack_lo`，
理论上它比 `owned_of` 更接近「真的放完了」。实测**更差**（8 跑 5 红），已回退。
原因未查清——记在这里免得下一个人重走。

## 未决（这是本 ADR 最重要的部分）

1. **偶发未根治**。逐条诊断显示 q2 的 7 条线程**全部** `state=Free owned=0`，
   所以漏的那条**不是** q2 自己的线程。
2. **扫描全部槽位**只找到三个恒定的 `owned=1`：`g=257/513/769`，即 **CPU 1/2/3 的
   slot 1**，也就是各 AP 的**常驻工人**（`spawn_resident`，按设计不退出）。
   它们的栈是**合法常驻**，不是泄漏。
3. **3 页 VA 保留 `0x100002000` 长期不还**：`va: 保留 0x100002000(+12288B) 第 2 页
   仍已映射，不放手` 从 **2026-11-11 的 `run-002.log` 起就一直在打**（最近 60 跑 58 跑有）。
   这是**远早于本轮的既有缺陷**，与 q2 的 `va+1` 是否同源**未验证**。
4. **`t_syscall_abi_arms` 之后固定 HANG**：最近 30 跑里 11 跑在
   `t_syscall_abi_arms -> ok` 之后无输出（下一格是 `t_handle_proc_owner`）。
   同样从 2026-11-21 起就存在，**不是本轮引入**。
5. **未做**：没有在 HEAD 上跑对照整链（要先把 ADR-242 的三处编译破损打回去，整链跑不了）；
   所以「不是本轮引入」靠的是**逐条日志指纹比对**，不是两次整链对比。

## 迁移与回滚

纯测试侧改动（三个文件，无产品代码）。回滚 = 恢复那三处 `Free` 等价判据。
**回滚会让判据重新变假绿**，不建议。

## 给下一个人的话

这个 ADR **没有修好 q2**。它修好的是**一个真实存在的判据缺陷**（Free ≠ 已回收），
并把三处复制粘贴的错前提纠正了。真正的泄漏源仍未知，下一步应该：

1. 在 `Mapping::drop` 里按 **VA 范围**记录「谁 drop 了什么」（ADR-227 的 `unmap-trace`
   已有雏形，但会改变时序——要用原子计数，别写串口）。
2. 或者从 `0x100002000` 那条保留入手：它是**唯一**稳定的、跨 12 天都在的异常，
   而且**已经有人替你把最早出现的时间点定位到 `run-002.log`**。
