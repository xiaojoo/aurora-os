# ADR-214：块层请求队列

状态：**已采纳**（2026-11-23：`t_block_queue` 八格全 true）

关联：ADR-194（请求合并，当时只做了合并、**队列本身没做**）、ADR-110（块请求层）

> 补的是 ADR-194 记下的欠账：**「队列本身还没做」**。

## 交付

```rust
pub const QUEUE_MAX: usize = 32;
pub struct Request { lba, sectors, token, seq }
pub struct DrainReport { issued, merged, sectors_ok, failed_at }
pub fn submit(lba, sectors, token) -> bool
pub fn drain(disk, budget) -> DrainReport
pub fn pending() -> usize
pub fn queue_stats() -> (u32, u32, u32)
```

## 决策 1：入队与执行分开

与 ADR-201 的定时器同一条纪律：

- `submit` 要能在任何上下文（包括中断）里做 —— 只写队列，不碰设备；
- `drain` 要碰设备 —— 只在安全上下文调。

## 决策 2：**插入排序**而不是快排

`QUEUE_MAX = 32`，插入排序的最坏 512 次比较可忽略，而它**稳定** ——
同 LBA 的请求保持提交序，判据才能预期输出。

## 决策 3：排序是「电梯算法的静态形态」

把「按提交顺序下发」换成「按盘上位置下发」：

- 对真盘：减少寻道；
- 对 AHCI：减少命令切换；
- 对判据：**顺序可预期**（这是能被证伪的前提）。

## 决策 4：合并规则与 token 的简化

「前一条的末尾 == 后一条的开头」就合并。

**合并后 `token` 取前一条的** —— 一条合并请求只回调一次。
这是有意的简化，已写进未决 1。

## 判据八格（`t_block_queue`）

```
queue: 入队=true 空拒=true 满拒=true 排序=true 合并=true 数据=true
       首失败停=true 清空=true ｜ issued=2 merged=2 ⇒ true
```

提交顺序 `30(2), 10(2), 14(2), 12(2)`：

1. 排序后 `10(2), 12(2), 14(2), 30(2)`；
2. 合并后 `10..16(6), 30..32(2)` ⇒ `issued=2 merged=2`。

## 负样本（变异证红）

把排序循环改成 `for i in 1..0`（不排序）：

```
queue: ... 排序=false 合并=false ... ｜ issued=4 merged=0 ⇒ false
```

**`merged=0` 说明合依赖排序** —— 不排序就无法发现相邻关系。
这条负样本同时证明了两件事，比单独破坏合并更有价值。

## 未决

1. **合并后 token 只有一个** —— 多个提交者共享一条合并请求时，只有第一个拿到回调
2. **队列是全局的，不按盘分** —— 多盘并发时会把不同盘的请求排在一起（顺序仍对，但电梯失效）
3. **`drain` 仍是同步的** —— 没有「提交后立即返回、完成时通知」的异步路径
4. **没有完成回调** —— `DrainReport` 是汇总，不是逐条回调
5. **电梯只做了静态排序** —— 没有「执行中途插入新请求并重排」
