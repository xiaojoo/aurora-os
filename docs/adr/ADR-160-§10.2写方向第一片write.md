# ADR-160：§10.2 写方向第一片——`write` 与 23 号的用户态出口（零新号）

状态：采纳（2026-11-19，证据来源 / 总设计 §10.2 写方向 / **零新号**）
关联：ADR-111（`write_at` 覆盖写）、ADR-160 前置的 ADR-156（只读四命令）、
`kernel/src/filesystem/vfs_ro.rs::write_at`、总设计 §10.2

> 写作纪律：已采纳 ADR 与有测试证据的事实优先于本文的目标设计；发现冲突先记差异，
> 不要为了让文档一致去改已经验证的结论。每条结论标「实测」或「推断」。

## 背景：写路径其实早就有了

审计（`docs/Aurora-OS-未完成步骤审计-2026-11-19.md`）把"FAT32 写路径"列为第 2 项，
当时判断是"要从零做簇分配/目录项/FAT 更新"。**勘察后发现这个判断不准确**：

| 层 | 状态 |
|---|---|
| `vfs_ro::write_at` | **已实现**（ADR-111 决策 1）：覆盖写已有区间，非整扇区读-改-写 |
| `fs_open::OPEN_WRITE` | **已实现**：写意图 flag + 挂载可写性闸 |
| 23 号 `SYS_FILE_WRITE` | **已实现**：`handle::begin_write` → `write_chunk` → `write_at` |
| 内核 ktest | **已覆盖**：`t_fs_rw_write`、`t_fs_rw_syscall23`、`t_fs_rw_open_write` |
| **用户态封装** | **缺** |
| **用户态命令** | **缺** |

所以本片的真实内容不是"造写路径"，而是**把已有的写路径接到用户态**。

## 决策

### 决策 1：`write` 只覆盖已有区间，**不能创建/扩展**

23 号的 `write_at` 越 EOF 时**整次拒绝**（`BadOffset`），一个字节都不写。
所以 `write <path> <text>` 的语义是"把文件**前 N 字节**改成 text"，
不是"写一个新文件"。

**这个边界必须写清**：`touch`/`mkdir`/`rm`/`cp`/`mv` 需要**创建/删除**，
那要簇分配、改两份 FAT、改 FSInfo、改目录项大小——**仍是未做的一刀**。
本片不解锁那 5 条命令，只解锁"写已有文件"。

### 决策 2：权限闸用 `CAP_WRITE` 不是 `CAP_READ`

写比读更高。`cmd_write` 开头 `allow(c, rt::CAP_WRITE)`。

### 决策 3：判据接受**三种**明确回答

`write /LOG.TXT abc` 之后必须是三者之一：

- `write: ok bytes=<n>` —— 真写进去了；
- `write: read-only vol` —— 该档根卷不可写（**明确说不能写**，不是静默成功）；
- `write: err=<n>` —— 内核拒绝（带错误码）。

**三者都算过**：本片证明的是"23 号有了用户态出口，且它给出明确回答"，
不是"这条命令在所有档都能写"。

## 验收与负样本

**实测**（`a3-shell,fat32-probe` 档，PASS(33) 16.0s）：

```
write /LOG.TXT abc
write: read-only vol
```

判定格 `_write_row`：三种明确回答之一（见决策 3）。
**变异证红**：`write_run` 在 `Err` 分支静默 `return`（不打任何消息）⇒
`_write_row=False`；还原 ⇒ True（实测）。

`check` 18/18（unsafe 523/U5 128）。

## 落地时撞到的两件事

1. **`a3-shell,fs-rw` 不是受支持的档**：我为测试临时用了它，得到
   `ktests: 107 passed 105 failed 2`（`t_fs_open_ring3` + `t_clock_uptime`）。
   单独 `fs-rw` 档是 **107/107 全绿**。**判定表只跑 `["fs-rw"]`**——
   组合档不在表里，它的红不能当作本片的红，也不能当作本片的绿。
   这条要记住：**"我临时拼的档"与"受支持的档"是两件事**。

2. **可写卷在产品路径上不可达**：`fs-rw` 档的可写卷挂在**口 4**，
   而根卷（`/`）是只读的。所以 `write` 在 `a3-shell` 档只能打 `read-only vol`。
   **写能力在内核 ktest 里通了，但用户态拿不到可写挂载**——这是本片最该记的欠账。

## 影响

正面：23 号第一次有用户态出口；`write` 有判据与变异证红；
**纠正了审计里"FAT32 写路径要从零做"的判断**——写路径早就有，缺的是接线。

负面（**必须诚实列出**）：
1. **`touch`/`mkdir`/`rmdir`/`rm`/`cp`/`mv` 仍未做**（需要创建/删除，是另一刀）。
2. **用户态拿不到可写挂载**：`/` 恒只读，口 4 的可写卷没进挂载表。
   ⇒ `write` 在产品档只能打 `read-only vol`，**"真写进去"未被用户态端到端证明**。
3. **不能扩展/截断**：`write` 只覆盖前 N 字节，文件尾保留原内容。
4. **没有 `>` 重定向**（那是 A3 的另一片）。

## 迁移与回滚

零新号。回滚 = 删 `runtime::file_write`/`OPEN_WRITE`/`SYS_FILE_WRITE`、
`cmd_write`/`write_run`、MSGS 四段常量、`_write_row` 格、argv 里的那一条。

## 未决

1. **可写挂载进产品路径**：需要挂载表支持"口 4 挂到 `/mnt`"之类的第二挂载点，
   或者让 `set_port` 指向可写卷。这是解锁"用户态真写"的前置。
2. **创建/删除**：簇分配 + 目录项写入 + FAT 两份更新 + FSInfo。
3. **扩展/截断**：同上，加上目录项 size 字段。
4. **`>` 重定向**：与管道共用 sink 机制，方向相反（写文件）。
