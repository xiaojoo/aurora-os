# ADR-032: 网卡的第一帧由宿主机抓包判，M8 的验收句不提前宣布

状态：已采纳（2026-11-06，M8-a① TX + M8-a② RX 与第一条协议往返，见文末补记；fuzz 与审计仍未做）
关联：手册 §8.6（驱动优先级：virtio-net 与 virtio-blk 同列 P1）§12.3/§12.3.1（门禁与注入清单）
§14（M8 那一行）ADR-029/030/031（"寄存器表由设备作证"、`DriverCtx` 唯一接口、两台仪器对账的形状）、BACKLOG 58

## 背景

M8 那一行写的是"网络栈、审计、漏洞响应演练"，验收句是**协议 fuzz 无高危缺陷**。
这一句在今天的代码量上不可达：既没有协议栈可以 fuzz，也没有做 fuzz 的脚手架。
如果按里程碑顺序宣布"M8 完成"，就是把一句没有量具的话写进台账（§12.4.1 规则 3 的反面）。

网络这一半还有一件与存储同形的事：驱动自己说"我发出去了"是**内核进程里的一句话**。
`KT_NET_TX` 能把队列、回执、缓冲完整性八格全跑绿，却仍然回答不了
"线上有没有那些字节、是不是那些字节"——那句话只有核外的仪器能说。
M5-c③（`qemu-io` 读盘）与 M6-b②（宿主机重解记录）已经是同一个形状，网络只是换了台仪器。

## 决定

1. **M8 按"能不能判"切两半，先做能判的那一半并如实登记另一半没做**。
   已交付：virtio-net 的 TX 路径 + 矩阵第 23 行（宿主机读 QEMU `filter-dump` 写下的 pcap，
   逐帧三处对账）。未交付：RX、协议栈、fuzz、审计日志、漏洞响应演练。
   §14 那一行的验收句**保持不勾**，写的是"这一半成立、那一半没做"，不是"M8 完成"。
2. **第二台仪器 = QEMU 自己的抓包器，判据按"只属于我们的那一格"分内外**。
   `filter-dump` 是双向的：实测抓包文件里除了我们那两帧，还有一条开机更早的 IPv6 组播离开报文，
   **源 MAC 与我们的完全相同**（slirp 代表这块网卡发的）。所以两种看着都合理的分法都错：
   "包数 == 帧数"（第一版就是这么红的）、"按源 MAC 分"（会把那条误认成我们的）。
   能分开的只有 ethertype `0x88B5`（IEEE 802 本地实验号）——它不冒认任何协议，也没有别人会用。
   于是判据是双向都咬得住的：少一帧 = 有一帧其实没上线，多一包 = 有一包不是用例发的。
3. **不新增驱动文件，复用 M5-f② 那条 split queue**：`handshake`/`setup_vq`/`put_desc` 三段
   由块设备与网卡共用，`DRIVER_MODULES` 不加条目 ⇒ 第 4 道门禁 `check-driver-ctx` 继续管着新代码。
   抽出来不是为了整洁：同一张寄存器表抄第二遍的人就是我，而抄错的那一遍在内核里读不出区别。
   设备选择从"配置空间里第一台 vendor 0x1AF4"改成 **按 PCI class 找**（0x01 存储 / 0x02 网络）——
   多挂一张网卡之后，前者会变成由命令行顺序决定的一件事。
4. **"我是网卡"不拿 PCI device id 当依据**。实测 QEMU 11.1.0 给 `virtio-net-pci` 的是 `0x1000`，
   而规范式子 `0x1000 + 类型` 算出来是 `0x1001`（transitional 网卡沿用 virtio 0.9.5 的老编号表）。
   改成 `num_queues >= 2` 加"RX 与 TX 的 `queue_notify_off` 不同"（实测 `队列数=3 门位rx/tx=0/1`）。
   `dev_type()` 保留但**只打印**：解不出来不等于不是网卡，解出来了也不等于就是。
5. **字段不存在与字段等于 0xFF 是两件事，判据必须能分辨**。一个特性都不接受 ⇒ 设备按 legacy
   形状只给 8 字节配置（`mac[6] + status`），第 8..15 字节读回全 `0xFF`。
   我第一版的第二条"宽度证人"比的是 `0xFFFFFFFF == 0xFFFF | (0xFFFF<<16)` ⇒ **假绿**：
   它在比同一串填充字节。这一格从此是 `Option<bool>`，字段不存在时取 `None` 并照样打印
   （与 M5-f② 那条"地址回读"三值形状同一条规矩：**没测到不许写成测到了**）。
6. **头长与"不接受 `VIRTIO_F_VERSION_1`"是耦合的，改一处必须重跑第 23 行**。
   今天按 legacy 剥头 ⇒ `NET_HDR_BYTES = 10`。一协商版本 1 就要带 `num_buffers` 改成 12，
   而这一改动不会让任何内核内判据变红（它只改线上那几字节）。所以耦合写在代码注释、这里
   与 BACKLOG 58 三处，量具是 pcap 的逐字节比对。

## 后果

- 判定链从 22 行到 **23 行**，静态门禁从 9 道到 **10 道**（`check-net-pattern`：帧的形状
  五个常量 + ethertype + 目的地址写法，两边各一份必须机器对账）。
- 新增构建变体 `virtio-net`：QEMU 命令行加 `-netdev user,…` + `-device virtio-net-pci` +
  `-object filter-dump,…`。抓包文件每次先删后写（上一跑的包会冒充这一跑的证据，
  同一类故障在 scratch 夹具上已经栽过一次）。
- 这条仪器还额外给出一条 M8-a② 的入口事实：**RX 队列没使能时主机侧已经在推包**，
  所以收方向不是"造一个对端"，而是"接住已经在来的东西"。
- `mac=` 给宿主机的值**不是**内核的期望值：内核读的是设备配置空间里那一份，
  两者相同是"我读对了偏移"的证据，而不是判据的输入。

## 没做到的

RX（队列 0 只读了门位）、控制队列、协商任何特性（MTU/多队列/校验和卸载因此都不存在）、
把帧交给上层协议（今天没有协议栈，那一帧是本地实验 ethertype）、中断认领（仍全轮询）、
§9.6 那条 fuzz、审计日志、漏洞响应演练。**"协议 fuzz 无高危缺陷"这句验收没有成立，
也没有被任何一条已交付判据暗示它成立。**

## M8-a② 补记：对端换成 QEMU 自带的 DHCP 服务器（2026-11-06，BACKLOG 59）

上面"RX（队列 0 只读了门位）"那一格已经作废：RX 队列真的建起来了，而且这一行不再靠图案自证——
对端是 `-netdev user` 里 **QEMU 自带的 BOOTP/DHCP 服务器**，内核发一份 DISCOVER、收一份回话。
三条决定在这一节里补：

1. **对端要挑"会答话的那一个"**。实测用户网络**不答 ARP**（42 字节的请求确实上了线，pcap 里零回话），
   但**答 BOOTP DISCOVER**（回一条 590 字节的 OFFER/ACK）。所以触发器是 DHCP，ARP 那条探针从代码里删掉，
   只留这条结论。判据不接受"多跑几遍撞一次"的现场——同一条规矩见 M6-a③ 的 `force_boot_state`。
2. **协议常数也要设备作证**。`magic cookie` 我凭记忆写成 `99,130,131,15`，而 slirp **不校验入站 cookie**
   ⇒ 请求照样被答，内核里没有任何一格能抓到它。把它纠正的是对端写回来的那四个字节
   （`0x63825363` = 99,130,83,99）。于是"寄存器表要设备自己作证"这条经验扩到协议字段：
   **凡是对端不校验的常数，判据只能建立在逐字节对账上**。
3. **回话由两条独立实现各解一遍**。内核 `parse_reply` 与宿主机 `bootp_of` 从同一串字节各自解出
   `op/xid/msg/yiaddr`，四个数逐一相同才算过；再叠一层"答案在核外"：`yiaddr` 必须等于
   `dhcpstart=10.0.2.15`（内核猜不到这个数），以及回话里的 `chaddr` 必须等于这块网卡的 MAC
   （它答的是我，不是别人）。DISCOVER 也反向重算一遍，所以**内核构造 IPv4/UDP/BOOTP 的那 290 个字节
   由宿主机逐字节核对**——第一次比就抓出错的是宿主机那份（IP 总长度只数了首部 20 字节）。

仍然没做：`REQUEST`/`ACK` 的完整四次握手（今天一次请求一次应答，拿到的地址不落到任何地方）、
把帧交给上层协议（解出来的四个数就是终点）、多缓冲接收（只挂一个接收缓冲）、
RX 中断认领（仍轮询 `used.idx`）、控制队列、协商特性、fuzz、审计日志、漏洞响应演练。
**M8 的验收句仍然不成立。**
