# ADR-204：下半部的真实消费者（idle 里的 drain）

状态：**已采纳**（2026-11-22：`t_idle_drain` 六格全 true）

关联：ADR-201（定时器）、ADR-202（下半部）、ADR-203（TCP 重传）

> ADR-201/202/203 三层都立住了，但**没有线程真的在 `drain`** —— 判据在手动取。
> 这一层把它接进 `idle_entry`。

## 为什么放在 `idle_entry`

需要「一个在安全上下文里、能反复跑、不占调度配额」的地方。`idle_entry` 正是：
它只在没有别的可运行任务时被选中，而且循环里本来就有「转一圈再查」的节奏
（`task_wake_tick` 那段注释记的就是这个形状）。

## 三条纪律（都来自 `idle_entry` 现有的注释）

1. **有界**：一次最多处理 `MAX_BOTTOM`(32) 条，不无限循环 —— 否则 idle 会饿死调度。
2. **不阻塞**：不等待、不睡眠、不取可能被别人长期持有的锁。
3. **不分配**：故障路径不分配（AGENTS.md 硬约束 6），这里连正常路径也不分配。

接法：

```rust
if drain_bottom() > 0 {
    BOTTOM_HANDLED.fetch_add(1, Ordering::Relaxed);
    continue;   // 有活干就不 hlt
}
```

## 决策 1：四个 `mac_of` 注入点（本仓库第四次用这个模式）

重传发段要查 ARP 表，而查表在 `sched/user.rs` 里 —— `network` 不能依赖 `sched`。

```rust
pub fn install_mac_of(f: fn([u8; 4]) -> Option<[u8; 6]>)
```

与 `install_proc_of` / `install_as_of_task` / `install_wait_ops` 同一个模式。

**这是第四次** —— 说明「内核层之间要互相看见但不想造环」在本仓库是常态，
而不是例外。

## 决策 2：`drain_bottom` 不直接发帧

`drain_bottom` 在 `sched` 层，它不该知道怎么装 TCP 帧。

所以分三层：

```
drain_bottom（sched）           ← 取队列
  → dispatch_timer（network）    ← 分派
     → tcp_handle_timer          ← 状态机
     → tcp_retransmit_send       ← 装帧 + 发
```

## 判据六格（`t_idle_drain`）

```
idle: drain=true 空队列=true 跳过未知=true 注入点=true 未装拒=true 分派到fired=true ⇒ true
```

## 负样本（变异证红）

把 `dispatch_timer` 里的 `RETX_FIRED` 去掉：

```
idle: ... 分派到fired=false ⇒ false
```

## 一个必须说清的缺口：重传发的是**空载荷**

`tcp_retransmit_send` 现在发的是「正确的头部 + **零载荷**」。

**原因**：`RetxState` 只记了长度、没存内容。存内容要每连接一份缓冲，
那是 `MAX_SOCKETS × 1460 = 374 KiB`，**不可接受**（AGENTS.md「栈数组不许跟容量走」的同一类问题）。

**所以：这个函数证明了接线通了，但没证明数据能重传。**

对端会看到「序号对了但数据没了」—— 那是最坏的一种故障（静默的数据丢失）。

**这是本 ADR 最重要的诚实记录。** 已写进未决 1，且是下一步必须做的。

## 未决

1. **重传发空载荷**（见上节）—— 这是最严重的
2. **`dispatch_timer` 只认 `TcpRetransmit`**（USB/块层的定时器还没消费）
3. **判据不覆盖「idle 真的在 drain」** —— 判据直接调 `drain_bottom`，
   而「idle 里那行会不会被执行」靠 `PASS(33)` 兜底
4. **没有「有活干时唤醒 idle」的机制** —— 现在靠 idle 自己转圈（`hlt` 前会查一次），
   如果 idle 正在 `hlt` 里，要等下一次中断才醒
