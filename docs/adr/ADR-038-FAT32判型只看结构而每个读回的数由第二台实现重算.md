# ADR-038：FAT32 的判型只看结构，而读回的每一个数必须有第二台实现从字节重算

状态：已采纳（L3-C①②，2026-11-07，手册 §8.4「文件系统」那一格，BACKLOG 78，判定表第 34/35 行；
L3-C③ 由 BACKLOG 79 续在同一个决定下，判定表第 36/37 行）；
与 ADR-029（AHCI 以现场读数为准）、ADR-032（网卡第一帧由宿主机抓包判）同一族

## 背景

块设备那一族到今天为止的判据都停在"**字节搬到了**"：PRD 编程对不对、LBA 写错高位读不读得到、
跨 255 扇区那一次能不能读全——全部由哈希与回读判。第一次有了"把这些字节当**结构**读"的一层
（引导扇区、FAT、目录项），而这一层的坏法与上一层不同：

1. **偏移表可以错得很合理**。第一版把 `BPB_BkBootSec` 写成 49（规范是 50），读回来是 **1536**
   ——一个由字节 49..50 拼出来的、看着完全像扇区号的数。同一次对表还确认 FSInfo 的结构签名在
   **484** 而不是 488：488 那一格是自由簇数（卷A 读出 64,430 = 64,496 − 66 已用，自洽）。
   写错 4 个字节会把"自由簇数"读成"结构签名"，而它俩都是 32 位、都不为 0，
   任何"非 0 即通过"的检查都拦不住。
2. **判型的权威说法是错的**。微软 FAT 规范给的是一条经验阈值（簇数 < 4085 是 FAT12、
   < 65525 是 FAT16、再多是 FAT32），而真实卷不遵守它。本机两块卷（都由 `mtools 4.0.49` 的
   `mformat -F` 造出，数值取自 `minfo` 与镜像字节）里就有一块反例：

   | 卷 | 簇数 | 按阈值 | 按结构 | 后果 |
   |---|---|---|---|---|
   | `fat32-small`（口 3，32 MiB） | 64,496 | **FAT16** | FAT32 | 阈值会拒绝一块**读得动**的卷 |
   | `fat32-wide`（口 4，64 MiB） | 129,022 | FAT32 | FAT32 | 两者一致，不提供信息 |

   只知道阈值的人会把第一块当 FAT16 拒掉，而它每个扇区都按 FAT32 的结构读得通。

## 决策

1. **判型只看结构，阈值只用来报数**。收下 FAT32 的唯一一道闸是
   `root_entries == 0 && sectors_per_fat16 == 0 && sectors_per_fat32 != 0`；
   `band_type(簇数)` 不参与任何判定，它存在的唯一理由是**把阈值的答案打印出来**。
   并且判据里明确要求"卷A 的阈值判型是 FAT16 而我们收下了"（`a_counter`）：
   夹具哪天换成一簇数真落在 FAT32 档的卷，这一格当场红，而不是悄悄变成一条空转的断言。
   ——反例必须留在串口上，否则它只是一个我正在相信的说法。
2. **每一个读回的数由宿主机第二台实现重算**。`tools/aurora.py` 的 `fat32_host_volume`
   按同一份规范偏移从镜像字节自己解析一遍：几何 14 格、每个文件 12 格（目录项 4 格 +
   走链 4 格 + 内容 2 格 + 两半簇号）、FSInfo 的自由簇、以及引导盘该崩在哪一道闸。
   这张表是**重写**的，不是从内核 import 的——共用一张偏移表就退化成一台仪器。
   内核 `fat32: 判据` 那十三个 bool 比的是"自己 vs 写死的期望数"，那种一致发现不了
   "两边错得一样"（本轮就撞上一次：见"证红"第 1 条，十三格里有六格同时因同一个掩码而红，
   而如果没有宿主机那台仪器，我会以为是六件独立的事）。
3. **合成卷只用来做贵到没法在真卷上跑的分支覆盖**，而它的可信度由真卷担保：
   同一个 `parse_boot_sector` 必须也把 mtools 造的两块真卷读成同样的形状。
   这块 11,264 字节的卷不进仓库（`.gitignore` 的 `*.img`），由 `tools/make_fat32_mem.py`
   现算，指纹登记在 `aurora.py`；配方与用例里那批写死的数分家时红在**编译之前**。
4. **走链必须有界**，两台实现各自的界必须是同一个数：内核 `MAX_CLUSTERS_WALKED = 65_535`，
   宿主机 `FAT_MAX_WALKED` 由门禁 `check-fat32-ports` 与它逐字对账。
   没有界的时候，损坏镜像的表现不是 panic 也不是报错，而是**内核里一次永不返回的循环**——
   L4 之外没人认领的第三种死法。宿主机那一侧同样吃过一次：它跟着走卷B 那个
   34,603,008 字节的 `FILLER.BIN`（没有任何判据读它）时，对账本身先挂死。
5. **尾格只喂真的属于文件的那几个字节**这件事由注入变体 `fault-fat32-tail` 撑着：
   多喂的那个字节是**文件之后的盘上内容**，而簇数、EOC、大小每一格都还好看
   （实测：`走字节=31321 尾字节=89`，目录对=true、链对=false，哈希从 `0xa4cd9301…`
   变成 `0x24522bf0…`）。没有这条注入，那句话就是修辞。
6. **今天不交付的按不交付写**：LFN（长名条目只**计数**，判据要求 `lfn_entries == 0`，
   等于要求这条判据跑在真被实现的那条路上）、子目录、写路径、分区偏移（引导盘的 LBA0 是
   保护性 MBR，必须被拒——实测它崩在第一道"每扇区字节数"闸而不是签名闸，因为 MBR 的
   0x55AA 也在位上）、通用 VFS 门面（inode/dentry）、virtio-blk 的 `Block` 实现
   （`virtio.rs` 的 `DEV` 是单设备静态，挂第二台要改成按 BDF 的表，会动到已绿的 22/33 行）。
   这些都记在 BACKLOG 78 的欠账里，不在代码里留"以后再补"的空壳。
7. **容器的来源换成盘，判据同时换成三台仪器**（L3-C③，BACKLOG 79）：整份字节 sha256
   （宿主机按 FAT 结构从卷里取的那份 vs `kernel/fixtures/hello.elf` 那份 rustc 产物）、
   ELF64 头与 PT_LOAD 表（宿主机第三份实现 vs 串口那三行段读数）、以及**同一跑里**内嵌那条路径
   `elfload:` 的读数与 `elfdisk: 跑后` 逐字段配对——"换了来源不换行为"由两行日志说，不由用例的
   八个 bool 说。配套新增两格是"输入来自元数据"之后才存在的：`size` 说大 4096 必须撞走链的界、
   截到 `max(offset+filesz) − 1` 必须撞加载器的界。**界由段表自己给**：这份容器的尾部有 14,936 个字节
   （`.symtab/.strtab`）没有任何 PT_LOAD 覆盖，"随便少几个字节"那种截短谁也发现不了。
8. **写区间不许依赖"解析器自己承诺不超过元数据"那句话**（③ 的证红逼出来的，判定表第 37 行）：
   ③ 把走链喂出的字节拷进静态缓冲时，第一版直接按 `已喂 + 本段长` 索引写，理由写的是
   "`walk` 承诺每段不超过目录项的 size"。而 `fault-fat32-tail` 那条注入推翻的正是这句承诺——
   两者同时打开时的表现是**越界 ⇒ panic(39)**：量具自己把"用例红"升级成"内核挂"。
   现在写之前先过界，越界就记下现场并拒绝往下装，实测
   `已喂=31232 这段还要喂=89 目录项说=31320 走链自报字节=31321`（正好多 1 字节），判定 FAIL(35)。
   第 37 行因此不写"这一构建红了就算"，而写**红必须点名**：FAIL 而串口没有那行溢出 ⇒
   实际值改判 CONTENT-MISMATCH，那一行就不许假装符合。

## 后果

- 接线方式沿用 `if=ide,index=N`（q35 的内置 ich9-ahci 把 IDE 兼容总线映到它的端口上，
  index 就是口号——这个映射是 M5-c 那一次**实测**的）。不另写 `ide-hd,bus=ahci0.x`：
  那条路径本机没量过，而端口表是内核自己扫出来的，接线方式一变就等于换了证人。
  口位的证人换成两头：`check-fat32-ports` 比口号，`check_fat32` 比内容
  （两块卷簇数不同，口 3/口 4 接反了内容对账当场红）。
- 判定表从 33 行长到 **37** 行（第 34 行"两个实现对上同一批数"、第 35 行"尾格多喂必须红"、
  第 36 行"盘上取出的容器装上并跑通，且与内嵌那份同数"、第 37 行"③ 的红必须点名"）。
- 这个变体**不进正常构建也不进四把尺子**：每簇一次 FAT 读 ⇒ 一轮走链发几百条块命令，
  取证行的量会挪动串口量，而 P4 那把尺子量的就是串口量。
- 真机上必须重测（M7）：卷是 mtools 造的，簇大小 1 扇区、根目录在簇 2、无 LFN——
  真实 ESP/SD 卡的几何与目录形状都会不同，而 `band_type` 那条反例在真机上可能反而一致，
  那时"阈值会拒绝一块读得动的卷"这条证词需要新的夹具，不能靠这块卷一直供着。

## 证红（本轮实测，三条都是跑起来才出现的）

1. **`FAT32_CLUSTER_MASK` 少写一个 nibble**（`0x00FF_FFFF`，应为 28 位的 `0x0FFF_FFFF`）。
   真卷的 EOC 是 `0x0FFF_FFFF`，被截成 `0x00FF_FFFF` 之后**小于** `EOC_MARKER`，于是每条链的
   结尾都不算结尾：两块真卷的三个文件全部报 `ChainEndsLate { bytes: 31320, size: 31320 }`——
   两个数相等，看起来像自相矛盾，而日志里没有末簇与它的 FAT 读数。定位它要靠宿主机重算
   FAT 扇区的哈希（`0xbaa84ee306374738` 两边相同 ⇒ 传输是对的，错的是读法）。
   事后做了两件事：把那个数写进常数旁边的注释（**为什么**是 28 位），并给
   `ChainEndsEarly/Late` 加上 `cluster`/`next` 两格——这一族错误以后会自己报出末簇号。
2. **一行字节序写反的负样本不会红，它会绿着不测任何东西**：`软盘形状` 那行把
   `total32 = 32,640` 写成 `0, 0x80, 0x7f, 0`（= 0x007F8000 = 835 万），阈值判型于是翻成
   FAT32、解析成功，于是"必须命中 UnsupportedFat(Fat16)"那一格拿到的是 `Ok`。
   负样本表每一行的期望必须与**镜像字节的算术**对得上，不能只对得上注释。
3. **两处查的是配方的意图而不是盘上的字节**：`open("CYCLIC")`（盘上是 `CYCLIC.BIN`）、
   `open("?OLD.TXT")`（配方的原名是 OLD.TXT，但首字节被写成删除标记 0x05 之后，
   那个 `O` 在盘上已经不存在了，两台实现都只能读成 `?LD.TXT`）。
   同族第三个：负表里"扩展字段不在位 ⇒ NoSignature"是**错的期望**——`BS_BootSig` 与
   510 那两字节的签名是两格，清 66 号字节只会让 `fs_name_ok` 变 false，解析照旧成功；
   那一格由 `m_boot_sig` 单独判，不该混在"必须被拒"这张表里。
