# ADR-026: 用户页住在低半区，判据落在"生效位"，架构规定的偏移按字节读回来

状态：已采纳（2026-11-05，M4-1 实测）
关联：手册 §5.1（R17）§6.3 §6.4 §6.7 §10.2 §13.1、ADR-017、ADR-024、ADR-025

## 背景

M4-1 从"红的"到"绿的"拆出五个缺陷，其中三个有同一个形状：**代码表达的意图是对的，
硬件据以决策的是另一样东西**。
①`user::init` 往 `USER_RX` 页里填机器码——W^X 说它不可写，SMAP 说内核不能直接碰用户页；
②用户页的叶子写了 `U/S=1`，而它的**上级表项**没有，ring3 一取指就 `#PF(err=0x15)`；
③`Tss` 用 `#[repr(C, align(16))]` 声明，Rust 的对齐规则把 `rsp0` 挪到偏移 8，
而 CPU 按架构从偏移 4 取 8 个字节——换栈换到一个被截断的地址，直接三重故障。
每一个都在串口上表现成"别的东西坏了"，没有一个能靠读代码看出来。

## 决策

### 一、用户 VA 单独一段窗口，登记仍共用一张表

`mm::USER_VA_BASE = 4 GiB`（低半区规范地址、在恒等映射 `0..max_phys` 之上），
`alloc_user_va_range()` 与 `alloc_va_range()` 共用同一条扫描与同一张 `va_res` 登记表，
只是起点与上界不同（内核段上界 `0xffff_ffff_7000_0000`，用户段 `1 TiB`）。

为什么不"复用内核前沿的 VA、再把共享的上级表项放宽"：内核的链是为内核建的，
放宽共享条目等于把**整条内核映射**的可达性一起拖进判据；单独一段之后，
用户页的 PML4/PDPT/PD 由用户映射自己创建（`walk_leaf` 的 `share` 参数带上 `P_USER`），
链上没有内核页。`walk_leaf` 仍然会把 `P_USER` 或进已存在的上级，因为这不是理论洁癖——
`effective_flags(内核栈)` 必须读出 `user=false`，这一条是对照组（见决策三）。

`PageFlags::USER_RX/USER_RW` 由 `new()` 强制 W^X，这个前提要能兑现才有意义：
**RX 页写不进去**，所以用户镜像的内容一律经 HHDM 直写页框，再来装叶子。
副产品是"内核构造用户内存"不需要 SMAP 窗口，只有"内核事后读用户内存"（`read_slot`）需要——
两条路径分开，§10.3 将来做 `copy_*_user` 时故障归属少一半歧义。

### 二、`map` 装完叶子必须把整条链读回来验一遍

`MmError::UserChainBlocked`：`flags.user` 的叶子装好后，用 `effective_flags()` 逐页确认
`user == true`，任何一页不成立就**整段回滚**并明确失败。

理由就是缺陷 ②：没有这一步，映射会"成功"，而失败在几百行之后的 ring3 取指上。
宁可不映射，也不留一条对 ring3 假装存在的映射。

### 三、判据落在生效位，不落在意图上

`mm::effective_flags(va)` 沿 PML4→PDPT→PD→叶子走一遍，规则两种：
- **P / W / U/S = 逐级相与**：每级都许可才算许可；
- **NX = 逐级相或**：任一级置了"不可执行"，这页就不可执行。

`NX` 一开始也按相与算了，于是用户数据页读出来是"可执行"——W^X 判据立刻报红。
**量具把规则算错与被测代码把位写错，在现场长得一模一样**，所以这条判据同时是两边的人证：
代码页 `user && executable && !writable`、数据页 `user && writable && !executable`、
内核页 `!user`（对照组），三者缺一即红。

`levels` 字段（沿途用了几级表）也在判据里：读回 2 级说明撞上了大页或链没走完，
那种读数不能当"权限正确"的证据。

### 四、偏移由架构决定的结构，一律按字节位置核对

`Tss` 改为 `#[repr(C, packed)]` + `const _: () = assert!(size_of::<Tss>() == 104)`，
所有读写走 `addr_of_mut!` + `write_unaligned`（packed 字段不能取引用），
并且新增 `trap::tss_offsets(slot)`：**按 Intel 那张表的字节位置**（RSP0@4、IST1@36、
IOMapBase@102）把值读回来。用例 `t_user_roundtrip` 判据 0c 把它与
`install_exception_stack` 装的 ist1、`set_rsp0` 装进的内核栈顶逐一比对。

同理，GDT 的用户段现在由判据 0 直接验**描述符位**（S=1、DPL=3、type、L=1/D-B=0），
而不是等 `iretq` 挂：缺陷 ③ 的现场是 `#GP` 而 QEMU 把错误码的 RPL 两位抹掉，
`0x1b` 报成 `0x18`，读起来像"选择子写错了"，指不到真正漏的那一位。

### 五、`PF_RESUME` 必须有配对的第二条登记

受控 #PF 探针原来只登记"恢复地址"。探针访到**已映射**的页时根本不故障，
那条地址就留在 `.data` 里成为地雷：下一次无关的 #PF 会被它劫持，跳进探针尾巴上的
`mov rax,1; ret`，而那条 `ret` 从别人的栈上弹出一个不是返回地址的数（实测 `0x3a000`），
内核就在 ring0 带着它去取指。现在 `PF_EXPECT` 记下探针**预期故障的 VA**，
分发必须满足 `resume != 0 && expect == cr2 && 不是取指故障` 才改 `frame.rip`；
否则计入 `PF_STALE_HITS` 并按非预期故障处理，且 `probe_page_fault` 返回前无条件清登记。

### 五、加载器按"能不能分配"来设计，而不是按好写好读

M4-2 第一次把这条规则撞出来：`KT_ELF` 的初版写了一句
`let h = HELLO_ELF.to_vec();`（22 KB），现场是
`kernel panic at /rustc/.../library/alloc/src/alloc.rs` + `qemu-exit=39`，
因为本内核的分配器上限是 `heap::LARGE_MAX = 2048` 字节。
所以 `elf::Program` 用定长数组而不是 `Vec`，`user::load` 逐页流式而不是按段开缓冲——
**这两处不是风格选择，是被分配器的上限逼出来的形状**，反过来也一样成立：
把"外部输入有多大"交给"内存分配"决定，就是把可用性交给输入决定。

同一层的另两条连带结论：

- 段权限需要第三种组合 `USER_R`（`r--`）。只有 RX/RW 时加载器只能多给权限。
- 用户 VA 可以**由容器指定**（`ET_EXEC` 搬不动），所以登记表需要一个
  "按给定地址占用"的入口（`mm::reserve_va_at`）：它比"发一段没人要过的"更危险，
  必须同时检查"没有被登记过"和"一页都没映射"，否则拒绝点会跑到 `map` 里去，
  回滚就要做第二遍。

## 被否掉的替代做法

- **先映射成可写、填完再改属性**：需要一条 `protect()`/重映射原语（要处理 TLB 一致性），
  M4-1 不该顺手发明它；HHDM 直写不需要新机制。
- **只验 `PageFlags`**（意图）：正是缺陷 ② 的成因。
- **给 `MAX_VA_RESERVATIONS` 拍一个更大的数**：改成由用量推导
  （`MAX_CPUS × MAX_TASKS + 16`），并且让"登记表满"依旧是明确失败而不是静默发放。
  24 那个数是 M2 时代拍的，M4 一开用户态就撞上，现场是 `L4: VA 保留登记表已满`。

## 还没解的（记在 BACKLOG 的 M4 一节）

任务**槽位不回收**：被杀掉的 Done 用户任务照样占着 run queue 的一格，
`MAX_TASKS` 从 6 提到 8 只是让这个用例不靠"谁先跑"的运气。
真解要先有"标 Free 之前先 unmap 栈、把帧归还 PMM"的路径——否则资源台账会说谎。

## 证据（同一构建，2026-11-05，`tools/aurora.py test` 10/10 符合）

```
user: segs udata=0x1b ucode=0x23 idx=[3,4] segs_ok=true
user: eff code=EffectiveFlags { user: true, writable: false, executable: true, levels: 4 }
      data=EffectiveFlags { user: true, writable: true, executable: false, levels: 4 }
      kernel_stack=EffectiveFlags { user: false, writable: true, executable: false, levels: 4 }
user: tss rsp0=0xffff80002045dff0 ist1=0xffff80002041dff0(期望 0xffff80002041dff0) iomap=104 tss_ok=true
user: served=3 unknown=1 kills=1 slots=[Some(1),Some(42),Some(18446744073709551615)] smap_blocks_kernel_read=true bad_state=Done
user: … pf_stale_hits=0 probes_clean=true
```
负样本一行也能动：`--features fault-no-smap` ⇒ `BOOT-INVALID(rc=37)`，
证明 §5.1 R17 那条"必需项没开成就不启动"不是修辞。
