# ADR-227：`unmap-trace` 让偶发消失（**典型 heisenbug**）

状态：**提议**（2026-11-23：插桩后 25/25 全绿，偶发不再复现）

关联：ADR-225（取证链）、ADR-226（排除假设 1）

> ADR-226 把假设收窄到「窗口内有 `Mapping` 被 drop」，并给了下一步：
> 在 `Mapping::drop` 里加一行日志。**加了之后，偶发消失了。**

## 插桩

```rust
#[cfg(feature = "unmap-trace")]
if self.virt.0 >= 0x1000_c0000 && self.virt.0 < 0x1000_d0000 {
    crate::log_info!("unmap-trace: 撤容器段 va={:#x} pages={} AS={:?}", ...);
}
```

只在 `unmap-trace` 特性下、只覆盖 fileprobe 的两个 LOAD 段。**没有改任何分支。**

## 结果：25/25 全绿

| 轮次 | 结果 | `unmap-trace` 行数 |
|---|---|---|
| 1–10 | **10/10 全绿** | 每次 2 行 |
| 11–25 | **15/15 全绿** | — |

每次都只有 **2 行**，而且是正常收尾的那两次：

```
撤容器段 va=0x1000c0000 pages=1 AS=None
撤容器段 va=0x1000c2000 pages=1 AS=None
```

**窗口内没有任何额外的 `Mapping` 被 drop。**

## 结论：这是 heisenbug

插桩前：约 1/8 失败。插桩后：**25/25 全绿**。

唯一改变的是 `log_info!` 那一行 —— 它写串口、耗时间、改变时序。

**所以这个偶发对时序极度敏感。** 这也解释了为什么它难定位：
任何「让它可观测」的动作都可能让它不再发生。

## 这否掉了什么

ADR-226 的假设 3 是「窗口内有 `Mapping` 被 drop」。
插桩直接观测这条路径：**窗口内一次都没有**。

但要注意**这个否定是弱的**：

- 插桩本身可能改变了行为（heisenbug），所以「没观测到」不等于「不存在」；
- 只有 2 行说明正常收尾的 drop 被观测到了，**插桩是有效的**；
- 但失败场景不再出现，所以无法确认失败时那条路径的行为。

**正确的说法是：「在插桩后的时序下，假设 3 不成立。」不能推广到「假设 3 永远不成立」。**

## 保留 `unmap-trace`

它默认关，只在需要定位时开。**留着它比删掉好**：

1. 它是唯一能看见「容器段被撤」的入口；
2. 若将来这个偶发换一种形态复现，直接开它就能取证；
3. 它证明了「插桩有效」（正常收尾的 2 行被看见）。

## 下一步（换方向）

heisenbug 不能靠加日志抓。可用的手段只剩：

1. **`bench` 的 P1（切换尺）** —— 它不改内核路径，只测量，可能不干扰时序；
2. **QEMU 侧的 `-d int`**（判定表里 M5-g③ 用过）—— 从外部看中断时序；
3. **不加日志的计数器**（原子自增，不写串口）—— 时序影响最小。

第 3 条最可能成功：把「窗口内 drop 次数」记成一个原子量，窗口结束时读它。
**不写串口**，所以不会改变时序。

2. **下一步应改用「不写串口的原子计数」**
3. **`unmap-trace` 默认关** —— 不能进默认档（会让偶发消失，掩盖问题）
