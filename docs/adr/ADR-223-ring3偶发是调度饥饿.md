# ADR-223：`t_fs_open_ring3` 的偶发是调度饥饿（**未修，已定位**）

状态：**提议**（2026-11-23：定位到调度层，**没有修**）

关联：ADR-222（`XFER` 锁序修复，`fs-open` 档从此能跑）

> ADR-222 修好 `XFER` 之后，`fs-open` 档第一次跑到底。
> `t_fs_open_ring3` 变成**偶发**：3 次里 1 次失败。

## 现场对比（决定性数据）

| | 成功 | 失败 |
|---|---|---|
| `换人` | `0→6` | `0→6` |
| `tick` | `6→11` | `6→56` |
| `rounds` | 3,412 | **44,523** |
| `served` | 34 | 34 |
| **`被拒`** | **0** | **41,613** |

两次的 `换人` 与 `served` 完全一样，**只有 `被拒` 差 4 万倍**。

失败时的症状链：

```
读用户页被拒（9 次）
  => 哨兵 DONE 没到位
  => 窗口超时
  => 所有信箱槽读到 0
  => 20+ 条判据全红
```

## 判断

**探针任务被调度了 4 万多次却一次都没真正跑起来。** 这是**调度饥饿**，
不是文件系统的问题，也不是 ADR-222 引入的。

## 为什么这次没修

1. **它与既有的几个偶发同源**：`t_q2_workload_slots` / `t_process_startup` /
   `t_shootdown_masked` 等也是约 1/10 的偶发，一直没有归因。
2. **没有第二台仪器**：`被拒` 是调度器内部计数，我无法在不改 `sched` 的前提下
   观察「谁在拒绝、拒绝什么」。
3. **AGENTS.md 硬约束 1**：不改已实测的调度语义。要动它必须先有 ADR 与更细的证据。

## 已排除

- **不是文件系统**：失败时 `被拒=41613` 发生在探针拿到 CPU 之前，FS 代码根本没跑。
- **不是 ADR-222 引入**：`XFER` 锁序修复让档从「100% HANG」变成「约 2/3 通过」，
  方向是对的；剩下的偶发是它**暴露**出来的既有问题。
- **不是页映射丢失**：诊断实测 `load 后 data_va=0x1000c2000 mapped=true read=Some(0)`，
  页在。

## 下一步该怎么做（留给下一轮）

1. 给 `被拒` 加分类计数（按拒绝原因），这是最小侵入的取证。
2. 查 `spawn_user` 之后到首次换入之间的路径，看是否有「任务可运行但不被选中」的窗口。
3. 用 `bench` 的 P1（切换尺）在失败跑里取一次快照，与成功跑对比。

|---|---|---|
| 1 | 0 | ok |
| 2 | 2 | **failed** |
| 3 | 0 | ok |

约 **2/3 通过**。这不是「绿了」，是「有时绿」。

## 一个纪律提醒

**「偶发通过」不等于「修好了」。** 本 ADR 特意把它写成 `提议` 而不是 `已采纳`，
并把失败率写出来 —— 否则下一个人会以为 `fs-open` 档已经稳定。
