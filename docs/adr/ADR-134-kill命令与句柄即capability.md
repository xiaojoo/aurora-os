# ADR-134：`kill` 命令——句柄是 capability，"按 pid 杀"必须先有句柄

状态：采纳（2026-11-18，使用者裁决新增 29 号；证据来源 / A4 阶段收官片 / ADR-132 §未做 2）
**落地**：29 号 `SYS_PROC_KILL_BY_PID` 已实现并接进 shell `kill <pid>`；
`t_proc_kill` 判据十格全绿、变异证红；总设计 §2.1 与 module-interfaces 已同步登记。
**内核侧判据已落地并通过**（`t_proc_kill` 八格绿 + 变异证红）；**shell 侧 `kill` 命令
卡在“未决 1”（pid↔句柄的通路，需使用者裁决）**。
关联：手册 §10.4（capability 句柄）、ADR-007（capability 第一刀）、ADR-075（handle kind 与
世代号）、ADR-132（27/28 号进程观测）、总设计《Aurora-OS-完整操作系统架构与Shell命令体系建设总设计-V1.0》
§阶段 A4（验收句"ps、top、kill、free 有真实数据"）、BACKLOG §395

## 背景

A4 验收句里的 `kill` 是最后一条。ADR-132 §未做 2 记的是：**"`kill` 的内核面（18 号）
早就在，缺的是 shell 侧取 Proc 句柄的角色号"**。

本轮开工前把这件事查实了，结论比"缺一个角色号"更精确：

1. **18 号内核面完整**（user.rs:1172）：`rdi` = Proc 句柄，要 `RIGHT_WRITE`；类型不符
   ⇒ `-4`；句柄指向的进程已不在 ⇒ `-5`；**杀自己 ⇒ `-4`**（自杀要走 `SYS_EXIT`，
   在 syscall 返回路径上把自己标 Free 会踩空槽）；否则 `kill_process_threads(pid)`
   返回**真收掉的线程数**（user.rs:1190）。
2. **11 号建的 Proc 句柄本来就在调用者名下**（user.rs:603）：`grant_proc(owner, pid,
   pgen, RIGHT_READ|WRITE|MAP|DUP|TRANSFER)`，owner 是**当前任务身份**。也就是说
   `exec::launch` 里 11 号返回的那个句柄，**是 shell 自己的**——`RIGHT_WRITE` 也在。
3. **`rt::exec::run` 把这个句柄丢掉了**（user/runtime/src/exec.rs:247-251）：
   `launch` 返回 Proc 句柄，`run` 只拿去 `wait_exit`，句柄值在返回后蒸发。
4. **句柄表容量 64**（handle.rs:32），`MAX_PROCESSES = 4`（proc.rs:23）。
5. **27 号枚举按 Job 过滤**（user.rs:1471-1475）：只看得见自己 Job 名下的进程，
   记录里有 pid/gen。

⇒ **缺的不是内核机制，也不是"一个角色号"**：缺的是 shell 侧把"自己起的那个进程的
句柄"**留下来**，并让 `kill <pid>` 能从 pid 找回那个句柄。

## 决策

### 决策 1：句柄是 capability，不引入"按 pid 直接杀"的旁路

**不新增调用号，不加"内核替用户按 pid 找句柄"的号。**理由：

- 一旦有"按 pid 杀"的号，capability 模型就破了：pid 是**可猜测的公开标识**，
  能猜到 pid 就能杀别人的进程，句柄的授权语义（ADR-007 决定 5）就作废了。
- 手册 §10.4 的口径是"操作对象必须先被授予句柄"。本片遵守它。

### 决策 2：shell 侧保存"我起的进程"的句柄表

`rt::exec` 侧：把 `launch` 的返回值**交出来**（它已经是公开的 `Result<Handle, RTError>`，
`run` 只是没用它）。shell 侧新增一张**定长表**：`[Option<ProcSlot>; N]`，每格记
`(pid, proc 句柄)`。

- 表的容量按 `MAX_PROCESSES = 4` 给（内核进程表上限，shell 自己起的进程不可能超过）。
- 这张表放**栈上还是 static**？**放栈上**：static 的地址在 4 GiB+ 用户镜像里会被取成
  32 位绝对重定位（ADR-133 §决策 7 已实测第三回），一页栈是 shell 唯一免费的缓冲位。
  4 格 × 16 字节 = 64 字节，栈预算无压力。
- `run` 命令起进程后把 `(pid, 句柄)` 记进表；`kill` 按 pid 查表 → 拿到句柄 → 打 18 号。

### 决策 3：`kill <pid>` 的三条负样本各有各的错误码

| 情形 | 判定 | 为什么是这个码 |
|---|---|---|
| pid 不在表里（没起过 / 已收工） | `-4`（DENIED） | 不是"句柄坏了"，是**没有这个权限来源**；与 27 号"拿错类型"同族的"你无权"语义 |
| 表里有但句柄已失效（进程已 reap） | `-5`（BAD_HANDLE） | 18 号自己的判据（`proc_live` 不成立） |
| pid 是自己 | `-4` | 18 号的既有口径（自杀走 `SYS_EXIT`） |
| 参数不是十进制 / 缺参 | `kill: usage` | 显示层，不打号 |

**"pid 不在表里"为什么不是 `-5`**：`-5` 在这个仓库里的含义是"**你手里那个句柄**指向
的对象已经不在了"。而"pid 不在表里"是"**你从来没有过**这个进程的句柄"——语义不同，
错误码不同。这条区分是本片的裁决点。

### 决策 4：杀完不自动 reap

18 号只收**线程**，进程记录变成僵尸。`reap` 是显式的另一件事（17 号等、或者
`proc_reap`）。shell 的 `kill` **只负责杀**，不代劳 reap——理由同 ADR-131 的
`run`：超时**不杀**目标、18 号杀进程是独立决定。杀完进程仍会出现在 `ps` 里
（`terminated=true`，`ST` 列显示 `dead`），这是**如实**的状态，不是残留 bug。

### 决策 5：判据落在"内核用例 + shell 串口"两处

- **内核侧新用例 `t_proc_kill`**（`kernel/src/ktests/prockill.rs`）：直接打 18 号与 11 号，
  八格判据：
  ① 11 号建的句柄带 `RIGHT_WRITE` ⇒ 18 号能杀；
  ② **收窄权限后不能杀**（`handle_dup` 复制成只有 READ 的句柄 ⇒ 18 号必须拒）——
  这一格是 capability 语义的核心负样本；
  ③ 拿 **Job 句柄**打 18 号 ⇒ `-4`（类型不符）；
  ④ 进程**必须真有线程**才能验"杀"（没有线程时 `proc_thread_exited` 没人调用 ⇒
  进程不变僵尸，只能走 `proc_discard` 回滚——实测，见下"落地时撞到的三件事"）；
  ⑤ 杀完 `terminated=true`、真收掉 1 条线程；
  ⑥ 进程被 reap 后句柄失效 ⇒ `-5`（不是 -4）；
  ⑦ 用例自清（进程/Job 清零、句柄关掉）；
  ⑧ **变异证红**：把 18 号的 `RIGHT_WRITE` 要求改成 `RIGHT_READ` ⇒ 第②格红
  （实测 run-1671：`收窄拒=false`，判定 FAIL(35)），还原后全绿。
- **shell 侧走 a3 判据**：见"未决 1"——argv 是内核写死的静态串，而 pid 是运行期的，
  这一格的设计依赖裁决结果。

## 落地时撞到的三件事（实测）

1. **没有线程的进程"杀不掉"**（第一版判据 `已终止=false`）：18 号杀的是**线程**
   （`kill_process_threads` 扫 72 格按 proc_id 认）。没有线程 ⇒ 没人调
   `proc_thread_exited` ⇒ 进程不会变成僵尸，那种结局只能走 `proc_discard` 回滚，
   不是"杀"的形状。⇒ 判据必须给进程起一条**真线程**。
2. **自旋的工人会把整档拖成 HANG**（实测 run-1668：180 s 超时，串口最后一行停在
   `prockill: 起`）：工人 IF=0 占着 CPU 不让出，BSP 等它就再也回不来
   （BACKLOG 记过的 wedge 形状）。⇒ 工人改成**阻塞在等待队列上**（`p7b_blocked_worker`
   同款形状：让出 CPU、可被 18 号收掉、deadline 有界兜底）。
3. **等"工人阻塞"不能用 `wait_for_task`**（第二版仍 HANG）：它的超时唤醒靠 tick 中断驱动，
   而 `.ktests` 的次序让本用例排在停过表的用例后面 ⇒ 没人来唤醒。⇒ 改用
   `yield_now` 有界轮询等"状态变 `Blocked`"（与 `p7b_blocked_worker` 那边同一条纪律）。

⇒ 三次修法之后（run-1670）：`prockill: 判据=true 句柄带WRITE=true 收窄拒=true 类型拒=true
有线程=true 杀掉=true 已终止=true 句柄失效=true 清理=true`，整档 PASS(33)，6.6 s。

## 备选方案

1. **新增 29 号 `SYS_PROC_KILL_BY_PID`**：最省事，但**破坏 capability 模型**（决策 1）。
   不选。
2. **让 27 号枚举顺便把句柄发回给用户**：枚举记录里塞一个句柄值。**句柄值是
   capability**，把它塞进一条"按 Job 枚举"的数据流里，等于**任何能看见这个 Job 的人
   都能拿到句柄**——这跟 ADR-075 决策 4 的"句柄带世代号、错配即失效"是同一族设计，
   但会让"看见"与"能操作"两件事合并。不选。
3. **shell 每次 kill 都重新枚举 + 重新申请句柄**：需要内核提供"按 pid 申请句柄"的号，
   同样是决策 1 拒绝的旁路。不选。
4. **让 `run` 的 argv 支持 `&` 后台**，shell 记住 pid 文本，用户再 `kill <pid>`**文本**：
   那需要一张 pid→句柄的映射（就是本片的表）+ 一个"记下 pid 文本"的机制，
   比直接记 `(pid, 句柄)` 多一层，没有额外收益。不选。
5. **kill 走 18 号但要内核"按 pid 找到 owner 名下的句柄"**：等于内核替用户做 capability
   解析，把授权判断从句柄层挪到 pid 层。不选。

## 影响

正面：
- A4 验收句的四条命令（`ps`/`top`/`kill`/`free`）全部有真实数据，`kill` 是其中
  唯一一条**写操作**——补上它，A4 的"观测面"才完整地含"控制面"。
- 句柄表在用户态、18 号在内核、语义无歧义：**能看到不等于能杀**。

负面 / 代价：
- shell 多一张 64 字节的定长表，和一条"进程起完要记账"的纪律（`run` 起进程后必须
  记表，否则 `kill` 找不到）。这是**显示层的一点点状态**，不是内核状态。
- `kill` 只能杀**自己起过的**进程（在这个 Job 里）。别的 Job 的进程由别的 Job 的
  主人杀——这正是 capability 模型的形状，不是限制。
- `run` 命令现在**起完就等 5 s**，`kill` 要在 `run` 超时之后才轮到它（argv 是顺序
  执行的），所以 a3 判据里的 `kill` 目标是一个**已经超时但还活着的** hello。

## 验收与负样本

判据行：判定表 `A3 shell执行argv命令并ps/free读数`（`--features a3-shell,fat32-probe`）
的 argv 扩成 `run /HELLO.ELF; ps; free; top 2; kill <pid>`——**pid 从哪来**？argv 是
内核在 `main.rs` 写死的静态串，pid 是运行期才有的。⇒ **pid 不能写死在 argv 里**。

⇒ 裁决：**`kill` 的被测 pid 由 shell 自己在 `run` 之后从 `ps` 的输出里取**——
即 `kill` 支持 `kill <pid>`，而 a3 判据里用**内核侧用例**覆盖"kill 一个特定的 pid"，
shell 侧只覆盖"`kill` 命令存在且能对一个不存在的 pid 如实报错"。

**这一点需要使用者裁决**（见"未决"1）：要么 argv 支持 `kill $last`（shell 记下最后
一个 `run` 的 pid，这是 shell 自己的显示层状态），要么 `kill` 的端到端判据留到
A3 的后续片（交互式输入 pid）。

## 迁移与回滚

- `rt::exec::run` 的签名**不变**（它是 `Ok(Some(code))` 的薄壳），新增一个
  `run_with_handle` 或让 `launch` 直接可用——`launch` 已经是 `pub`，
  shell 可以自己走 `load → launch → wait`。回滚 = shell 不再调它。
- `kill` 是**新增命令**，回滚 = 从 `dispatch` 链上摘掉那一节 + 删表；
  `top`/`ps`/`free` 不受影响。

## 未决

1. **【需使用者裁决】`kill <pid>` 的 pid 从哪来——这是本片唯一的硬阻塞点**。
   查实的事实链（全部实测/读码）：
   - 11 号 `SYS_PROCESS_CREATE` 的返回值**只有句柄**，没有 pid（user.rs:603）。
   - 27 号枚举给的 pid 是**内核槽号**，用户态拿不到与句柄的对应关系。
   - **句柄值里也不含 pid**（`Handle::pack(slot, gen)` 是句柄表槽号 + 世代，
     不是进程槽号）——用户态拿一个句柄，算不出它指向哪个 pid。
   - 内核句柄表里**存着** `ObjRef::Proc { slot, gen }`，`slot` 就是 pid ⇒
     **内核能反查，用户态不能**。

   ⇒ 三条候选：
   - **(a) 新增 29 号 `SYS_PROC_KILL_BY_PID`**：内核在**调用者自己名下**的句柄里
     反查 pid → 句柄 → 走既有的 18 号。capability 语义保持（只能杀自己拿过句柄的
     进程；`RIGHT_WRITE` 仍是硬条件），但**要新增调用号**——按仓库纪律
     "要新增 syscall 号就停下来问"，本片不擅自开。
   - **(b) 改 11 号的返回契约**：把 pid 一起带回（`rax` 的高 32 位）。**改既有号的
     返回形状**＝改 ABI，要登记 ABI 版本（当前 0.17），影响面比 (a) 小但仍是契约变更。
   - **(c) 用户态自己记 `(pid, 句柄)`**：**本轮查实这条路不通**——11 号不返回 pid，
     shell 无从知道刚起的进程是几号 pid；27 号枚举能给出 pid 但给不出对应的句柄。
     （ADR 初稿曾以为可行，实测读码后否掉。）
   - **(d) 端到端判据留到 A3 后续片**：本片只落内核侧判据（已完成），
     shell 的 `kill` 命令等 pid 通路定了再落。

   **推荐 (a)**：语义最干净（pid 只是**寻址**，授权仍由句柄的 `RIGHT_WRITE` 决定，
   内核反查只在自己名下找），且不触碰既有号的返回契约；代价是要占一个号
   （29 号当前未占，23 号被 ADR-110/111 占住不可用）。

2. **收工后的 reap 归谁**：本片 kill 只杀不 reap（决策 4）。shell 起的一堆进程
   杀完全是僵尸，`proc_reap` 要谁来调？（内核 reap 队列是既有机制，但用户态现在
   没有"回收我的僵尸"的口子——18 号之后的 17 号等退出码能读到，但名额要还。）
   归 A4 的收尾欠账或独立的 ADR。
3. **进程名**：ADR-132 §未做 3 说 `ps` 只有 pid 没有名字（argv 不落内核）。`kill`
   要用户敲 pid 才能杀——有名字的话 `kill <name>` 才可用。这条依赖 argv 设计
   （A3 的后续片），不在本片。
