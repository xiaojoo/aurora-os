# ADR-244：槽位「Free」不等于可复用 —— 三条 spawn 路径的选槽判据收紧

状态：**已采纳**（2026-11-23）。实测把 `t_q2_workload_slots` 的偶发从
**30%（15/50）压到 0%（0/20）**，整链 PASS 从 **2/8 → 19/20**。

关联：ADR-243（同一条病的判据侧）、ADR-047 决策 2（持 RUNQ 不许 drop Mapping）、
ADR-067（OwnedSet）、ADR-241（信箱归属）、BACKLOG §565/§566。

## 问题

`t_q2_workload_slots` 长期偶发，失败签名**恒为**：

    q2: 回滚不成立 f97419->97415(差 -4) va21->22(差 1) 收尸=4 回滚=0

`-4` 恰好是 `STACK_PAGES`，`va+1` 恰好是 `STACK_VA_PAGES(5)` 里被映射的那 4 页之外的
1 条保留。**一条内核栈（4 页 + 1 条 VA 保留）永久漏掉。**

### 取证过程（每一步都留了读数，不是猜的）

1. **加「再等一个窗口」**（`q2-再等`）：等 3×10⁹ cycles 后 `f` 与 `va` **一个都没变**
   ⇒ 不是「回来得晚」，是永久漏。
2. **逐条打 7 条线程的终态**（`q2-槽`）：**全部** `state=Free owned=0 kstack_lo=0`
   ⇒ 漏的那条**不在** q2 自己的线程里。
3. **扫全部槽位找 `owned>0`**：只找到 `g=257/513/769`（CPU 1/2/3 的 slot 1 =
   各 AP 常驻工人，`spawn_resident` 按设计不退出）⇒ 它们的栈是**合法常驻**，不是泄漏。
4. **给 `release_va_locked` 加拒绝计数**：同一跑 `拒绝放手的保留 12→12`
   ⇒ **零拒绝**，漏的不是「放手被拒」，而是「**根本没人放手**」。
5. **给 `release_owned` 加「按 slot 的调用序」日志**——这一步定位到了：

        #36 slot=6 放出=1
        #37 slot=7 放出=0     ← 就是它
        #38 slot=8 放出=1

   `has_bag` 检查说「袋里有东西」，进去却是空的。那一跑正是红的。

## 根因

三条 spawn 路径都用 `state == Free` 选槽：

| 位置 | 函数 |
|---|---|
| `mod.rs:1711` | `spawn_inner` |
| `mod.rs:1782` | `spawn_user` |
| `mod.rs:1613` | `init_idle` |

而 `terminate_task` 是**在持 RUNQ 时**就标 `Free` 的（`mod.rs:376`），`release_owned`
要等**放锁之后**才跑（`release_owned` 里 `drop(bag)` 在锁外，ADR-047 决策 2 的硬要求）。

于是存在窗口：**槽是 Free、袋里还挂着映射**。这时 `s.tasks[slot] = Task { ... }`
整体覆盖旧槽，旧袋连同里面的 `OwnedItem` 一起消失——
**`OwnedSet` 没有 `Drop`**，所以 `Mapping::drop` 根本不跑，4 页内核栈与那条 VA 保留
再也没有主人。

这也回答了第 2 步的怪现象：**漏的那条槽被新任务复用并覆盖了**，新任务自己正常走完
生命周期，所以事后逐条查全是干净的。

## 决策

1. **三条选槽判据全部收紧成「`Free` **且** `owned.n == 0`」**。
   袋不空 ⇒ 还没被回收，**不能用**；跳过让 `reap` 在下一次抢占点收它才是对的路径
   （不能就地释放：那要在持 RUNQ 时 drop `Mapping`，ADR-047 决策 2 明令禁止）。
2. **`terminate_task` 的就地回收带上 `dead_id`**（`release_owned_checked`）：
   `has_bag` 快照与真正取袋之间，那个槽可能已被 `reap` 收掉并**复用**；
   校验放在取 RUNQ 的那个临界区里，与取袋同一个原子步骤。
   命中时记 `RELEASE_STALE`（纯原子，不写串口，ADR-227 的教训）。
3. 新增两个可数证据：`spawn_skipped_stale()`（因袋未空而跳过的次数）、
   `release_stale()`（因槽被复用而拒绝回收的次数）。

**这是收紧，不是放宽**：原判据在「Free 但袋还满」时认为可复用是**假绿**；
新判据要求袋真空。

### 负样本（变异证红）

把 `Some(dead_id)` 换回 `None`（恢复旧行为）跑 8 次：**1/8 红**（`run-10944`）。
**这条负样本的强度不足**——1/8 与 0/20 在统计上分不开。如实记在这里：
`dead_id` 校验本身**没有被独立证明是必需的**，它是在修 `Free` 判据的同时加的第二道闸，
而实测 `stale=0`（20 跑里一次都没命中）。真正的修复是**选槽判据那条**。

## 未决

1. **`dead_id` 校验是否必要，未证明。** 20 跑 `stale=0`。保留它是因为它是零成本的
   防御（一个整数比较）且语义正确，但**不要**把它当成已证实的修复。
2. **20 跑的样本量不足以声称「偶发已消除」。** 30% → 0/20 的置信区间上界仍在
   ~14% 左右。要更强的结论需要 100+ 跑。本 ADR 只说「20 跑未复现」。
3. **`0x100002000` 那条 3 页 VA 保留**（ADR-243 未决 3）**未处理**：它从 2026-11-11
   起就在打，与 q2 的 `va+1` 是否同源**未验证**。
4. **`t_syscall_abi_arms` 之后的 HANG**（最近 30 跑 11 跑）**未处理**，与本轮无关。

### 更准的读数

| 项 | 修前 | 修后（提交态，25 跑）|
|---|---|---|
| q2 偶发 | 15/50 = 30% | **1/25 = 4%** |

### 新发现 1：探针本身会消除偶发（heisenbug，与 ADR-227 同型）

给 `release_owned_checked` 加一行「记录进来时的 (slot, state, owned.n, idok)」，
**20 跑 0 红**。这不是修复——是**观测改变了时序**（ADR-227 已记过同一件事：
`log_info!` 会让偶发消失）。所以**不要**把探针当成修法，也不要因为它变绿就以为修好了。

### 新发现 2：漏的那一格进来时是 `state=Done owned=1`

探针分布（20 跑合计）里 `slot=7` 恒为 `state=3(Done) owned=1 idok=true`
——**袋里确实有 1 条**，不是空袋。这把 ADR-244 正文里「进来时袋已空」的推测**证伪**了。
真实情形是：**袋里有东西，但那条映射的 `Mapping::drop` 没有把它还回去**，
或者它被还了却又被算进了别的格。

### 新发现 3：`REAP_PENDING[cpu].store(waiting)` 是覆盖，会冲掉别人的账

`reap` 结尾是 `REAP_PENDING[cpu].store(waiting)`（**覆盖**），而 `waiting` 只统计
「被 `gi == cur` 挡住」的格数。若某一格在 `reap` **扫过它之后**才被 `terminate_task`
标成 Done 并 `fetch_add(1)`，那笔账要等下一轮；而本轮的 `store(waiting)` 会把它冲成 0
（本轮谁都没被挡住时）⇒ 之后再也没有抢占点扫那一格。

**我试过修它，失败了，已完整回退。** 第一版用 `fetch_update` 做减法，
结果触发了 `L4 sync: 锁序违规，外层 rank=8(RUNQ) 本次 rank=4(GROW)`
——**20 跑里 15 跑变成锁序违规崩溃**，比原问题严重得多。回退后恢复到提交态。

教训：`reap` 在抢占点上、持 RUNQ，任何在那里新增的锁操作都必须先过
`lock-order.md` 那一关。这个方向**没有**被证伪，但需要重新设计（不能取锁）。

### 未决更新

- ADR-244 正文「覆盖 `Task` 会遗弃旧袋」这条推断**证据不足**：
  Rust 的赋值会 drop 旧值（`OwnedSet` 没有 `Drop`，但 `Task` 的字段会逐个 drop，
  `OwnedSet` 里的 `Option<OwnedItem>` 会被 drop）⇒ `Mapping::drop` **会**跑。
  所以遗弃假设**可能是错的**，而探针显示的 `state=Done owned=1` 支持「另有路径」。
  **如实记：真正的根因仍未确定。**
- 剩余 4% 的偶发**未归因**。下一步应该从 `REAP_PENDING` 的账目语义入手，
  但**必须**在不新增锁操作的前提下重新设计。


## 追加二：2026-11-23 深夜 —— 把「漏的是什么」钉死了，但**没修好**

这一轮**没有**减小 4%，但把归因从推测变成了证据。代码只加了两行**读数**（不改任何判据）。

### 决定性证据：漏的精确是「一条内核栈」

在 `t_q2_workload_slots` 里增读 `resource::live_of(MOD_STACK_TASK)`
（按**模块**记账，不受别的模块分配干扰）：

| 运行 | 模块栈帧差 | 结果 |
|---|---|---|
| run-11130 | **+4** | **q2 红** |
| 其余 15 跑 | 0 | 全绿 |

配合 `(f差, va差)` 的全历史分布（9660 次 `0/0`、24 次 `-4/+1`、16 次 `-8/+2`、
6 次 `-4/0`、5 次 `-12/+3`…）——**每一份都是 4 帧 + 1 条保留的整数倍**，
即 `Mapping::drop` 一次该做的事。所以：**漏的确实是内核栈的 `Mapping` 没被 drop**，
不是别的模块的分配漂移。

### 纠正我上一轮的一个**错误归因**

上一轮我说探针显示 `slot=7 state=Done owned=1` 是泄漏点。**那是错的**——
那个组合在 20 次全绿的跑里**每次都有**，它是 `reap` 准备收的正常中间态。
ADR-244 补记里「漏的那格是 Done owned=1」这句据此**作废**。

### `REAP_PENDING` 覆盖问题：方向对，但两种写法都撞锁序，已全部回退

`reap` 结尾是 `REAP_PENDING[cpu].store(waiting)`（覆盖）。而每个待收格在标 Done/Free
时都已 `fetch_add(1)` 过一次，所以这一格本身就是欠账数；本轮**扫过之后**才被标 Done
的那一格，其 fetch_add 会被 `store(waiting)` 冲掉 ⇒ 再没有抢占点扫它。

试了两种修法，**都失败**：

| 写法 | 结果 |
|---|---|
| `fetch_update(|cur| cur.saturating_sub(retired).max(waiting))` | **15/20 跑 `L4 sync: 锁序违规 rank=8(RUNQ)`** |
| 只 `fetch_sub(retired)`（不补 waiting） | **9/16 跑同样违规** |

第二种的机理：去掉 `store` 后 `REAP_PENDING` 长期不为 0 ⇒ 每个抢占点都全扫
⇒ 持 RUNQ 的锁流量暴涨 ⇒ 级联违规。**两种都完整回退**，验证基线 0/8 违规。

结论：`REAP_PENDING` 的账目语义**确实有问题**，但**不能**在 `reap` 里做读改写
（那个位置持 RUNQ，只允许单条原子指令，而且不能让 PENDING 长期非 0）。
正确方向应该是**在登记侧**做（`fetch_add` 时一并保证不丢），或在收尾时用
一次**有界**的补扫。这一条留作下一次的起点。
