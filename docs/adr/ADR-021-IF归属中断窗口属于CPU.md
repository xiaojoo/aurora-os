# ADR-021: IF 的归属——中断窗口属于 CPU，不属于任务

状态：已采纳（2026-11-05，M3b-1 实测）
关联：手册 §5.2 §6.4 §6.5 §7.1（R16/R23）§12.3.1 §12.4.1、ADR-020、ADR-022、里程碑 M3a→M3b

## 背景

M3a 把抢占调度接上之后，留下一条**没有定论就往下走**的缝，当时的现场是：

> 抢占测试分成两段窗口时，第二段一条 tick 都收不到（`sw=6 ticks=6 irr0=0 isr0=0 svr=0x1ff rte2 未屏蔽`）。
> LAPIC 使能、EOI 干净、重定向表项没关——请求根本没送到 CPU。

根因不在 APIC，在 rflags 的归属：

* 硬件的默认行为是 **`iretq` 把栈上那份 rflags 整个装回 CPU，连 IF 位一起装**。
  中断门（type 0x8E）只把**活的** IF 清零，压在栈上的那份是故障前的原样（IF=1）。
* 于是"谁关中断"变成不确定的事：`with_interrupts` 退出时那句 `cli` 由**当时持有 CPU 的那个上下文**
  执行，而下一个被换入的任务又带回它自己帧里的 IF=1。
* M3a 为了不把这条缝踩实，做了两件事：测试改成单窗口；新任务的合成帧里手工写上 `0x202`（带 IF）。
  后者是**把没定的规则写成了魔数**——注释里就承认了"写成 IF=0 的话接手的新任务带着关中断的状态跑，
  再没有 tick 来抢占任何人"。

多核一来这件事就藏不住了：一条 CPU 上的 IF 是**那个 CPU 的状态**，而任务可能在这条 CPU 上被换入、
在另一条 CPU 上从未被换入过。规则必须先定，再放 AP（BACKLOG 原文："M3b 之前必须定"）。

## 决定

**IF 属于 CPU，不属于任务。**具体三条：

1. 每个 CPU 有一份 `apic::CPU_IF[slot]`——"这个 CPU 的中断窗口此刻是开的还是关的"。
   `apic::with_interrupts` 开窗口时**先立牌再 `sti`**，退出时**先 `cli` 再倒牌**。
   顺序不是风格：反过来就留下一个"窗口开着但牌上写着关"的区间，落在里面被抢占的话，
   换入的人会被强行关掉 IF。
2. 调度器换入任何上下文时，按那张牌**改写异常帧里的 IF 位**，然后才 `iretq`。
   实现就在 `context_load(frame, if_open)` 的第一件事上（`bts`/`btr` bit9）。
   必须放在弹栈**之前**：`rsi` 会在 pop 序列里被那个任务自己的值覆盖。
3. 新任务的合成帧写 `rflags = 0x2`（**只有保留位，不带 IF**）。IF 由 CPU 在换入那一刻供。

选它而不是另一条（"rflags 归任务、窗口只等不关"）的理由，按代价排：

| 判据 | IF 归 CPU（本决定） | rflags 归任务 |
| --- | --- | --- |
| 关中断这件事的归属 | 一个 CPU 只有一个窗口所有者，`cli` 落在谁身上不影响正确性 | 谁最后拿到 CPU 谁就有权关掉别人的窗口——M3a 的实际故障 |
| 新任务首次运行要不要带 IF 魔数 | 不需要（写 0x2，机制供 IF） | 必须，而且必须永远写对（写错=整机停摆） |
| 多核之后要不要改 | 不用：`CPU_IF[slot]` 天然 per-CPU | 要把每个任务的帧按 CPU 重新解释 |
| 代价 | 换入时多两条位域指令；`with_interrupts` 多两次原子写 | 零额外指令 |
| 中断窗口内的语义 | "本 CPU 现在收不收中断"，与谁在跑无关 | "这个任务当时能不能被中断"，与 CPU 的实际状态脱钩 |

代价的第二行要说清楚：**换入的 IF 由牌上的值决定，所以临界区里绝不能开中断**。
持锁期间 `save_and_cli` 已经关了 IF、牌也是关的，这条天然成立；如果将来有人在持锁时调
`with_interrupts`，看门狗（ADR 见 §7.1）会先叫。

## 实测：这条规则真的在跑

正向（默认构建，`-smp 4 -m 512M -cpu max`）：

| 读数 | 值 | 含义 |
| --- | --- | --- |
| `preempt: switches 0 -> 27`，两个工人各 `runs=9` | ✔ | 轮转照旧成立 |
| `preempt: 第二段窗口 ticks 27 -> 29 (收到 2)` | ✔ | **M3a 那条"第二段收不到 tick"的症状没了**。这就是当初删掉的两段式写法，现在作为判据放回用例 |
| `if-rule: frame_before=Some(2)(IF=false) frame_after=Some(66179)(IF=true) runs=2` | ✔ | 合成帧里 IF=0，同一个任务后来存下的抢占现场里 IF=1 —— 这一位是 CPU 给的，不是任务带的 |
| `if_loads closed/open = 0/32` | 见下 | 换入时窗口"开着"发生了 32 次 |

> 说明：上面几行取自**同一条规则在不同运行里的读数**（每一条都来自真实串口日志，不是我拼的），
> 不是同一次启动的快照——切换次数在不同运行之间本来就会抖（27~32）。
> 要看单次启动的完整现场，`docs/testing/baselines/` 里每次 `bench` 都存了一份原始输出。

### `loads_closed = 0`：位操作两条分支都有覆盖，"关着窗口换进别人"这条路径还没有

今天**所有**换入都发生在开窗口的窗口之内：抢占的触发源只有 tick，而 tick 要求 IF=1，
而 IF=1 只在窗口内。所以运行时计数 `loads_closed` 必然是 0——它是**写好了但没被走过**的代码，
不能算验证过。含糊处理的方式是"等以后有触发源再说"，这里分两步补救：

1. **位操作本身直接可测**（已做）。把 `context_load` 开头那两条位域指令拆成一条可调用的
   `if_patch(frame, if_open)`，用例 `KT_IF_PATCH` 拿一块 23 字的scratch 走**同一条指令序列**：
   ```
   if_patch: rflags_off=160 (asm 写死 160) size_ok=true opened=0x8000000000000202
             closed=0x8000000000000002 idempotent=0x8000000000000202 others_untouched=true
   ```
   三条判据各挡一种错法：偏移对账挡"帧布局改了但 asm 没改"；`closed` 保留 bit63 挡
   "掩码写成 imm32 被符号扩展错"（这一类在 M3b-1 真的发生过：`and [rsp+160], 0xfffffdff`
   被 LLVM 的 integrated assembler 当场拒掉，改成 `bts/btr` 带 8 位位号之后才没有歧义）；
   `others_untouched` 挡"写到了隔壁寄存器那一格"——那种故障的现场是某个任务恢复后
   某个寄存器变成别的值，比 IF 位错难查一个数量级。
2. **"关着窗口换进别人"这条完整路径仍然没测**（诚实记账）。它的触发源不是"AP 接入调度器"
   ——AP 上同样没有 tick 就进不了抢占点——而是**任务主动让出/阻塞**（`schedule()`）：
   一个任务在 IF=0 的时候自己放弃 CPU，换进来的人就必须被写成"窗口关着"。
   那条原语在 M4/M5（等待型驱动）时才出现，已按此挂在 BACKLOG，
   `loads_closed` 这两个计数器就是它的验收读数。

位域指令这一处也踩过一次：第一版写 `and qword ptr [rsp + 160], 0xfffffdff`，
LLVM 的 integrated assembler 直接报 `invalid operand for instruction`。
换成 `bts/btr` 带 8 位位号之后既没有歧义也不会写错掩码。

## 负样本：`fault-if-carriage`（判定矩阵第 8 行）

只把 `preempt_point` 里那一行换回"任务自己带 IF"（`if_open = 帧里那一位`），
别的都不动。实测：

```
判定=HANG qemu_rc=-1 用时=60.0s
最后一条串口：[test] t_cpu_ids_agree -> ok
（下一条就是 t_preempt_round_robin，它再也没打出任何一行）
```

也就是说去掉机制之后**不是报红，是整机停摆**——和 M3a 记录的症状同一条形状：
第一个被换入的新任务带着 IF=0 跑，从此没有 tick 能抢占任何人，开窗口的那个上下文永远回不来。
因此这一行的期望判定是 `HANG(rc=-1)`（判定契约里 HANG 本来就是独立一级，§12.3），
并且它在矩阵里单独用较短的超时（60 s）：这一条注定要等到超时。

`python tools/aurora.py test` 当时跑 8 行，实测 8 行全部"符合"；现在矩阵是 9 行
（ADR-023 又加了一行），9 行仍全部"符合"。

## 后果

* `sched::spawn` 不再写 `0x202` 这个魔数；那句"写错就整机卡死"的注释变成了机制说明。
* `with_interrupts` 从"临时开一下 IF"变成"占用本 CPU 的中断窗口"，语义上是个可以嵌套判断的状态。
  今天还不检测重入嵌套（用例里没人套着开），已记 BACKLOG。
* `context_load` 多了第二个参数，签名变化会让"帧布局改了但出口没改"这类错误当场编译不过——
  这是要的：帧偏移是 asm 与 Rust 之间唯一没有类型系统保护的接缝。
* AP 今天不跑调度器（ADR-022 记录降级形状），它打开 IF 时**没有**写进 `CPU_IF`——那张表只服务
  调度器改写异常帧。这条缺口在 `smp` 模块头与 BACKLOG 都挂了账：AP 接入调度器时必须同时接上，
  否则那条 CPU 的换入会全部按"窗口关着"改写。
* 判定矩阵从 7 行变 **9 行**（本 ADR 一行 + ADR-023 的 shootdown 一行），实测 9 行全部"符合"；
  `bench` 的四道门禁仍"符合"（最新一次：P3 min 807/808 → 224,626；P1 min 987/808 → 23,258，
  地板 180；P4 重复性离散度 0.93%）。
* **`if_patch` 拆成 `call` 之后 P1 的 min 看着变高了，但这句话不能写成结论。**
  同一条用例在这段开发里的历次读数：462/534 → 510/686 → 808/987，跨度比"同构建两次的地板"
  （73~180 周期）大得多，也就是说 **min 在不同构建之间本来就不可比**。
  没有做过"同一构建、加/不加这条 `call`"的对照实验，所以这里只登记事实：
  换入路径上多了一条 `call/ret`，而现有数据**不足以**把那段差值归给它。
  要归因就得按 §12.4.1 规则 3 做一次专门的对照，已挂进任务清单（排在 P3/P5 per-CPU 化之后——
  那时这张表本身按 CPU 分开放，读数才第一次可比）。
