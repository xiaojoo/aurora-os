# ADR-179：句柄表与任务表从定长 .bss 改为运行时分配

状态：**已采纳**（2026-11-22，使用者裁决「直接改动架构吧」）

关联：ADR-178（容量基线改为 Linux 对齐）、ADR-063（FrameInfo 影子数组，本 ADR 的模板）、
ADR-075（每 AS 页表）、ADR-065（VA 保留表与 sched 解耦）、ADR-018/026（堆上限 2048）

> 写作纪律：每条结论标「实测」或「推断」。实测指有 run 日志/编译产物为证。

## 背景：ADR-178 撞到的两堵墙

ADR-178 把容量基线改成 Linux 量级，但在两个常量上撞墙（**均实测**）：

### 墙 1：`MAX_HANDLES = 131072` 破坏 IOAPIC 映射

二分实测（每档都跑满一轮，看 `apic handoff ... irt=`）：

| `MAX_HANDLES` | `.bss` 占用 | IOAPIC `irt` | 结果 |
|---|---|---|---|
| 64（基线） | 0 | **24** | PASS |
| 4096 | 0.25 MiB | **24** | 正常 |
| 32768 | 2 MiB | **24** | 正常 |
| **131072** | **8 MiB** | **1** | IOAPIC 读不到，HANG |

`irt=1` 的机制：`ioapic_read(va, 0x01) >> 16` 读到 0 ⇒ `irt_entries = 1` ⇒
`GSI 2 -> RTE 2 超出 I/O APIC 0 的 1 条表项` ⇒ `apic::init failed` ⇒ 无 tick ⇒ HANG。

**根因**：`Table { slots: [Entry; MAX_HANDLES], ... }` 是 `static`，8 MiB 的 `.bss`
把内核镜像布局推到让 `map_device` 的 VA/物理对应关系坏掉。**不是 IOAPIC 本身的问题。**

### 墙 2：`MAX_TASKS = 256` 导致内核栈溢出

实测：Double Fault（`vector=8`）：

    cr2=0xffff80002041cf08   rsp=0xffff80002041cf10
    IOAPIC va = 0xffff80002041f000   （cr2 距它 8440 字节）

栈顶撞到了 `map_device` 分配的 VA 区。

**根因**：`tasks: [Task; MAX_TASKS]` × `MAX_CPUS(8)` ⇒ 2048 个 `Task` 静态数组，
加上 `WORK[MAX_TASKS_TOTAL]`、`FLAGS[MAX_CPUS]` 等，把 `.bss` 撑到挤压栈区。

### 两堵墙是同一个病因

**定长全局 `.bss` 数组**。Linux 不用这种结构：

| | Linux | Aurora（改前） |
|---|---|---|
| 打开的文件 | 每进程 `files_struct`，按需增长 | 全局 64/4096 格定长表 |
| 任务 | `task_struct` 从 slab 分配 | 每 CPU 定长数组 |

**所以「再调大一点」修不了**——调大到某个值必然再撞墙。必须把表本身挪出 `.bss`。

## 决策

### 决策 1：句柄表与任务表改为运行时分配（照 ADR-063 的模板）

`bootstrap_frame_info()`（`mm.rs:3165-3194`）已经给出了完整可用的形状：

    1. phys_alloc(order, MOD_BOOT) 分连续帧
    2. core::mem::forget(frames)   // 永不归还，生命周期=内核
    3. arr = (hhdm + base) as *mut T
    4. st.table.store(hhdm + base, Release)   // 存 HHDM 虚地址
    5. st.table_len = n                       // 存长度

**照抄这五步**，只换类型。这样做的三个好处：

1. **`.bss` 不再按容量增长** ⇒ 两堵墙同时消失；
2. 已有先例、已被 production 路径验证（`frame_info` 跑了整个 M 系列）；
3. 不需要新分配器（`phys_alloc` 已存在），不碰 `LARGE_MAX = 2048` 那条纪律。

### 决策 2：表访问走「HHDM 基址 + 下标」而不是静态切片

改前：`TABLE.lock().slots[i]`（编译期确定地址）
改后：运行时基址解引用（`*mut Table` 从 HHDM 算）

**安全性论证必须写在每处解引用旁**（硬约束 5）：指针来自 bootstrap 分配的连续帧、
长度是 `table_len`、生命周期是整个内核、访问都在既有锁内。

### 决策 3：`unsafe` 计数会上升，必须登记白名单

ADR-160 的 ratchet 要求新增 `unsafe` 进 `docs/security/unsafe-whitelist.toml`，
写明指针来源、地址范围、对齐、生命周期、并发规则、上下文约束、由谁保证不变量。

**这会让 `check-unsafe` 的数字上升**——那是真实代价，不隐藏。

### 决策 4：分配失败要能启动失败，不能静默降级

`bootstrap_*` 返回 `Result`，`main` 收到 `Err` 就走 `boot-invalid`（判定 37）。
**绝不允许**「分配失败就用 0 长度表继续跑」——那会让系统在缺表状态下运行，
症状是随机的句柄/任务丢失，比启动失败难查得多。

### 决策 5：容量仍由 ADR-178 的基线决定

本 ADR 只改「表放哪里」，**不改「表多大」**。容量值的唯一来源仍是
`docs/architecture/capacity-baseline.toml`。两者正交：

    capacity-baseline.toml  决定 MAX_HANDLES = 131072（要多少）
    ADR-179（本文）          决定那 131072 格放在哪（.bss 还是 phys_alloc）

## 影响

1. **两堵墙消失**（推断，待实测）：`.bss` 不再随容量增长。
2. **启动期多两次 `phys_alloc`**：句柄表约 8 MiB、任务表约 200 KiB。
   代价是启动时多占物理内存，收益是 `.bss` 回归可控。
3. **`check-unsafe` 计数上升**——登记后是已知数。
4. **`frame_info` 的 `MOD_BOOT` 归属**照抄：这两张表也归 `MOD_BOOT`、永不归还。
5. 既有 ktest 的判据不变（容量、语义都没变），所以**判定表不该出现新的红**。
   这条是可验证的：改完跑整链，与改前的红/绿集合逐个比。


## 补记一（2026-11-22 同日）：三个「上限」都不存在，全是 `.bss` 布局的症状

正文的「未决 2」曾把三个值写成「实测上限」。**补测之后推翻了那三条**：

| 项 | 正文曾写的「上限」 | 补测结果 |
|---|---|---|
| `MAX_HANDLES` | 4096 | **131072 PASS(33)**，`irt=24`，`base=0xffff800010000000` |
| `MAX_TASKS` | 64 | **256 PASS(33)**，100/100 |
| `MAX_VA_RESERVATIONS` | 256 | **65536 PASS(33)**，`map_hole 往返=true` |

**为什么之前会撞墙**：三个都是同一类——**栈数组按容量线性增长**。

| 位置 | 写法 | 容量大时 |
|---|---|---|
| `revoke_task` / `reset_for_test` | `[0u8; MAX_HANDLES]` | 131072 ⇒ **128 KiB 栈数组** ⇒ Double Fault |
| `kill_process_threads` | `[0usize; MAX_TASKS_TOTAL]` | 256×8=2048 ⇒ **16 KiB 栈数组** ⇒ Double Fault（反汇编可见 `sys_process_kill_core` 连减三次 `subq $0x1000, %rsp`）|

修法：**栈数组一律取小常量 + 边界判断 + 分批判**，不跟着容量走。
  `MAX_REVOKE_VMOS = 64`、`KILL_BATCH = 64`。

**这条纪律值得单独记住**：容量常量出现在 `.bss` 数组里，会推高镜像布局；
出现在**栈数组**里，会直接打穿栈。两种都是「调大反而坏」，但成因完全不同。
前者靠 ADR-179 的运行时分配解决，后者靠「栈数组不许跟容量走」。

### 最终容量（全部实测通过）

| 常量 | 值 | 验证 |
|---|---|---|
| `MAX_PROCESSES` | 32768 | `capacity: 进程=32768 ... ⇒ true` |
| `MAX_ADDR_SPACES` | 32768 | 同上 |
| `MAX_JOBS` | 1024 | 同上 |
| `MAX_HANDLES` | 131072 | `handle: slots ... len=131072` + `irt=24` |
| `MAX_TASKS` / `MAX_TASKS_SUPPORTED` | 256 / 256 | 100/100 |
| `MAX_VA_RESERVATIONS` | 65536 | `map_hole 往返=true` |
| `MAX_LAZY_REGIONS` / `MAX_LAZY_PAGES` | 4096 / 64 | `mmap族 ⇒ true` |
| `EARLY_POOL_PAGES` | 128 | `pool=29`（不再 exhausted）|
| `MAX_REVOKE_VMOS` | 64 | 新增，栈数组上界 |

### 补记二（2026-11-22 同日）：VA 保留项数组也改为运行时分配

补记一确认「三个上限都不存在」之后，`MAX_VA_RESERVATIONS=65536` 仍不稳定（连跑 6 次 0 次通过）。
查下来是**同一个病因的第三个实例**：

    State.va_res: [VaReservation; MAX_VA_RESERVATIONS]   // 65536 x 16 B = 1 MiB

`State` 在 `.bss` 里，1 MiB 的数组又把它推高了——与句柄表的 8 MiB 是同一类。

**修法**：`va_res` 改成 `va_res_ptr: AtomicU64` + `bootstrap_va_res()`，
照句柄表那五步（`phys_alloc_above` → `forget` → HHDM → 存基址）。
访问走 `va_res_slice()`，调用方持 VMM 锁。

**顺带修了一处 O(n) 扫描**：`release_va_locked` 原来逐项查位图（65536 次迭代，持 VMM 锁），
改成**按 word 批扫、跳过全 0 的 word**（实际在用的保留是个位数，迭代数降到约 1）。

### 读数

| 配置 | 连跑 6 次 |
|---|---|
| 65536 + 定长数组 | **PASS=0** |
| 65536 + 运行时分配 | **PASS=5**（另 1 次是既有偶发 `t_q2_workload_slots`）|

引导日志：`va: 保留项数组引导 base=0xffff800010000000 len=65536 pages=256`。

### 这条补记的一般化

**ADR-179 的形状适用于任何「容量常量 × 大元素」的定长数组**：

| 数组 | 容量 | 元素 | `.bss` 增量 |
|---|---|---|---|
| `Table.slots` | 131072 | ~64 B | 8 MiB |
| `State.va_res` | 65536 | 16 B | 1 MiB |

两者都让 IOAPIC 的 `irt` 从 24 读成 1（或让 `State` 推高布局导致别的连带）。
**判断标准**：`容量 × 元素大小` 超过几十 KiB 的定长数组，就该考虑挪出 `.bss`。

## 未决 2 的更正

「`MAX_TASKS` 与 `MAX_TASKS_TOTAL` 的最终值——本 ADR 之后重新二分」→ **已做完**：
`MAX_TASKS=256` 通过。`WORK`/`FLAGS` 仍是静态数组，但 256×8=2048 项只占 16 KiB，不是瓶颈。

## 未决

1. **真正对标 Linux 的 per-process fd 表**——本 ADR 只把全局表挪出 `.bss`，
   没有改成每进程。那是下一步（ADR-180），因为它要动 `proc` 结构与 `dup` 语义。
2. **`MAX_TASKS` 与 `MAX_TASKS_TOTAL` 的最终值**——本 ADR 之后重新二分，
   看能撑到多少（`WORK`/`FLAGS` 仍是静态，可能仍是瓶颈）。
3. **表用 `phys_alloc` 还是将来的 slab 分配器**——后者要新写分配器，
   本轮明确不做（ADR-018 的纪律：不造没调用者的东西）。
