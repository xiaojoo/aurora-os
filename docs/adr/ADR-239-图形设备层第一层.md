# ADR-239：图形设备层第一层（能力探测与格式推导）

状态：**已采纳**（2026-11-23：`t_gpu_mode` 八格全 true，`PASS(33)`）

关联：ADR-208（USB 字节层，同一思路）、ADR-196（驱动注册表）

> 切片 I 第一层。**不写任何寄存器、不做模式设置。**

## 为什么从字节层开始

`display` 现有的两个文件分工明确：

| 文件 | 知道什么 |
|---|---|
| `frame.rs` | 像素怎么落到**一块已映射的显存**（几何、掩码、越界、双缓冲）|
| `fbcon.rs` | 字符怎么变成像素（字形、双宽格、浮窗）|
| **`gpu.rs`（新）** | **哪块显存、什么格式、能力有哪些** |

而 `Frame::init()` 现在直接从 **Limine 启动信息**取帧缓冲 —— 那不是「从设备取」。

与 USB 切片（ADR-208 先做 TRB 字节层）同一个思路：**先让字节层可证，再接硬件。**

## 交付

```rust
pub struct ModeInfo { width, height, pitch, bpp, memory_model }
pub enum ModeError { ZeroSize, ZeroBpp, BppNotByteMultiple, PitchTooSmall, NotRgb }
pub enum GpuKind { Bochs, Cirrus, Qxl, VirtioGpu, UnknownDisplay }
pub fn bochs_mode(xres, yres, bpp) -> ModeInfo
pub const BOCHS_REG_ID/XRES/YRES/BPP, BOCHS_ID_MAGIC
```

## 决策 1：`validate` 的检查顺序有意义

先排除「除零」，再排除「行放不下」，最后排除「格式不支持」。

一个 `bpp=0` 的坏描述不该被报成「内存模型不对」—— **根因优先级**。

## 决策 2：`GpuKind::from_ids` 对未知显示类回 `UnknownDisplay`，不回 `None`

「这是块显卡但我不认识」与「这不是显卡」是两件事：

- 前者要能被**计数**（判据要看见它）；
- 后者直接跳过。

## 决策 3：`pitch` 要自己算

Bochs 的 `XRES` 只是像素宽，**没有 pitch 寄存器**。它的 pitch 是 `xres * bpp/8` 再按 4 字节对齐 ——
这是实现细节，不是协议字段。所以 `bochs_mode` 自己算并交给 `validate` 复核。

## 判据八格（`t_gpu_mode`）

```
gpu: 合法=true 零bpp=true 非8倍=true pitch小=true 非RGB=true bochs=true 识别=true 字节=true ⇒ true
```

## 一个负样本咬不动的教训（**这是本 ADR 最有价值的部分**）

第一版的 `validate` 结尾是：

```rust
let row = self.row_bytes().ok_or(ModeError::ZeroBpp)?;
```

我删掉前面的 `if self.bpp == 0 { return Err(ZeroBpp) }` 做负样本 —— **判据全绿。**

原因：`bpp=0` 会通过 `bpp % 8 != 0`（`0 % 8 == 0`），然后 `row_bytes()` 回 `None`，
`ok_or(ZeroBpp)` **仍然回 `ZeroBpp`**。

**兜底路径掩盖了被删的检查。**

### 修法：把兜底改成不变量

```rust
let row = self
    .row_bytes()
    .expect("bpp 已校验为非 0 且 8 的倍数，row_bytes 必然可算");
```

现在删掉 `bpp == 0` 检查，`expect` 会 panic ⇒ **负样本咬住了**（形式是 HANG）。

## 这条应当推广

> **`ok_or(同一个错误码)` 这种兜底会掩盖前面的显式检查，让负样本咬不动。**
>
> 兜底该用 `expect` 写成**不变量**（「走到这里必然成立」），
> 而不是伪装成某个正常错误分支。

判据的负样本是检验「判据有没有牙齿」的唯一手段 —— 而兜底会让牙齿变假。
