# ADR-085：实时上屏——控制台字节流与内核日志共用同一个镜像环，画面证人改用配对对照

状态：已采纳（2026-11-13，S6d 实测 / BACKLOG §247 / build/s6d-live-check.py 与 run 序列）
关联：ADR-083（显示子系统第一刀；决策 7 的一次性冻结闸门、决策 8 的确定性字形）、
ADR-082（S5c shell 作为 init、S5d 常驻停机）、ADR-084（键盘并入 21 号）、BACKLOG §245/§246

> 写作纪律：已采纳 ADR 与有测试证据的事实优先于目标设计；每条结论标「实测」或「推断」。

## 背景

S6c 之后，"屏幕上看到键入的内容"这一格被明确记为**没做**（§246 第八节）。当时给了两个理由，
其中一个错了，本轮实测纠正：

1. `fbcon` 只在 init 窗口结束那一刻画一次屏（ADR-083 决策 7 的一次性闸门）——**这条是真的**；
2. 我以为"shell 的输出经 `Sink` 旁挂进环，所以内容已经在环里、只缺重画"——**这条是错的**：
   shell 走 20 号 `console_write`，落到 `serial::write_bytes`，而那条路**根本不旁挂**
   （旁挂点只有 `Sink::write_str` 与 `line()` 的换行）。所以即便当时就重画，画面上也不会有
   shell 的一个字。⇒ **镜像环的语义本身要改**，这是接口语义变更，所以有本 ADR。

另一个背景是量具事实：`fbcon::glyph()` 的图样只由码点 `mod 5` 决定——本机算过，
95 个可打印 ASCII 只落在 **5 种不同图样**上（实测）。所以"从像素反解出文本"这条最容易想到的
画面证人**根本承载力不足**（每格约 2.3 bit），不能假装它读得出字。

## 决策

1. **一个环，两个来源**：`serial::write_bytes` 在 `framebuffer` 特性下把**真写出去的那一截**
   （`&bytes[..done]`）旁挂进同一个 8 KiB 环。于是画面的语义从"内核日志的镜像"变成
   **"控制台上看到的东西的镜像"**（日志经 `Sink`，用户程序输出经 `write_bytes`）。
   新入口 `serial::mirror_bytes(&[u8])`；`mirror_note(&str)` 改成它的包装，不再自己循环。
   **为什么按字节而不是转字符串**：20 号交来的是一段字节，硬转 `&str` 会让非 UTF-8 的写
   变成"悄悄少几个字节"——那种丢法没有任何读数。**为什么只挂 `done`**：串口因背压少写的字节
   不该在画面上假装存在。
2. **实时重画 = 把一发长等待拆成有界轮询，不新开等待语义**：`fbcon-live` 档在 init 的等待处
   每轮 `wait_for_task(gidx, window_cycles(16))`，没等到收工就整窗重画一次；总上界仍是
   `console-probe` 的那 1000 窗口（非常驻档仍是 32）。
   **不动 `sched`**（硬约束①）：用的还是同一个有界等待，形状与 `park_until_init_exits` 一致。
   拿不到帧缓冲或几何放不下 ⇒ **退回一次性等待并在串口上说明**（特性退化必须可见）。
3. **`redraw_window` 与 `drain_and_draw` 分工**：前者可重复调用、按行号直写、**一个字都不打印**、
   没被内容占满的行一律刷空；后者保留 §245 的滚动语义与串口行。
   **不合并成一个带开关的函数**：开关会让"每轮打一行"这种错误在下一片重新变得可能，
   而"每轮打一行"会把 §245 按行序读的判据搅掉。
4. **窗口行是预算不是容量**：`min(正文行, 24)`。一行是 160 格 × 64 次设备写，画满 98 行会把一轮
   拉到上百毫秒；实时重画要的只是"取样时刻任意"。`Frame::init()` 每次调用都真映射一遍 MMIO ⇒
   **映射只做一次**，不在轮询里反复映射（那既贵又要碰 VMM 锁）。
5. **画面证人的形状：配对对照 + 定向图样匹配，不做 OCR**。同一次跑里取两次 dump：
   键入前（dump1）必须**找不到** `echo` 那串字节的图样，键入并等到串口应答后（dump2）必须
   **找到**它；再加一条"从没打过的串"作为反空转格。两条**正控制**分别用 shell 横幅
   （走 `write_bytes`）与一行内核日志（走 `Sink`）——它们不同源，所以能区分
   "什么都没画"与"控制台字节没进环"这两种红。
6. **既有像素判据不动，但只复测到能复测的那一格**：`handles,resident-init,framebuffer,fbcon-mirror`
   那一跑重测**仍 PASS**（实测 `旁挂=149788 现存=8192 窗口行数=71 画上=7`，末行 == 最后一条日志正文
   不符=0/1344）——注意**环里的内容确实变宽了**（控制台字节也进来了），所以 `窗口行数` 从 §245 的
   数变成了 71，而那条判据读的是"最后一条日志正文"，它自己仍在冻结标记之前 ⇒ 判据成立。
   `fbcon-live` 是独立一档，不并进 `framebuffer`——并进会让 §242"滚动恰好一次"与 §245 的判据
   一起失去确定的取样时刻。
   **`framebuffer` 单档（hello 作 init）那一格本轮量不出来**：见未决 6，那一档 5/5 停在
   `init-user:` 之后、第一条 `fbcon:` 之前，且**在已提交的 HEAD 码态同样停** ⇒ 不是本片引入，
   但本片也拿不到它的答案。

## 备选方案

- **只做重画、不改环**：即 §246 记的那条错误前提。实测画面上永远不会有 shell 的一个字。
- **像素→文本反解（OCR）**：见背景里的 5 图样实测——承载力不足，反解出来的字符串没有意义。
  要它成立必须先有可读字体（见未决 1），而且那时字体资产要两份实现，漂移风险按 §245 的教训要配
  自己的对账。
- **给 20 号单独开一个"用户输出环"**：语义上把画面拆成两本账（日志与用户输出各一个窗口），
  而屏幕上它们本来就是同一段字节流；两本账只会让"画面上的这一行到底来自谁"重新变得要猜。
- **在 `Sink::write_str` 里判断调用者**：那要求 `Sink` 知道 20 号的存在，方向反了（diagnostics
  不该认识 capability 的入口）。
- **每轮画完打一行串口**：会把 §245 的行序判据搅掉，而且 62 行的日志把"实时"变成"刷屏"。

## 影响

正面：画面第一次成为**交互的**证人；`console_read`（S6c）+ `console_write` + 实时画面构成
一条完整的"打进去→答出来→看得见"的路径。
负面/代价：+1 特性 `fbcon-live`；镜像环的语义变宽（同名函数 `mirror_*` 现在含用户输出，
读日志的判据要按这个口径重读）；每轮最多 24 行的设备写落在 init 等待里（实测一整场问答
17 轮，串口字节与 S6c 那一跑同量级）。
基线影响：`known_scc` 与 `ring_edge_sites` 不变（`display` 仍在环外）；unsafe 白名单不变
（新代码零 unsafe）；`display.public_api` 增 `fbcon::redraw_window`。

## 验收与负样本

判据（`build/s6d-live-check.py`，features=`fbcon-live,ps2-kbd,resident-init,console-probe`）：
实测读数 `正控制一（shell 横幅）=(22,0)`、`正控制二（内核日志行）=(20,0)`、
`TOKEN 图样 dump1=None / dump2=(21,7)`、`反空转格=None`、串口 `kb7kb7kb7` 命中、`bye` 命中、
`resident-init: init 已收工`、`轮询=17 收工=init 自己退出`、`kbd: 字节=39 入环=20 break=19 派发=40`、
`qemu_rc=33` ⇒ 判定=PASS。

负样本（三条各自证红）：
- **N4 不调用重画**：两条正控制**都落空**（画面什么都没画），`dump2 含 TOKEN` 红。
- **N5 控制台的写出不进环**：正控制二**仍在** `(22,0)`（内核日志照常画）而正控制一落空、
  `dump2 含 TOKEN` 红 ⇒ 这一格把"没重画"与"字节没进环"分开。
- **N6 窗口取最老的 N 行而不是最新的 N 行**：`dump2 含 TOKEN` 红。
  **要说清**：N6 与 N4 在两条正控制上症状相同（都落空），"画了最老的行"这一格本片没有单独取证
  ⇒ N6 只证到"最新窗口"这个选择是吃重的，没证到它画了什么。

还原的证人：三处变异锚点逐字命中（`原文命中=1 / 变异残留=0`）+ 判据读数与变异前逐字一致 +
同一变体连续两次构建同为 `2b42d4fea1f2`。**变异前那一跑的 `989ea4a57dab` 不复现（差 56 字节），
不归因**：各档共用同一条 `kernel_path`，中间夹过默认档与 `framebuffer` 档的构建，增量缓存能挪动
debug 信息（§236 记过"产物已被后续构建覆盖 ⇒ 无法再核"）。
⇒ **口径更正**：ELF 哈希只在"同一变体连续两次构建"之间当证人；跨变体穿插时它不够，
必须配文本锚点与读数一致（本轮就是这么抓出我自己那条前提错误的）。

## 迁移与回滚

无接口迁移：20 号的参数、返回、权限都不变，只是它的字节现在也会被旁挂。
回滚 = 去掉 `fbcon-live`（重画与轮询循环整体消失）；若连字节流旁挂也要退，去掉
`write_bytes` 里那一行 `mirror_bytes` ⇒ 画面退回"只镜像内核日志"（§245 的语义）。
不可回滚的部分：本 ADR 把 §246 里"键入内容上屏"那条前提错误记成了纠正记录，不要覆盖原文。

## 未决

1. **可读字体**：`glyph()` 只有 5 种图样 ⇒ 它不只是"不好看"，而是**承载不了信息**（每格约 2.3 bit）。
   要"屏幕可读"必须换字形表，并配字体资产的两侧对账。这条优先级比 S6b 时更高。
2. **终端回显**：~~画面上看不到那个键本身~~ —— **这条写错了，S6e 实测更正**：
   `user/shell` 的读循环里有 `let echo = [b]; con_write(console, &echo);`，
   键入的每个字节都**逐字回显**（S6e 从像素读回的一行就是 `> echo kb7kb7kb7`）。
   仍未做的是**阻塞读**（21 号一直是非阻塞轮询，shell 在忙等）。
3. **`fbcon-live` 的 durable 矩阵行**：判据活在一次性夹具里；仍受 `tools/aurora.py:3037`
   `run_serial_rx` 缺必填实参那笔旧欠阻碍。
4. **窗口行 24 这个数字没做过容量敏感性实测**（为什么不是 8 或 48——只算过设备写成本，
   没量过轮询延迟与串口字节的影响）。
6. **`framebuffer` 单档 + hello 作 init ⇒ 停在 fbcon tail 之前**（本轮实测 5/5：
   `run --features framebuffer` 与 `build/s6b-freeze-check.py` 都是 885 行、最后一行
   `init-user: 产品路径起 ring3 … 等待收工=false`，ktests 已 82/82；420 s 的预算也不出来 ⇒ 不是慢）。
   A/B 已经做到的三格：① **已提交的 HEAD（S6c）码态同样停**（elf `82b51d721afd`）⇒ 非本片引入；
   ② `framebuffer,handles` 6.7 s PASS；③ 默认档与 `handles` 档 PASS。
   ⇒ 症状范围是"**画面上屏 × 一个只会自旋的 ring3 init**"这一格，不是"画面上屏"本身。
   **引入点未核**：§241/§242 的取证跑用的是 `handles,resident-init,framebuffer`，
   这条 `framebuffer` 单档的形状是不是曾经跑通过，本轮没有证据，不编。
   形状与 §231 那次"IF=0 ∧ HLT=0 ∧ RIP 在用户半区"同族——**这是推断，没做现场取证**。
7. 画面上"两条正控制所在行"的**行号会随日志滚动而变**（本轮 (22,0)/(20,0) 是这一次跑的现场读数，
   不是契约）；要固化成矩阵行得先有一个与行号无关的判据形状。
