# ADR-259：块层真异步、DMA 租约与用户进程完成通知

状态：**已采纳**（2026-11-26，使用者裁决 C）。关联：ADR-110/194/214/215/251、
ADR-189（容量）、BACKLOG §589。

## 背景

`Block::read_sectors/write_sectors` 仍同步；AHCI/virtio/NVMe 都在提交后等待完成。
ADR-251 的 `submit/drain` 只是延迟完成队列，不拥有数据缓冲，回调仍是核内函数指针；
`panic=abort` 下回调 panic 会终止整机。现有 callback 只有测试调用点，没有产品消费者。

## 决定

1. `block_io` 是拥有请求状态机的深模块；驱动是适配器，只负责本设备的 DMA 租约、
   提交、回收、取消和缓冲复制。新增 `AsyncBlock` 接缝，不改变既有 `Block` 同步接口。
2. 核内请求状态机只暴露提交、完成、取消与租约领取四类事实；驱动适配器另提供
   稳定的 `AdapterId`、租约分配/复制与 submit/reap/cancel/release。`RequestId` 含适配器、
   目标与序号；完成逐 token 恰好一次，带已落地扇区数与原始 `BlockError`。提交拒绝与在途
   失败分开。`AdapterId` 绑定请求、完成与租约领取；驱动 `local_id` 使用单调 u64 且不复用；
   写缓冲长度必须严格等于 `sectors × 512`。
3. DMA 租约由具体驱动拥有，因为 AHCI/virtio/NVMe 的缓冲约束不同。租约在设备仍可能
   写入时不得释放或复用；取消在发射前可撤，发射后只撤通知，超时/复位必须确认设备
   静止后才能还租约。`block_io` 持有租约状态，驱动不得自行提前归还。完成取出时返回
   不可复制的 `LeaseClaim`，复制/释放都消费或借用该 claim，旧完成值不能在槽复用后双释放。
   请求带绝对 deadline；超时先向驱动取消，只有驱动确认 `Cancelled` 才入 `NotSettled` 完成，
   否则保留租约并置 `TimedOut`；迟到真实完成按原结果交付并计 `late`。
4. `RANK_BLOCK_DRIVER=1` 的门闩串行全部驱动租约访问与 submit/reap/cancel；顺序为
   门闩(1) → 驱动锁 → 块队列(37)。所有公开入口拒绝 ISR；`poll` 处理适配器返回的所有
   target；`queue_clear` 在仍有在途请求时不重置异步序号或台账。
5. 完成队列与通知队列分离。核内完成队列把 `Completion + lease` 交给请求消费者；消费者
   复制数据后才释放租约。用户通知队列只镜像定长 token/result 记录，不传内核指针，也不拥有
   DMA 租约；通知处理失败不改变请求结果或缓冲生命周期。
6. 用户通知 broker 使用独立 ring3 进程与一页共享 VMO。端点包含 Proc 代号/世代、VMO 代号/
   世代、子 AS 映射 VA 与环布局；安装时核验活性。记录含 magic/version、单调 seq、token、
   target、result、sectors_done 与定长诊断载荷。producer/consumed 用 Acquire/Release 发布。
7. 未确认记录由核内账本保留；同一端点慢消费时不得覆盖，替换端点后按 seq 重投。进程死亡
   只使旧端点失效，不回收别人的在途请求；监督者重建进程与 VMO 后安装新端点。回调进程
   panic 通过 3 号正常退出，由监督者观测，不进入内核 panic handler。
8. 第一轮不新增 syscall：核内编排创建回调进程并传共享 VMO，`block_io` 经核内接口安装端点。
   若将来需要用户自助注册，再单独裁决 78+ 号段。
9. ADR-215 的旧函数指针回调只保留给既有测试，新产品路径不经它；测试迁移完成后删除，
   不把“旧测试入口仍会 abort”写成新接口的生存保证。

## 切片顺序

1. `AsyncBlock` + fake 适配器：租约、提交、完成、取消、超时、队列满、恰好一次与失败不提交。
2. virtio-blk 单请求真异步：提交后立即返回，显式 reap 完成；保留同步 `Block` 路径。
3. AHCI：每请求命令槽/PRP，顶半只置完成标志，deferred reap；复位前排空在途。
4. NVMe：先交付单槽提交/CQE 回收（本节第 4 片）；队列深度内多 outstanding、禁用与致命态排空仍未实现，不并入本片结论。
5. 用户通知 broker + `aurora-user-shell` 第二 bin + 进程死亡/端点替换/重投/panic 负样本。
6. 同步 `read_checked` 改为异步核心的等待包装，产品语义不变；跑完整矩阵。

## 验收

- fake：提交不执行设备；reap 前无完成；取消发射前有效；租约在完成前不释放；满池拒绝。
- 真驱动：同一 ELF 下 submit 立即返回，reap 后数据/错误/扇区数与同步路径一致。
- 用户进程：收到定长记录后故意 panic，仅该 Proc 退出，核内完成队列与租约台账不损坏；
  替换端点后未确认 seq 重投，已确认 seq 不重复。
- 负样本：提前还租约、重复完成、丢 ctx/token、覆盖未确认记录、端点 gen 不校验、
  把用户 panic 当内核 panic，分别必须红。
- 真机未验证；AOCI MCP 不可用，索引未更新。

## NVMe 多 outstanding 与排空补记

- DMA 环扩为 16 页：4 个队列页 + 8 个单扇区数据槽。`async_reap` 先等一条真实 CQE，
  再非阻塞排空已发布项，按 CID 找槽，完成顺序可与提交顺序不同。
- `async_drain` 先收完在途 CQE，再删除 I/O SQ/CQ，最后禁用控制器；缺完成项的租约保留。
  `async_recover` 要求全部租约已归还且 CFS=0，重写 AQA/ASQ/ACQ、清零 Admin 环、重新使能，
  再清零并重建 I/O 队列。重复恢复实测必须重写 Admin 基址，只写 `CC.EN` 会第二次超时。
- `run-17981` NVMe **100/100 PASS**：八请求单次回收 8/8、第九租约拒、数据逐槽正确；
  禁用排空 `completed=2/outstanding=0/queues_deleted=true`，恢复后读成功；软件致命态同样排空，
  CFS 未清时拒恢复，清后恢复成功；Reserved 租约存在时拒恢复。
- `run-17982` 每次只交一条完成红 `单次回收=false`；`run-17983` 不禁用红 `disabled=false`；
