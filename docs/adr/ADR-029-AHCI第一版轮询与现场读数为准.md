# ADR-029: AHCI 第一版只读、只轮询，寄存器冲突以本机现场读数为准

状态：已采纳（2026-11-05，M5-b 实测）
关联：手册 §8.7.1（先把 class 解码表钉住）§8.7.2（存储入口）§8.2（驱动错误不打死系统）§8.3（MMIO 访问）§6.7（资源台账）§12.3（每道门禁各有负样本）、ADR-026（按架构偏移声明字段 + 取证读位置）、BACKLOG 的 M5-a/M5-b

## 背景

M5-a 把 PCI 枚举立起来之后，存储入口就是这台机器上的 `0000:1f.2 = 8086:2922`（ICH9 AHCI）。
写第一版驱动时最先撞到的不是代码，是**我脑子里那张寄存器表**：

| 我以为 | 实测/权威出处 | 怎么被撞出来的 |
| --- | --- | --- |
| H2D 寄存器 FIS 的类型是 `0x34` | `0x27` 才是 H2D，`0x34` 是 **D2H** | Linux `libata-sata.c` 写 `fis[0]=0x27`；QEMU `ahci.c` 收到不是 `0x27` 就**静默丢命令** |
| 端口块从 `0x400` 开始 | `0x100 + 0x80*n`（0.9x 时代才是 0x400） | 写 `0x418` 读回全 0；写 `0x118` 读回 `0x4010`（FRE+FR 同时亮） |
| `PxCMD` 在端口内偏移 `0x14` | `0x18`（`0x14` 是 `PxIE`，`0x10` 是 `PxIS`） | 同上 |
| 命令表头 DW0 低 8 位是标志、`5<<8` 是 FIS 长 | CFL 在 **bits[4:0]**，`5<<8` 会把 bit8 的 `R` 置起来 | QEMU 校验 `2 ≤ CFL ≤ 16`，把 `CFL=0` 的命令丢掉 |
| PRDBC（已搬字节数）在表头 DW1 的 bits 31:16 | 本机 QEMU 报在**低 16 位**（`0x00000200` = 512） | 串口：`表头DW1=0x00000200`，而数据确实到位（哈希与宿主机逐位相同） |
| 设备会把 D2H 写回命令表的 CFIS 区 | 本机 QEMU **不写回**，那 64 字节留着驱动自己写的 H2D | 串口：`表内FIS=0xe000000100258027` 的第 5 字节 = 我们写的 LBA |
| `HR` 之后 `PxCMD` 回复位值 0 | 挂着设备的口读回 `0x6`（`SUD|POD`） | 判据第一版写"整寄存器等于 0"，当场红 |

五条里有四条会表现成"命令发出去了但什么都没回来"。这类现场最难归因，因为它既不像崩溃也不像报错。
所以这一版的形状由三条决定，而不是由我把表抄对决定。

## 决定

### 1. 只读、只轮询、不认领中断

`PxIE` 保持复位值 0、`GHC.IE` 不置，完成判据是 `PxCI` 自己落 + `PxTFD` 的 BSY/DRQ 落定。
理由不是"轮询更简单"：中断认领（MSI/MSI-X）今天还没做，把两件事做在一起，
红了就说不清是传输坏了还是中断没接上。§8.2 要的"驱动的错误不打死系统"这一版就能成立——
所有失败路径都是 `Err`，用例读成一格红然后继续跑。

### 2. 出处三处，冲突以现场为准，并把冲突本身记下来

规范（Intel AHCI 1.3.1）+ Linux `drivers/ata/ahci.h`/`libata-sata.c` + **本机 QEMU 11.1.0 的
`hw/ide/ahci.c`**（它就是我要驱动的那台设备）。前两处给字段位置与命名，第三处给"这台设备真的
怎么处理这一格"。上面表格里最后三条就是三处不一致的地方：**代码按现场写，判据不引用规范说了算**。
`PxCMD` 的复位判据因此只咬一件事——"我写进去的那一位被 `HR` 清掉了"，不咬整寄存器等于 0。

### 3. 判据分三层，设备自报的计数格不进判据

1. **位级自证**（不需要相信任何表）：`GHC.AE` 置起读回；`HR` 自清；往端口 0 写 `FRE` 必须读回
   `FRE+FR`，`HR` 之后 `FRE` 必须没；`ST→CR`。这一层一次验住 GHC 的偏移、HR 的位、端口块基址、
   `PxCMD` 的偏移、`FRE/FR/ST/CR` 的位。
   另外 `AE` 的证法在这台机器上换过：`CAP.SAM=1` 意味着 `AE` 复位值就是 1 且只读
   （QEMU 把 `GHC` 的写掩成 `0x3|AE`），所以"先清再置"这种证法不成立——判据改成
   "置得起 + `SAM` 读回来解释得清它为什么只读"。
2. **两台仪器**：端口数 = `PI` 位图 **等于** `CAP.NP+1`（字段位置核过才敢互证，
   BACKLOG ㉑ 那一课的收尾）；签名 = 端口侧 `PxSIG(0x24)` **等于** `FRE` 打开时设备写进
   本口接收区 `+0x40` 那条 D2H 的分类字段；完成状态 = `PxTFD` 低字节 **等于** 那条 D2H 的字节 2。
   `CAP[23:16]` 这一格仍然只打印不判：`NP` 在 bits[4:0]（0 基），把它当端口数会读出 21 个端口。
3. **内容对账**（判据在核外）：内核只报数（`ahci: 读 lba=… 哈希=0x…`），
   `tools/aurora.py` 的 `check_disk_content` 用**同一份 FNV-1a** 对宿主机的 `build/aurora.img`
   算一遍并逐条比。这条的负样本是 `--features fault-ahci-lba`：只把第二次读的 **LBA 标签**打成
   第一次的，读的东西不动 ⇒ 内核自判的每一格（MBR 签名、`EFI PART`、两次哈希不同）照样全绿，
   只有宿主机那台仪器叫 ⇒ 证明的是尺子能分辨，不是驱动能分辨。
   它走红判定契约里**新的一级** `CONTENT-MISMATCH`（rc 仍是 33），不并成 `FAIL`：
   `FAIL` 的成因在串口里，这一级的成因在核外，混起来就没法回答"到底是内核说的还是我们说的"。

### 4. DMA 结构：一段连续物理内存 + UC 别名，不进全局堆

`phys_alloc(order=2)` 一次拿 4 页（命令列表 1 KiB / 命令表 / 每端口 256 字节的接收 FIS 区 /
数据缓冲），四片的 1024/128/256 字节对齐要求由偏移本身满足——不必四次分配去赌对齐。
映射走 `PageFlags::DEVICE`（PCD ⇒ UC）而不是 HHDM 的 WB 别名：**设备写完我们立刻读，
拿到缓存里的旧值会被读成"没搬回来"**，UC 就不欠这笔账（真机上同理成立）。
这正是 BACKLOG 里"大连续缓冲走 `phys_alloc` + 临时映射，不进全局堆"那条的第一次兑现
（堆的单次上限 2048 字节会当场打死任何"按块开缓冲"的写法）。

**每端口必须有自己的接收 FIS 区**：第一版所有口共用一格，于是"这条口有没有设备"实际变成了
"最后起的那条口有没有设备"——后起的会把前一条的 D2H 盖掉。现在按 `+0x100*num` 切，
端口数超过 16（一页 ÷ 256）直接报 `TooManyPorts`，是**可见的容量失败**，不是静默截断。

### 5. 数据缓冲每次发射前填 `0xEE` 而不是清零

"DMA 一个字节都没搬"和"搬回来一堆 0"必须分得开。但**哨兵覆盖率不能当判据**：
保护 MBR 里 `0xEE` 只出现在一个位置——分区表项的类型字节（`0x1C2`，GPT 的要求），
而那次读是成功的（哈希与宿主机逐位相同），`untouched` 却报 1。
所以它只在日志里当辅助取证，真判据是位置敏感的内容见证：`0x1BE == 0x00`、`0x1C2 == 0xEE`、
`0x1FE..0x1FF == 0x55AA`、LBA 1 的头 8 字节 == `EFI PART`、两次读的哈希互不相同。
（第一版我拿"前 16 个字节"凑过 `0xEE`，读的是代码区，当场假红。）

## 没做到的（都记进 BACKLOG）

1. **48 位字段的高位没有任何判据**：这条盘只有 131072 个扇区、一次只读 1 个，
   所以 FIS 字节 8/9/10（LBA 31:24/39:32/47:40）与字节 13（扇区数高字节）全部写 0 也判不出来。
   **这一格本轮就靠这个空档藏过一次真缺陷**：第一版 LBA 高位按 `>>32/>>40/>>48` 写，
   规范是 `>>24/>>32/>>40`（整段地址搬错一格），而这台机器的任何判据都读不出来。
   现在按规范改对了，但"改对了"本身仍然没有判据。
   字段位置本身三处出处一致（规范 §4.2.3.2 的图、Linux `ata_tf_to_fis`、QEMU
   `ahci_init_move_sglist`）：字节 8/9/10 = LBA 31:24/39:32/47:40，字节 12/13 = 扇区数低/高。
   缺的不是"出处"，是**判据覆盖**。补齐的配方两步（各自独立）：
   ① 挂一个大于 128 GiB 的稀疏裸盘，读 `LBA = 2^28 + 1` 一个扇区并与宿主机哈希对账
   （只有字节 8 写对才可能读对内容）；② 一次读 256 个扇区（128 KiB，一条 PRD 就够），
   扇区数高字节必须参与寻址，否则设备搬 0 或按"0 = 65536"搬 32 MiB。
   —— **这两步都已在 M5-c①② 落地**：裸盘那步换成了 qcow2（`truncate` 在这台 NTFS 上不稀疏，
   见 BACKLOG ㉝），字节 8 现在由 `KT_AHCI_HIGH_LBA` 钉住，扇区数由 257 扇区那次同长度对读钉住。
   **仍然没有判据的只剩字节 9/10**（LBA 47:32）——那要一块 2 TiB 以上的盘。
   另外**扇区数那一格当时被一条选错的判据证成了"证不出来"**：我把 `count` 先写在字节 12/13（规范/Linux 的位置）、
   后改成字节 3/11（NCQ 那条布局），两次一次 1 扇区的读**都全绿**——因为 QEMU 用 PRDT 的
   字节数封顶了这次传输，与扇区数无关。所以现在的 12/13 是**出处定的，不是现场定的**；
   把它变成现场结论的正是上面那步"一次读 256 扇区"。这一条也是一次自我提醒：
   **同一个读数在两种互斥写法下都绿，就说明这把尺子根本没在量这件事。**
2. ~~只有读~~ **M5-c③ 已打通写方向**（`WRITE DMA EXT`=0x35 + DW0 的 W 位 + 回读逐字节比对 +
   不覆盖判据 + 宿主机 `qemu-io` 对账）。**FLUSH 仍没有**：`FLUSH CACHE EXT`(0xEA) 在 QEMU 的
   DMA 路径上是空的 case（只有旧的 0xE7 实现了），拿它做判据只会得到假绿 ⇒ 真机之前不写它。
3. ~~错误恢复没有~~ **M5-d 交付了分类与状态机**：卡住类 ⇒ `Resetting`（重新起端口，成功就继续），
   干净错误（`ERR`/`ABRT`）⇒ 只计数不抖控制器，超过按口累计的 3 次预算 ⇒ `Quarantined`
   （此后命令一个寄存器都不碰）。**仍然没有的**：`CLO`（本机 QEMU 不理这一位，`PxCMD` 里没有
   代码读它）、freeze、COMRESET（`PxSCTL.DET`）、`PxSERR.DIAG.X`(bit26) 的清法。
   也就是说"重置"现在只是**重新起软件引擎**，链路层面的复位还没做。
4. 活动寄存器（`PxSACT`）、NCQ、多个未完成命令没有；只用第 0 槽。
5. `MMIO 写必须 4 字节对齐`：QEMU 直接忽略非对齐写，所以驱动只用 `write32`（`hw.rs` 也只给了这个）。
6. 环形结构与设备窗口常驻不回收（与内核同寿命），这是**有意的**，但意味着没有"设备拔出/驱动卸载"这条路径。

## M5-c 补：把两处"只有出处"的字段变成现场结论，以及三条我自己写的死判据

上面"没做到的"第 1 项（48 位字段的高位）已经在同一轮里补掉，用的是两条新判据：

1. **扇区数 12/13**：一次 **257 个扇区**的读（131584 字节）。判据不是"命令有没有完成"——
   实测负样本 `fault-ahci-count-hi`（把高字节挪到字节 11）之后 QEMU 照样清 `PxCI`、
   状态报 `0x50`、只是**少搬** 131072 字节。判据改成**同长度对读**：长读的最后一个扇区必须与
   单独读那一个扇区逐字节相同。这条不需要阈值、也不需要"内容应当是什么"的先验。
2. **LBA 31:24（字节 8）**：这块 64 MiB 的盘最大 LBA 是 `0x1FFFF`，那一格恒为 0，
   所以**任何本机判据都碰不到它**——我第一版就把它按 `>>32` 写过而全绿。补法是挂第二块盘：
   130 GiB 的 qcow2（文件 199 KB），宿主机在 `LBA = 2^28` 写 512 字节 `0xA5`，
   内核读那一格要求"不等于 `0xA5` 的字节数 = 0"，并用同一块盘的 LBA 0（全零）做控制组。
   负样本 `fault-ahci-highlba` 把这个字节改回 `>>32` ⇒ 非A5=512、两次不同=false ⇒ FAIL(35)。

三条**我自己写的、看起来像判据实际抓不到东西**的东西，全部在这一轮里被当场发现——记下来是因为
它们共同的形状是"读数是绿的，但那条断言根本没在测量它声称测量的东西"：

| 死判据 | 为什么抓不到 | 发现方式 |
| --- | --- | --- |
| 宿主机对账里 `if lba in by_lba` | `lba` 是字符串、字典键是 int ⇒ 恒为假，"同一 LBA 报出两个哈希"从没跑过 | 加第二条长读时同一 LBA 出现两次却没报冲突，觉得不对 |
| "长读的哈希 ≠ 短读的哈希" | 少搬 131072 字节时两条本来就不等 ⇒ 这条对"搬没搬满"完全不敏感 | 注入 `fault-ahci-count-hi`：`长读更宽=true` 而尾巴是哨兵 |
| `copy_out` 与 `data_at` 两套坐标 | 一个从环形基址起算、一个从数据缓冲起算 ⇒ 同长度对读恒不相等，看起来像驱动坏了 | 正常构建里 `尾扇区一致=false` 而两次哈希都是对的 |

容量关系也在这轮落定：一次传输的上限 = 数据缓冲大小（256 KiB 环形结构里剩 232 KiB ⇒
`MAX_SECTORS = 464`），一条 PRD 的字段上限是 23 位 = 8 MiB − 1 ⇒ 块层将来必须会拆多条 PRD。
判定矩阵因此从 11 行到 **14 行**；`do_test` 的不符项现在**自带成因**（打印那一跑的
`-> fail` / `[fatal]` 行），因为串口会被下一次启动覆盖——这一轮就有一次红过却拿不到成因。

工具侧一条硬教训：**这台机器的 NTFS 上 `truncate(130 GiB)` 不是稀疏的**（实测占用 133120 MiB），
要造"大到能碰 LBA 高位"的盘必须用 qcow2。当场删掉了探针文件，剩余空间回到 476.3 GiB。

### M5-c③ 又添两条"以现场为准"

| 项 | 规范/源码的说法 | 本机实测 | 后果 |
| --- | --- | --- | --- |
| DW0 的 W 位（bit6） | HBA 用它判断 PRDT 的方向，QEMU 的 `ahci_populate_sglist` 只在"没置 W"时校验 `bytes == count*512` | 不置 W 位，写**照样成功**、宿主机照样读到图案（方向实际由命令字节 `0x35` 决定） | W 位在本机**不能当判据**。矩阵里那条负样本因此改名成"丢 W 位本机不可见"并按实测期望 PASS——它是记录，真机必须重测 |
| 表头 DW1 = PRDBC（bits 31:16） | 设备自报已搬字节数 | 本机把同一个数报在**低位**：1 扇区 `0x200`、8 扇区写 `0x1000`、257 扇区读 `0x20200` | 位置都不对，更不判它；我上一轮在此写下的"QEMU 不累计这一格"是拿一次 `0` 读数下的错结论，已改 |

还有一条**判据自身**的教训（同一类第四次）：写用例第 3 格原本是"第 1 扇区与第 8 扇区的首字节必须不同"，
而图案 `(i*7 + lba) & 0xFF` 以 256 字节为周期、扇区间距 512 字节 ⇒ 两个扇区首字节天然相同（实测都是 `0x3c`），
一次正确的写被自己的判据判成失败。它想抓的"只写了一个扇区"其实已被第 2 格的逐字节比对覆盖，
于是换成有真实咬合的**不覆盖判据**（在下一个 LBA 再写一次，回读第一段仍要逐字节等于图案），
并配 `fault-ahci-write-partial` 证明它会红。

### M5-d 又添三条"以现场为准"，其中一条改的是判据本身

| 项 | 我以为 | 本机实测 | 后果 |
| --- | --- | --- | --- |
| 越界读是不是错误 | 读一个远超盘容量的 LBA 会带 `ERR` 回来，正好当"干净错误"那一格 | **连错误都不报**：命令正常完成、`PxTFD` 干净、内容照样返回 | "命令成功"不能当"地址有效"用 ⇒ 块层必须自己知道容量（已记 BACKLOG ㉞） |
| 干净错误长什么样 | 非法命令码会以 `ERR` 完成，而我原来的完成判据是"等 `PxCI` 落下" | `tfd=0x0441`（状态 `0x41` = READY\|ERR、错误 `0x04`），**而 `PxCI` 恒为 1、一个字节都没搬**（`DW1=0`、哨兵剩 512）：本机 `ahci_clear_cmd_issue` 只在 `!ERR && !BSY && !DRQ` 时才释放命令槽 | 只看 `PxCI` 的轮询把"设备报了个错"读成"设备卡死"⇒ 每条错误命令抖一次控制器（实测 `resets` 从第一格就开始涨）。判据改成两条并联：`PxCI` 落下 **或** 接收区出现一条**新的**带 `ERR` 的 D2H（发射前把那条 D2H 的类型字节盖成设备永远不写的 `0`，"新的"才读得出来） |
| 恢复结束时端口是干净的 | 起端口成功 ⇒ 下一条命令读到的就是它自己的回执 | 一次独立跑里，撤销隔离后第一条读请求 8 个扇区，设备自报 `DW1=0x200`、D2H 的扇区号只推进 1 ⇒ 那是**楔住那条 1 扇区命令**在 `ST` 重新拉起时补跑出来的 DMA 与回执 | `start_port` 先排空 `PxCI`（短暂拉起 `ST` 等有界 200 ms 落零，排不空就 `Err(DrainStuck)` 记一次失败重试）。**这条修复没有能变红的判据**：把排空整段关掉，`pending_cmds` 连着 3 次都读 0（旧命令那时同步答完了）⇒ 那一格只打印不进判据，真在量的是"整段回执"`dw1 == want`（它就是那次抓到 512/4096 错配的尺子） |

还有一条是**判定链自己**的（BACKLOG ㊱）：写用例"写完前后哈希必须不同"依赖目标区开局为空，
而那块 130 GiB qcow2 只在 `do_test` 的每行前重造 ⇒ 单跑 `run --features ahci-scratch` 复用了
上一次留下的图案，同一条用例经两条路径读出两个数（`改了=false`）。夹具该跟着"要挂这块盘"这件事走，
而不是跟着哪个子命令走 ⇒ `make_scratch()` 移进 `do_run`。

## 判定链这一轮的净增

- `ktests` 从 45 条到 **47 条**（`KT_AHCI` 认领与端口枚举、`KT_AHCI_DISK` 第一条 DMA 读）。
- `tools/aurora.py test` 的判定矩阵从 10 行到 **11 行**（新增 `fault-ahci-lba` 那一行，期望
  `CONTENT-MISMATCH(rc=33)`）。实测 11 行全部"符合"，`check` 5 道门禁全 `[ ok ]`，
  `bench` 四道门禁（含 P3/P1 两把尺子的分辨性）也仍"符合"。

顺带在这一轮里修掉的两个**工具级**缺陷（都是"量具看不见"那一类，记在这里而不是代码注释里）：

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| 改完代码 `run`，读到的是上一次 `test` 留下的负样本构建（rc=39） | `do_run` 只在镜像**不存在**时才重造，而 `test` 跑完留下的是最后一个变体 | `ensure_image`：先按当前源码构建，再比"变体名 + ELF sha256"两件事，任一不符就重造。判定必须和"我启动的到底是哪个产物"绑在一起 |

还有一条结构性事实这一轮又撞了一次（ADR-028 已经写过）：`.ktests` 段的执行顺序不跟着源码顺序走——
`t_ahci_disk` 在日志序号 `0x3e` 就跑，而源码里排在它前面的 `t_ahci_claim` 到 `0xbd` 才跑。
所以两条用例都必须能自己认领设备，`ahci::init()` 因此做成**幂等**：第一版不幂等，
第二次认领会再分配一份环形结构，并把前一份的映射与页框一起 drop 掉——而设备还在用它。

`drain_reap()` 的等待上限也从 120M 周期(≈36 ms)抬到 1G 周期(≈300 ms)：`bench` 的第二次同构建
启动（宿主正忙）让 `KT_USER_POINTER` 报过一次假红。抬上限之外还加了一条——**失败时把窗口里
进来了几轮 tick 一起打**，下次再红就能分清"tick 没进来"（环境）与"tick 进来了但没回收"（被测代码）。

## M6-a③ 补：本机还会**吞掉一次发射**（`PxCI` 写下去读回 0）

又一条"与规范不一样"。规范里 `PxCI` 是命令槽位图：软件写 1 就是把那条命令交给设备执行，
设备完成后自己把这一格清掉（本驱动就靠这两件事当回执），
本机偶发把这一次写**丢掉**：写 1、立刻读回 0，设备端什么都没发生。第一次抓到它的现场是启动路径：

```
[warn] ahci: 认引导盘 口0 第1次读 LBA1 失败 IssueStuck(0)
```

后果之所以大，是因为这条路径的下游是**判定链**：`state_store::read()` 拿不到引导盘 ⇒ `Err` ⇒
§9.4 的"读不到就按最坏情况"⇒ 一次被吞的写变成一次安全模式。而它也能落在任何一条用例的块读上，
表现是**矩阵里红的行号每次都换**（实测：一轮红在 `高LBA`、下一轮红在 `正向`、又一轮红在
`t_state_store`）——这种"红的位置会飘"的形状本身就是线索：不是某一格坏了，是底下有一条命令没了。

| 处置 | 论证 |
| --- | --- |
| `transfer()` 抓到 `IssueStuck` ⇒ `recover()` 之后**重发一次**；第二次仍被吞就把 `Err` 交出去 | 命令被吞意味着设备根本没收到它，因此重发一条**写**命令也是安全的（不是"可能已经落盘的写失败了"）。只重发一次：无限重试会把"这台控制器不能发射"读成"很慢但最终成功" |
| 分类层（`boot_port`）仍保留 3 次有界重试并逐次打出错误名 | 它重试的是"这块盘是不是引导盘"这件事，任何 `Err` 都要重试（`CmdTimeout`、`DrainStuck` 也在内），与上面只治 `IssueStuck` 的那条不是同一件事 |
| 每一次吞都打一行 `[warn]` | 没有这行，今天只能说"偶发少了"；有了它，24 连跑里那一次被 recover+重发救活的事实是**可读的**（见下） |

复量（正常构建 24 连跑，同一镜像不重建）：**24/24 PASS**、0 遍进安全模式、
`发射被吞` 出现 **1 次**（日志序号 `0xb0`，那次启动仍然 PASS）。修之前同一把尺子 16 连跑红 1 遍、
24 连跑红 1 遍（`t_state_store`），12 连跑里另有一遍把启动锁进安全模式并且**再也出不来**。

同一条调查里另有一处"量具不忠实"，与 AHCI 无关但形状一样（判据在等一个它证明不了的东西）：
`t_copy_user` 用 `served() == 35` 当"程序跑完了"，而 `SYSCALLS_SERVED` 是在
`syscall_dispatch` 的**入口** +1 的——它只证明请求进过内核，不证明程序已经回到用户态把返回值
写进自己的格子。红的那一遍与绿的那一遍只差一格：`buf_err=Some(0)` 对 `Some(-3)`，
其余三格、`kills`、`served=35/35` 与 `槽位=Runnable` 逐位相同。改成"读格子之前先有界等那格落定，
并把等了几轮与周期数打出来"（实测 24 连跑里等回填轮数全为 0，即正常时机下第一读就命中，
那 24 个 0 是"这条等待没有变成新的假绿"的证据，不是"没必要等"的证据）。

## M6-c① 补：重发被吞的命令**不占 §8.2 的重试预算**（两种重置分开数）

上面那条"恢复后重发一次"接在 `recover()` 上是错的：`recover()` 会 `PORT_RESETS[口] += 1`，
而那个数的语义是"这个口反复失败、按预算升级到隔离"。被吞的那条命令根本没进设备，
重发就成功了 —— 它是一次成功的重试，不是一桩未解决的故障。合并计数的直接后果是判据被顶掉：
`t_ahci_recovery` 断的是 `引导口resets == 0`，意思是"一个口的故障没传染到另一个口"，
而引导口自己偶发被吞一次就会让这个数变成 1 —— **红的是一桩根本没发生的传染**。

| 处置 | 为什么这样分 |
| --- | --- |
| 新增 `PORT_ISSUE_RESETS` + `recover_for_issue()`：只 `start_port`，不占预算、不参与隔离判定 | 预算必须只数"设备报过错/没答完"那一类。分开之后 `resets_of(口)` 才是它名字上说的那个意思 |
| 读数行同时打 `被吞重发合计` 与 `引导口被吞` | **分开数不是藏数**。被吞这件事在日志里仍然逐口可见，只是不再冒充故障传染 |
| 判定表的"成因"改成连红行上面两行一起打 | 那一次飘红的成因没留下来：用例都是先打读数再下结论，而"成因"只挑 `fail`/`fatal` 那一行 ⇒ 看得见"不成立"、看不见哪个数不成立。与 ㊵㊶ 同族（量具看不见 ≠ 被测物不存在） |

一句必须写的边界：分开计数解释了"一次被吞为什么会红"，但**不构成"飘红已治好"的证据**——
那一次的读数没留下来，而这次改动之后尚未观察到新的红。同一份构建单独连跑 6 遍是 6/6 PASS，
读数每遍都是 `全局resets=3 受害口resets=3 引导口resets=0 隔离数=1 干净错误=1 预算=3`。
