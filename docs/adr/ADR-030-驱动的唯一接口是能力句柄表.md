# ADR-030: 驱动的唯一接口是能力句柄表；MMIO 与 DMA 由内核持有

状态：已采纳（2026-11-05，M5-e 实测）
关联：手册 §8.2（驱动生命周期）§8.3（MMIO/DMA 抽象）§8.5（迁移到用户态的代价论证）§6.7（资源台账）
§12.4 的 P2（这条接口到底多贵）、ADR-024（"一次 UC MMIO 读约 600 周期"那一档对照）、ADR-029（AHCI 第一版）、
BACKLOG 的 M5-e

## 背景

手册 §8.5 写着"`DriverCtx` 是驱动与内核之间唯一的接口，驱动不持有原始指针"，§2.4 那张表又用
"不在首期承担微内核的 IPC 与性能代价"作为架构选择——**这句话要成立，必须先有 P2 这个数**；
而 P2 要有被测对象，就必须真有一条接口层。

问题是"要不要建这一层"在这台机器上有两种做法，而它们的差别看不见：

| 做法 | 代码形状 | 差别 |
| --- | --- | --- |
| 让 ahci 继续自己 `MmioRegion::map` + `phys_alloc` + 裸 `read_volatile` | 短 100 行，跑起来一模一样 | 全部判据照样绿。等到第二个驱动出现，"唯一接口"就只是文档里的一句话 |
| 驱动只能通过句柄表要资源 | 多一张表、多一层间接 | 一样绿，但多了一条**能被机器判出来**的性质 |

所以我先问的不是"值不值 100 行"，而是**这条性质有没有一条会变的判据**。
下面第 3 条决定就是为此而加的文本网关，第 6 条就是为此而加的数字。

## 决定

1. **句柄 = `槽号 + 世代号`，资源本体只活在表里**。驱动拿到的两个值都是 `Copy` 整数；
   `Ring` 那份静态结构里存的是 `(令牌, 句柄)`，被 drop 也不会解映射（映射在表里）。
   四种拒绝各有形状，不许压成一个 `Io`：`NoSuchHandle`（表里没有这一格）、
   `StaleHandle`（槽号对但世代号不对）、`NotOwner`（这一格属于别的 `ModuleId`）、
   `Access(HwError)` / `Denied(&'static str)`（窗口、对齐、参数）。
2. **撤销后复用同一格是必须测的那件事**，不是"看起来合理"的那件事。用例先撤销、再映射，
   断言新句柄落在**同一个槽**上、世代号变了、表里读到的世代号与新句柄一致，
   然后旧句柄必须 `StaleHandle`。空着那一格时读到的是 `NoSuchHandle`——
   两种坏法分开挡，否则"撤销真的摘走了表项"这件事没有证据。
3. **驱动模块不许出现裸访问**，由新门禁 `check-driver-ctx` 机器判：
   `DRIVER_MODULES = ["ahci.rs"]` 里每个文件不得出现 `read_volatile` / `write_volatile` /
   `write_bytes` / `from_raw_parts` / `ptr::`。这是一条**文本**网关——因为那条绕过的路
   读起来完全正常（自己摸映射比走句柄还快），系统里没有任何东西会因此变红。
   尺子自证：把清单临时指向 `driver.rs`（那里合法地有裸访问），门禁报出
   `driver.rs:312 出现裸访问 ['read_volatile','ptr::']` ⇒ 它能红。
4. **DMA 缓冲区不交出切片**，只给带偏移的 volatile 访问器（`dma_read8/32`、`dma_write8/32`、
   `dma_fill`、`dma_copy_out`）＋ `bus_addr()` 返回的**整数**总线地址（填描述符用，解不开引用）。
   这一条是 §8.3 原来的设计，第一次真正落到代码上。
   代价落在内容对账那一步：数据缓冲的哈希从"对一段切片算"改成"逐字节问答"（131 584 次），
   换来的是"驱动侧没有一块能被随意读的映射"。
5. **首期只做被用到的方法**：`map_mmio` / `read32` / `write32` / `release_mmio` /
   `alloc_dma` / `bus_addr` / 一组 volatile 访问器 / `release_dma`。
   手册里还有 `request_irq`、`set_timer`、`log` 三个方法——**这一版不写空签名**：
   先把没人调的方法摆进 trait，就是把目录当成实现。等中断认领（BACKLOG 仍开）落地时一起加。
6. **P2 的判据说的是量具，不是阈值**。三条线（一次 MMIO 读、一次 MMIO 写、一次 DMA 映射+撤销）
   之外必须有第四条：同一采样做 1 遍与做 4 遍，`min` 的比值要 >2×；再加一条数量级自检
   "一次 DMA 往返必须比一次寄存器读贵"。**先证明这把尺子在量这件事，才允许它进基线表**。

## 实测（本机 QEMU 11.1.0 / q35 / `-m 512M -smp 4 -cpu max`，周期数）

| 线 | `min` | `mean` | 读数 |
| --- | --- | --- | --- |
| 一次 MMIO 读（`CAP`，句柄表那条路） | 554 | 2 890 | 四次读的 `min`=1 956（比值 3.53×，判据要 >2×） |
| 一次 MMIO 写（`GHC` 原值写回，幂等） | 552 | 2 494 | 读写 `min` 打平，说明这一档的成本是"总线往返 + 句柄表两次索引"，不是方向 |
| 一次 DMA 映射+撤销（1 页：`phys_alloc` + 建叶 + 解映射 + 台账两笔） | 37 674 | 60 324 | 比一次寄存器读贵 **约 68 倍** |

同一构建连跑两次的散布（`2026-11-05T15-38-39Z-p3p4.txt`）：MMIO 读 `min` 554/541（差 2.4 %）、
DMA 往返 `min` 37 674/35 350（差 6.2 %）——**这三个数是散布量级以内的**，所以"68 倍"这种比值可以讲，
而"552 还是 554"不能当结论。四个构建（含两种负载注入）里 MMIO 读 `min` 落在 522~554。

对照：ADR-024 那次按排除法得到的"一次这种读在本机 QEMU 约 600 周期" ⇒ 本条直接量到 522~554，
差 8~13 %。两把尺子来自不同路径（那次是异常入口查 CPU 槽位，这次是句柄表读设备寄存器），
**没有互相验证的关系，只是同数量级**，所以不写成"印证"。

`KT_DRIVER_CTX` 六格的读数（一次跑，全部为 `true`）：映射时读回的命令寄存器 = `0x0007`
（`IO|MSE|BME` 三位都在，判据只看 `0b110` 那两位）；经 ctx 与经驱动读到同一个 `CAP=0xc0141f05`；
窗口 4096；越界拒 / 未对齐拒；撤销后同一格复用且旧句柄被拒；别人（另一个 `ModuleId`）
拿正确句柄被拒；空槽与越界槽号都拒；DMA 页框从 0→2、撤销后**页框 / 表占用 / VA 保留三本账
都回到原位**（基线：表占用 MMIO/DMA = 1/1 —— 那一格正是 AHCI 自己走 ctx 占的，
等于顺带证明了驱动确实经这条路拿的资源；VA 保留 18 → 18）。

写这条用例时踩到自己挖的坑，记下来当形状：**日志行里第二次调 `mmio_authorized(h)` 打印出 `0x0000`**，
而判据是 `true`。原因是日志在函数末尾执行，那时那两格句柄都已撤销，`unwrap_or(0)` 把"读不到"
打成了"读到 0"。判据没错（它当场算的），**是打印会骗人** ⇒ 要报出来的值必须当场存下来。
（`tools/aurora.py` 的"量具看不见不等于被测物不存在"同一类，这次是量具看错了。）

尺子能动过：把 `check_m` 里世代号与主人两道检查整段删掉再跑，读数是
`旧句柄被拒=false 别人被拒=false`，其余一条没变，用例红 ⇒ 这两条判据在量它们说的那件事
（临时改动已还原，还原后的 ELF 与改动前逐位相同）。

## 后果

- `ahci.rs` 剩下的 `unsafe` 只有 5 处，全部是那一格静态 `RING` 的 `UnsafeCell` 读写
  （拿句柄，不拿指针）。数据路径上的 `unsafe` 一个都不剩。
- `AhciError` 少了两个变体（`Map(HwError)`、`Ring(mm::MmError)`），换成一个 `Ctx(DriverError)`：
  错误形状跟着资源申请路径走，两条路各自一套码就会有人去猜是哪一个。
- **`check` 从 5 道门禁到 6 道**（新增 `check-driver-ctx`）。新增驱动必须加进 `DRIVER_MODULES`，
  不加 = 这条网关不管它。
- P2 上线 ⇒ `bench` 的判定行从 3 条变 4 条（P3 / P1 / **P2** / P4 对照），四个构建的日志各多 6 行
  （P2 五条 + `KT_DRIVER_CTX` 多出的三本账那一条），串口量 25 062 → **26 148~26 163** 字节。
  这一档**没有单独归因**（探针自己就要打这些行）；本轮 P4 的同构建地板是 0.52 %，
  比上一轮 M5-d 的 1.36 % 低 ⇒ 不把差值当回归读。
- 这一层让"微内核迁移值不值"那笔账第一次有数字，单位只用**周期**（本机 TSC 非 invariant，
  手册 §12.4 早就规定跨次只看比值）：**一次寄存器往返约 550 周期，一次 DMA 建/撤约 37 700 周期**。
  将来若把 `DriverCtx` 改成系统调用代理，要比较的就是这两档，而不是"感觉会慢"。

## 没做到的（都记进 BACKLOG）

1. `request_irq` / `set_timer` / `log` 三个方法没有（见决定 5）。
2. 中断上下文那条守卫（`alloc_dma`/`map_mmio` 撞 `apic::in_isr()` 就 `WrongContext`）**没有判据**：
   要造出"在 ISR 里调用"需要一条中断侧的钩子，而现在没有任何驱动认领中断，
   这条支路在生产路径上也走不到。留作中断认领那一轮的配套用例。
3. 表容量写死 8 + 8，槽号两张表各自从 0 数（`NotOwner` 那条只覆盖了 MMIO 侧）。
   真机多驱动会先撞上这个上限——那是一条**可见失败**（`ResourceExhausted`），不是静默降级。
4. `PhysAbove4G` 这条限制仍然在驱动里（AHCI 只编程低 32 位）。真正的解法是 64 位基址或 IOMMU，
   两个都还没做。
5. `mm::map` 失败时那次 VA 保留由 `alloc_dma` 自己放手（写了注释）；但这条错误支路本身没有用例打，
   因为它需要"映射必失败而分配成功"的设备形状。

## M5-f② 补记：第二个驱动进来了，"唯一接口"这句话第一次有了对照组（实测 2026-11-06）

`virtio-blk` 是 `DriverCtx` 的**第二个消费者**，也是第一个不是 AHCI 的存储控制器。它一条裸指针都没拿到：
`map_mmio` 拿 BAR、`alloc_dma` 拿一段 8 页的连续区（描述符环 / _avail / _used / 数据 / 请求头 / 状态
都在这段里按固定偏移切），`bus_addr` 只交回一个整数。`check-driver-ctx` 那条文本网关把
`virtio.rs` 一起扫（禁用 `read_volatile`/`write_volatile`/`ptr::`/`from_raw_parts`），它是绿的。

| 现场量出来的（不是从规范推的） | 读数 |
| --- | --- |
| 队列地址那三格（`queue_desc`/`queue_driver`/`queue_device`）写下去读得回来吗 | **读得回来**（`地址回读=Some(true)`）。这一格以前是不确定的：规范说它们在，没说过一定能回读，所以代码里把结果存成 `Option<bool>` 而不是直接断言 |
| `queue_enable` 写 1 读回 | 1 |
| 队列深度、容量、notify 地址与步长 | `qsize=256`、`capacity=131072`（= 宿主机那块 64 MiB qcow2 的扇区数）、`notify=0x3000`、`multiplier=4` |
| 一条读请求的回执 | `used.id=0`（我们挂的链头）、`used.len=513`（数据 512 + 状态 1 —— 设备把它写的两段都算进长度）、`status=0`（`VIRTIO_BLK_S_OK`） |
| 第一条 I/O 的内容 | 扇区 0 整扇区等于夹具图案 `0x5C`；扇区 1 哈希不同（位置敏感）；写扇区 8 后回读哈希 == 写前哈希 == **宿主机用 qemu-io 读回来的哈希**（矩阵第 22 行） |

这次改动顺手补了 `DriverCtx` 的两个访问宽度：`dma_read16`/`dma_write16` 与 `dma_copy_in`。
理由不是"想对称"：描述符的 `flags`/`next` 与 avail 环的 `idx` 都是 `u16`，只能用两次字节访问拼的话，
就把"一次 16 位写"拆成两个设备可能看见中间态的写；而 `dma_fill` 只能填重复字节，写一段任意
数据就得 512 次 `dma_write8` 且每次都重新做一次边界检查。两者都在 `driver.rs` 里集中做一次界检查。
