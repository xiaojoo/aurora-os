# ADR-053：等待队列的依赖反转、放锁后再切走、以及 P4 的三段切分

状态：已采纳（2026-11-08，S1/W1 的 P4；修正 ADR-047 决策 3/4 的两处落地形状）
关联：ADR-047（W1 接口与锁序）、ADR-040（回调表反转依赖的先例）、ADR-048（运行队列锁）、
ADR-049（resched 自陷）、ADR-051/052（前提变判据与兜底 idle）、
`docs/architecture/lock-order.md`、`docs/architecture/module-interfaces.toml` 的环 A 基线

## 背景

ADR-047 把 `WaitQueue` 放在 `sync`（理由：驱动、IPC、块层都要用它，而它们不能依赖 `sched`），
并写了"持 `WAITQ` → 查条件 → 占槽 → 标 `Blocked` → 取 `RUNQ` → 换人"。落地前发现两处必须改：

1. **`sync` 不能引用 `sched`**。今天 `sched -> sync` 是一条单向边，`sched` 是环 A 之外的单点。
   若 `sync::WaitQueue` 直接调 `sched::` 去标状态/换人，就新增 `sync -> sched`，
   `sched` 会被拉进强连通分量 ⇒ `check-module-interfaces` 的 `known_scc` 与
   ADR-044 的站点棘轮同时红。这不是门禁在挡路，是它正确地指出了分层被打破。
2. **"持等待队列锁换人"在本仓库会死锁**。`sync::IrqGuard` 的 `Drop` 在**函数返回时**执行，
   而一个阻塞的任务在被人唤醒之前**不会返回**——于是它睡着的整段时间里 `WAITQ` 一直被持有，
   任何唤醒方都取不到这把锁。Linux 那种"由调度器在切换时释放 rq 锁"的语义我们并没有。

## 决策

1. **依赖反转用回调表**（沿用 ADR-040 的形状）：`sync` 侧定义 `WaitOps`
   （`current_token`、`block`、`wake` 三个函数指针）与一张默认 no-op 表，
   由 `sched` 在启动时装真实现（`sched::install_wait_ops()`）。
   `sync` 因此不引用 `sched`，依赖方向不变，环 A 不动。
   装表是一次性写入， unsafe 站点按 U4 登记（与 `hooks` 同一论证）。
2. **放锁后再切走**（修正 ADR-047 决策 4 的措辞）：
   - `wait_until(cond, deadline)`：持 `WAITQ(5)` → 查 `cond` → 占槽 → 取 `RUNQ(8)` 标
     `Blocked(token)` → **放掉 both 锁** → `yield_now()` 自陷切走（ADR-049）。
   - `wake_one/wake_all`：持 `WAITQ(5)` → 出队 → 取 `RUNQ(8)` 标 `Runnable` → 放锁 →
     若目标 CPU ≠ 本 CPU 则发 `VEC_RESCHED` IPI。
   - **防丢唤醒仍然成立**：致命的窗口是"查完条件到入队之间插进一次 wake"，
     而这两步在**同一把 `WAITQ` 锁内**，所以插不进来。放锁之后即使立刻被 wake，
     本任务已是 `Runnable`，自陷让出后仍会被选回来——不会丢。
3. **`WaitToken` 放在 `sync`**：`TaskState::Blocked(sync::WaitToken)`。
   `sched -> sync` 边已存在，所以类型放这边不新增任何依赖；反过来放 `sched` 会让 `sync` 依赖它。
   形状沿用 ADR-047：`{ queue: u8, seq: u64 }`，`seq` 是唤醒世代号，
   用来分辨"叫醒的是这次等待"而不是上一次遗留的那次。
4. **`reap` 与 `Blocked`**：`Blocked` 既不是 `Free` 也不是 `Done`，所以 `reap` 天然跳过它
   （正确：它还活着、还持有资源）。但**杀死一个阻塞任务**必须同时把它从等待队列里摘掉，
   否则后来的 wake 会去碰一个已释放的槽。P4a 先以保守形状落地：
   `wake_task(gidx)` 只在目标槽**确实是 `Blocked`** 时才转移状态，否则返回 false（无操作）；
   `terminate_task` 对 `Blocked` 槽的摘链留到 P4b 与 `WaitQueue` 同轮（那时才有链可摘）。
5. **P4 切三段，每段都有真实调用者与判据**（避免"没有生产者的状态"，ADR-051 决策 2 的同一理由）：
   - **P4a**：`WaitToken` + `TaskState::Blocked` + `sched::block_current/wake_task`，
     由一条**同核**阻塞/唤醒用例直接调用（真实调用者），判据看状态转移与世代号；
   - **P4b**：`sync::WaitQueue` + `WaitOps` 装表 + 条件等待协议 + 定长槽位与 `NoCapacity`，
     配**变异 A**（把入队移出 `WAITQ` 锁 ⇒ 丢唤醒计数 > 0）；
   - **P4c**：跨 CPU 唤醒（hooks 加 `mark_need`、`apic` 的 resched 分支立牌）+ 4 核
     生产者/消费者压力 + **变异 B**（去掉 IPI ⇒ 跨核唤醒延迟超界）。

## 备选方案

- **把 `WaitQueue` 放 `sched`**：拒绝。驱动/IPC/块层不能依赖 `sched`（ADR-047 的原始理由），
  放那边等于把未来的使用者全部绑到调度器上。
- **`sync` 直接引用 `sched`**：拒绝，见背景 1（会把 `sched` 拉进环 A）。
- **持 `WAITQ` 锁切走**：拒绝，见背景 2（阻塞期间锁不释放，唤醒方全死）。
- **给 `IrqSpinLock` 加"切换时释放"的特殊语义**：拒绝。那要改锁的核心语义，
  影响所有既有锁与 `INNERMOST` 的 per-CPU 论证（M3b-1），代价远大于"放锁后再切"。
- **一次把 P4 全做完**：拒绝。`Blocked` 一进枚举就要同轮改所有消费者，
  再叠加队列协议与跨核 IPI，红了分不清是哪一层；三段各自有调用者与负样本更可控。

## 影响

- 依赖图不变（`sched -> sync` 已存在；`sync` 不新增出边到 `sched`），环 A 与棘轮不动。
- 锁序表里 `RANK_WAITQ(5)` 那一行到 P4b 才转"已落地"；P4a 只用 `RANK_RUNQ(8)`。
- `TaskState` 加变体后，`matches!(state, Runnable | Running)` 的既有站点**天然排除 Blocked**，
  语义正确（阻塞不是"可运行"），但要在 `tasks_active()` 的注释里写明，
  免得被读成"任务消失了"（ADR-051 决策 4 的同一要求）。
- 登记面：`sync::WaitToken`、`sched::block_current`/`wake_task` 若被产品路径引用则要登记；
  P4a 的调用者是 ktest，按 ADR-043/045 口径**不算产品边**，所以 P4a 可能零登记改动，
  由门禁说了算，不自行预判。

## 验收与负样本

判据随三段各自落地，本 ADR 只把它们钉成清单：

| 段 | 判据 | 负样本 |
| --- | --- | --- |
| P4a | 同核阻塞/唤醒：状态 `Running→Blocked→Runnable`、世代号递增、wake 对非 Blocked 槽返回 false | 去掉世代号检查 ⇒ 陈旧 wake 被当成有效（用例红） |
| P4b | 丢唤醒计数 = 0；`NoCapacity` 可观察；条件检查与入队同锁 | **变异 A**：入队移出锁 ⇒ 丢唤醒 > 0 |
| P4c | 4 核生产者/消费者：`wake` 与 `block` 计数差 ≤ 在途数；跨核唤醒延迟有界 | **变异 B**：去掉 IPI ⇒ 延迟超界；**V3**：反向嵌套 `RUNQ→WAITQ` ⇒ L4 |

## 迁移与回滚

- P4a 回滚：删 `Blocked` 变体与两个原语、还原消费者；无登记面变更时不需要动登记表。
- P4b/P4c 回滚各自独立：`WaitOps` 表退回 no-op 即等价于"没有等待队列"，
  已阻塞的任务不会被唤醒，所以回滚必须在没有阻塞任务时做（启动期或用例结束后）。

## 未决

1. 容量 `MAX_WAIT_QUEUES=16 × MAX_WAITERS=16` 仍是拍的（ADR-047 已记）；
   P4b 落地时要么用真实并发度钉住，要么明确写成"上限，超出回 `NoCapacity`"。
2. `deadline` 的时间源：P4b 先用 TSC 绝对值 + 调用方给的时限，定时器轮（P6）落地后改成轮驱动。
3. 杀死阻塞任务的摘链（决策 4 留到 P4b）与 `terminate_task` 的交互要配负样本。
