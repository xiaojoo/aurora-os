# ADR-039：模块接口登记与依赖矩阵基线（V1.0 Task A/B）

状态：已采纳（2026-11-07，V1.0 Task A/B；T0.1 之后；BACKLOG §88/§89）
关联：V1.0 §2/§3/§14、ADR-007（capability 句柄）、ADR-030（驱动唯一接口是能力句柄表）、
BACKLOG §87–§89

## 背景

本仓库在 T0.1 之前只有一个 `aurora-kernel` crate，模块边界靠 `pub`/`pub(crate)` 隐式存在；
`main.rs` 7,617 行，测试与启动编排混在一起。T0.1 把 74 个用例与 32 个辅助项搬进
`kernel/src/ktests/` 后，`main.rs` 只剩 677 行；但“模块对外提供什么、谁可以调用谁”仍然
没有任何登记，也没有机器检查。

Task A/B 的实测事实：

- 产品路径实际依赖图是**一个 14 模块的强连通分量**：
  arch / boot / capability / diagnostics / driver / irq / memory / pci / resource /
  sched / storage / sync / testing / time；security 与 integration 在环外。
- V1.0 §2.2 明示的禁止方向里，当前唯一的实际违例是 `arch -> sched`
  （apic/smp/trap 调 `sched::mark_tick` / `init_idle_task` / `exit_current`）。
- `mm -> ahci/virtio`、`pci -> ahci`、`resource -> sched` 当前都干净；
  `driver -> storage` 的唯一命中是注释里的 `ahci::RING`，剥注释后不算实际边。

## 决策

1. `docs/architecture/module-interfaces.toml` 是模块接口的唯一机器可读登记表：
   16 个逻辑模块覆盖 main.rs 的 29 个顶层 `mod` + main 本体；
   `public_api` 只登记**产品路径实际跨模块引用**到的 `pub`/`pub(crate)` 符号
   （剥 `//` 注释、排除 `ktests/*`；测试钩子只进 `test_targets`）。
2. `dependencies` / `allowed_callers` 由源码引用边计算，与实际边**双向相等**；
   §2.2 的禁止方向写入 `forbidden_dependencies`，实际命中的边必须列入
   `known_violations`（冻结基线，不是许可）。
3. 当前 14 模块环写入 `[baseline].known_scc`。新增环成员或改变环的划分 ⇒ 红；
   消环是好事，但必须显式更新基线并在 BACKLOG 记一条。
4. `check-module-interfaces` 七条规则：模块覆盖、public_api 符号存在、依赖/调用者对账、
   forbidden+known_violations、unsafe_scope 对 unsafe 普查、SCC 基线、test_targets 存在。
5. `check-interface-change`：`module-interfaces.toml` 或 `module-dependencies.md`
   有未提交改动时，工作树里必须同时有 `docs/adr/ADR-*.md` 的改动；ADR 标题编号唯一、
   状态行存在且取值合法。ADR 模板新增为 `docs/adr/ADR-template.md`；既有 24 份不回改，
   只做最小机器校验。

## 备选方案

- **从 rustc AST 自动生成**：拒绝。稳定版工具链不提供稳定的 AST 接口；本轮用文本扫描，
  以“剥 `//` 注释、排除 `ktests/*`、短名解析”控制误报，边界写在 module-dependencies.md §6。
- **先拆 crate 再登记**：拒绝。没有稳定接口时先造空壳违反 AGENTS 硬约束 2；
  且拆 crate 需要逐条消环，不能一次重写。
- **只写文档、不做门禁**：拒绝。文档会腐烂；本轮已用 6 个负样本证明门禁会咬。
- **立即消掉 14 模块环**：拒绝。需要改 `arch`/`sched` 之间的接口（例如把 tick 回调
  改成注册式），属于后续 ADR；先冻结，再逐步消。

## 影响

- 只改文档与 `tools/aurora.py`；内核源码零改动。默认注册仍 53 条、默认跑 PASS。
- `check` 从 15 道变为 16 道（新增 `check-interface-change`）。
- 代价：每条跨模块 `pub` 接口/依赖变化都要同步登记表；`known_violations` 是债务，
  不是许可，拆 crate/分层时要逐条消掉。
- 已知边界：文本扫描不解析字符串字面量里的同名文本；产品文件内的 `#[cfg]` 测试代码
  也计入依赖（如 `storage -> testing`，这是真实编译期依赖）；`serial` 专属禁止项与
  “低层不得引用 main 测试函数”尚未机器化；单 crate 没有 Cargo 依赖图可查。

## 验收与负样本

- `check` 16/16；默认 `run` PASS（53/53/0）。
- Task A/B 的 6 个负样本（删逻辑模块、伪造 public_api、删真实依赖、删 known_violation、
  伪造 unsafe_scope、删 SCC 成员）各自先红后绿，原文见 BACKLOG §88/§89 与 `.scratch/t01/`。
- 本 ADR 新增的接口变更门禁再做两个负样本：改 `module-interfaces.toml` 但不加 ADR ⇒ 红；
  同时加一份临时 ADR ⇒ 绿；还原后绿。

## 迁移与回滚

- 无代码迁移。回滚方式是删除登记表与两道门禁，不触碰内核实现。
- 已采纳的决策若被推翻，按新 ADR 取代本份；不改写本文件的历史结论。

## 未决

- `check-interface-change` 是**工作树门禁**：干净树（CI 已提交之后）不推断历史。
  若要 CI 事后审计，需要另设基于提交历史的检查（未做）。
- 14 模块环的消解顺序（先 `arch->sched` 还是先 `memory->sched`）未定。
- §9.2 第二到第五步的 crate 提取未开始。
