# ADR-018: 内核堆的 OOM 出口与可失败分配的分工

状态：已采纳（2026-11-04，M2-b 实现并实测）
关联：手册 §6.5、§6.4、§9（三级资源错误）、§12.3 门禁、ADR-005（`panic=abort`）、ADR-015

## 背景

M2-b 要把内核堆接成 `#[global_allocator]`。接上之后，`alloc` crate 里所有
`Vec`/`Box`/`String` 的分配都经由它，而这些调用点**没有一个能返回错误**。
手册 §6.5 原文同时要求两件事：「禁止隐式 OOM 崩溃」和「失败作为三级资源错误向上传播（§9）」。
在稳定版 API 上这两条不能同时满足，必须挑一条为主、并给另一条指定落点，否则实现时
会出现「文档说可传播、代码里无处传播」的静默降级。

## 硬约束（不是选择）

| 事实 | 依据 |
| --- | --- |
| `GlobalAlloc::alloc` 的返回类型是 `*mut u8`，没有 `Result`；返回 null 后由 `alloc` crate 走 `handle_alloc_error` | 本工具链 `core::alloc::GlobalAlloc` 签名，编译期即定 |
| `handle_alloc_error` 在 `no_std` + `panic=abort`（ADR-005）下落到我们的 `#[panic_handler]` → 串口打 `kernel panic` → 退出码 **39** | 实测：`--features fault-heap-oom` 构建里 `Vec::with_capacity(2049)`，串口停在 `kernel panic at library/alloc/src/alloc.rs`，`qemu-exit=39` |
| 内核里失败必须**要么可观察、要么停机**，不允许「返回空指针继续跑」 | §9.2 完整性分级；空指针被解引用会变成 #PF，把资源问题伪装成异常问题 |

## 实测（两条路各有归属，别混）

| 注入 | 结果 | 结论 |
| --- | --- | --- |
| `Vec::with_capacity(LARGE_MAX + 1)`（走全局分配器） | 串口 `kernel panic at library/alloc/src/alloc.rs` → 退出码 **39** | 运行时分配失败的出口确实是 L4；已固化成 `--features fault-heap-oom` 构建，进 `tools/aurora.py test` 判定矩阵第四行 |
| 把堆窗口压到 8 KiB（小于预映射的 16 chunk） | `heap::init failed` → 退出码 **37**（BOOT-INVALID） | **建堆失败与堆内分配失败是两个不同的出口**，这是对的：前者是启动前提不成立，后者才是运行期资源耗尽。不要把它们并成一个码 |

> 撤回：本 ADR 初稿把第二行写成了“判定链稳定给出 39”。实测它给的是 37，
> 因为 `heap::init` 的 `Err` 分支在 `after_switch` 里走的是 `Code::BootInvalid`。
> 39 那条结论的真实依据是第一行。

## 选项

1. **不接全局分配器**，内核里禁用 `Vec`/`Box`，一切分配显式走 `try_*`。
   代价：`alloc`  machinery（含后续 `fmt` 的动态部分）全部不能用，M3 起的代码会不断破例。
2. **接全局分配器 + 失败即 L4 停机**；同时提供 `heap::try_alloc` 给需要 `Result` 的调用方。
3. 预留兜底池：分配失败时从原子预留池借，先记日志再决定。§6.5 的「中断上下文只用预留原子池」
   是这条的子集，但 M2-b 没有原子池，也没有「借了还得起」的证据。

## 决策

采纳 **2**，并加三条限制使其不退化成「隐式崩溃」：

1. **`GlobalAlloc` 路径失败 = L4**，这是接口给的唯一选项，不是我们的偏好。因此规定：
   内核态容器（`Vec`/`Box`/`String`）只允许出现在**已核算过分配预算**的路径上；
   预算未核算的新代码路径一律用 `heap::try_alloc`（返回 `Option`）或 M2-c 的 `aurora-alloc::try_*`。
   这条写进 §12.1 评审清单，不停留在注释里。
2. **超过大小类上限（`LARGE_MAX = 2048` 字节）的请求明确失败**并计入 `OOM_COUNT`，
   **不做大对象的「看起来能用」路径**。理由：`GlobalAlloc` 的接口里无处安放 `mm::Mapping`
   的物理页所有权，硬做必须另建一张全局表，而那张表自己又需要分配器——先建循环依赖，
   再用一个静默坏掉的实现掩盖它，比返回 None 更贵。实测这条是**能分辨的**：
   `KT_HEAP_OVERSIZE` 里 `oom_count` 0 → 1，且分配返回 `None`。
3. `OOM_COUNT` 是 L3 资源错误的唯一可观察出口。任何返回 None 的分支都必须计数，
   不许静默返回；用例断言的是**增量**，不是绝对值（前面的用例已经把计数用掉了）。

## 后果

- 「一个错误不拖垮整个系统」（用户定的总目标）在 M2-b 这一层的兑现方式是**边界收窄**：
  堆失败只发生在分配点，且分配点被限制在预算已核算的路径上。真正把这层做成故障域，
  要到 M2-c 的资源登记 + 故障注入框架，以及 M6 的用户态隔离。
- 中断上下文禁止堆分配（§6.5 原文）目前没有机制保证，只有约定。列为 **M3a 之前的门禁项**，
  已写 BACKLOG。
- 本决策不覆盖 VMM 的用户地址空间 OOM、也不覆盖物理帧耗尽时的降级策略（§6.7 诊断项），
  那些各自需要独立 ADR。
