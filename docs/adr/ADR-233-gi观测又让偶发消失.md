# ADR-233：`gi` 观测又让偶发消失（第二次 heisenbug）

状态：**提议**（2026-11-23：加观测后 0/20，偶发再次消失）

关联：ADR-227（第一次 heisenbug）、ADR-232（`reap` 观测，未干扰）

> ADR-232 的 `reap` 观测（两个 `fetch_add`）**没有**干扰时序（16/20 与加观测前一致）。
> 本 ADR 加 `REAP_LAST_GI.store` + 遍历 `owned` 的循环 —— **偶发消失了（0/20）。**

## 加了什么

```rust
// reap 真要收之前
REAP_LAST_GI.store(gi as u32, Ordering::Relaxed);
{
    let s2 = rq(cpu);                      // <-- 又取一次 RUNQ 锁
    let n2 = s2.tasks[slot].owned.n;
    for k in 0..n2.min(MAX_OWNED) { ... }  // <-- 遍历 owned
    drop(s2);
    if has_c { REAP_LAST_HAD_CONTAINER.store(1, Ordering::Relaxed); }
}
```

**比 ADR-232 多了两样东西**：

1. **又取一次 RUNQ(8) 锁**（`rq(cpu)`）；
2. 一个 `MAX_OWNED` 次的循环。

## 结果：0/20

| | ADR-232（两个 fetch_add）| ADR-233（+ store + 取锁 + 循环）|
|---|---|---|
| 失败 | 4/20 | **0/20** |

## 为什么这次干扰了、上次没有

`fetch_add` 是**无锁**原子指令（几十纳秒）。

而 `rq(cpu)` 要**取 RUNQ 锁** —— 若此刻锁被占（本 CPU 或别的 CPU），就要自旋。

**在 `reap` 里多取一次 RUNQ 锁，等于把「从判定到回收」的时间窗口拉长**，
而那个窗口正是竞态的窗口。

## 这解释了 ADR-227 与 ADR-232 的差别

| ADR | 加了什么 | 是否干扰 |
|---|---|---|
| 227 | `log_info!`（写串口，几十微秒）| **是**（25/25 全绿）|
| 232 | 两个 `fetch_add`（无锁，几十纳秒）| **否**（16/20）|
| 233 | `fetch_add` + `rq()` 取锁 + 循环 | **是**（20/20 全绿）|

**分界线是「有没有取锁」**，不是「有没有原子操作」。

## 这条应当推广

> **在竞态窗口内加观测时，只要不取锁、不写串口，就基本不干扰时序。**
>
> 取锁会引入自旋等待，而自旋等待的长度取决于别的 CPU —— 那是不确定的，
> 足以改变竞态的胜者。

## 我本可以避免这个错误

ADR-232 已经证明「两个 `fetch_add` 不干扰」。要继续观测，应该：

1. 在**已经持有 RUNQ 锁的那段代码里**读 `owned`（那个块已经 `rq(cpu)` 过）；
2. 或者只记 `gi`（一个 `store`，不取锁），不遍历 `owned`。

我选了「再取一次锁」—— 那是把 ADR-232 的成果浪费掉了。

## 现在的状态

代码里有 ADR-232 与 ADR-233 两批观测。**ADR-233 那批让偶发消失**，所以：

- 它**不能**留在默认档（会掩盖问题）；
- 但它是 `unmap-trace` 特性下的，默认档不受影响；
- 保留它没有害处（默认档不编译），但**它的读数在 `unmap-trace` 档下也不可信**
  （因为它自己干扰了）。
