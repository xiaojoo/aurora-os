# ADR-165：容量与编号的四处变更（ModuleId 撞号、驱动槽、任务数、syscall 段）

状态：已采纳（2026-11-20，使用者裁决）
关联：ADR-030（驱动句柄表）、ADR-044（环内站点棘轮）、ADR-155（`.text` 扩容）、
ADR-162/163/164（这三条推翻裁决之后，容量不够用了）

> 四件事合在一份 ADR 里，因为它们**互相依赖**：不扩槽就装不下新驱动，
> 不扩任务数就起不了新的等待任务，不预留 syscall 段就每个新号都要裁决一次，
> 而 `ModuleId` 撞号会让新增驱动时台账读错。分开写会让四条决策互相引用成环。

## 背景：四处具体的缺口（都是实测）

### 缺口 1：`ModuleId(19)` 被两个模块占用

    driver/virtio.rs:21:  pub const MOD_VIRTIO: ModuleId = ModuleId(19);
    memory/vmo.rs:20:     pub const MOD_VMO:    ModuleId = ModuleId(19);

`resource/mod.rs` 的台账**按 `ModuleId` 聚合**（O(1) 记账，见该文件 §1 的第 1 条）。
所以查"virtio 占了多少帧"会读到 VMO 的数，反之亦然。

今天不出事，是因为两条账从不放在一起比。但 `ledger: module 19 live=0 frames alloc=5`
这类读数**已经在日志里**，含义是模糊的。

### 缺口 2：驱动槽 8+8 已接近满

    driver/mod.rs: const MMIO_SLOTS: usize = 8;
    driver/mod.rs: const DMA_SLOTS:  usize = 8;

实测占用（今天在线的档）：AHCI(1 MMIO + 1 DMA) + 2×virtio-blk(2+2) + virtio-net(1+2)
≈ **4 MMIO + 5 DMA**。而 `virtio::probe()` 还会**临时多占 1 格** MMIO。

NVMe 一台就要 **1 MMIO + 5 DMA**（Admin SQ/CQ + I/O SQ/CQ + 数据页），
xHCI 要 **1 MMIO + 2 DMA**，HDA 要 **1 MMIO + 1 DMA**。8 格必然不够。

### 缺口 3：`MAX_TASKS = 9` 每 CPU 零余量

    sched/mod.rs: pub const MAX_TASKS: usize = 9;

`AGENTS.md` 把它列在"已知脆性"里。USB 的事件环轮询、GPU 的 fence 等待、
音频的流喂样本，都需要常驻任务——而零余量意味着**新增一个就会挤掉一个**。

### 缺口 4：syscall 号 1..47 连续占满，2 号不是空洞

实测：1..47 连续（2 号是 `rdi + rsi` 算术探针，**不是未用**），
99 号是 `SYS_NOT_A_NUMBER` 负样本。下一个可用号是 **48**。

需要新号的：TCP/Socket 一族（ADR-162 之后还会有 USB HID 事件出口、
音频控制），每加一个都裁决一次不现实。

## 决策

### 1. `MOD_VMO` 换号

把 `memory/vmo.rs` 的 `MOD_VMO` 从 **19** 改成 **20**（未用号）。

**为什么换 VMO 而不是换 virtio**：`virtio` 的 19 出现在既有日志读数里
（`ledger: module 19 …`），换它会让历史读数对不上；`MOD_VMO` 的引用面更小
（`vmo.rs` 内部 4 处 + `ktests/memory/mm.rs` 1 处）。

**同时必须做**：`docs/security/unsafe-census.md` 与 `resource` 台账的说明里
凡提到"模块 19"的地方都要能分辨是哪一个——换号后**旧日志的 19 一律是 virtio**，
这要在 `resource/mod.rs` 的注释里写明（历史读数不可重解）。

### 2. `MMIO_SLOTS` / `DMA_SLOTS` 扩到 16/16

    const MMIO_SLOTS: usize = 16;
    const DMA_SLOTS:  usize = 16;

**同时必须做**（否则扩了也不够）：NVMe 的 4 个队列**塞进同一块 `alloc_dma`**
（连续页自己切偏移），把 5 格压到 2 格。

理由：`DmaHandle` 的访问器本来就收 `off` 参数（`dma_read8/16/32`、`dma_copy_in/out`、
`dma_fill`），所以"一块大 DMA 切成几个环"是**接口已经支持的形状**，
不需要新接口。

### 3. `MAX_TASKS` 从 9 扩到 12

**代价要写清**：`MAX_TASKS_TOTAL = MAX_TASKS * MAX_CPUS`（8 核 ⇒ 96 个任务槽）。
每个 `Task` 结构体在 `RQ` 的静态数组里，扩 3 格 × 8 核 = 24 个槽的静态内存增量。

**必须同步改的判据**：凡按 `MAX_TASKS` 算的用例读数（`t_q2_workload_slots` 的
"回基线"、`tasks_active()` 的上界）都要重核。

### 4. syscall 号段 48–63 一次预留

把 **48–63（16 个）**按族分配，**一次裁决、分段使用**：

| 段 | 族 | 数量 |
|---|---|---|
| 48–55 | 网络（socket/bind/connect/send/recv/shutdown/setsockopt/getsockopt） | 8 |
| 56–59 | 输入事件（键盘/鼠标/触摸/合成） | 4 |
| 60–61 | 音频（流控制/参数） | 2 |
| 62–63 | 保留（不分配，留给下一个未预见的族） | 2 |

**分配规则**：族内顺序固定（上面表格的顺序就是号序），**不许跳号**——
跳号会让"下一个可用号"这件事又变成需要查表的问题。

**64 及以上**：超出预留段时**重新裁决**，不自动延续。

## 备选方案

| 方案 | 不选它的理由 |
|---|---|
| 给 `MOD_VMO` 用 63 之类的大号 | 号段要留出扩展空间；20 是紧接着已用号的第一个空位，语义上"VMO 是第 20 个模块" |
| 只扩 `DMA_SLOTS` 不扩 `MMIO_SLOTS` | 新驱动两个都要（NVMe 1+5、xHCI 1+2），只扩一个还是会撞 |
| 扩到 32/32 | `.bss` 增量 ×4，而 `MMIO_SLOTS` 只影响表项不占物理内存——但没实测过 16 够不够之前，先到 16（16 = 今天 8 的两倍，且能装下 NVMe + xHCI + HDA + 现有全部） |
| `MAX_TASKS` 扩到 16 | 静态内存与 `MAX_TASKS_TOTAL` 的判据变动面更大；12 够覆盖 USB/GPU/音频各一个常驻任务 |
| syscall 一次预留到 127 | 号段是 ABI 承诺，预留太宽会锁死未来布局；16 个够用一轮 |
| 每加一个 syscall 单独裁决 | 使用者明确要求"一次预留一段，按族分配" |

## 影响

**正面**：

- 新增驱动不再"加一台就满"；
- `ModuleId` 撞号消除，台账读数不再模糊；
- 任务数有余量，USB/GPU/音频的常驻任务有地方放；
- syscall 不必每加一个裁决一次。

**负面 / 代价**：

- `MMIO_SLOTS`/`DMA_SLOTS` 从 8 到 16 会让 `DriverCtx` 的静态表翻倍（`.bss`）；
- `MAX_TASKS` 9→12 会让每 CPU 的任务数组变大，且**要重核所有按它算的判据**；
- syscall 48–63 一旦写进 ABI 文档就是承诺，**改号等于破坏兼容**；
- **`ModuleId(19)` 换号会让旧日志的"模块 19"含义变化**——这是不可逆的历史读数问题，
  只能在注释里写清"19 在新代码里是 virtio，旧日志里两者混用"。

## 验收与负样本

| 变更 | 判据 | 负样本 |
|---|---|---|
| `MOD_VMO` 换 20 | `resource::live_of(MOD_VMO)` 与 `live_of(MOD_VIRTIO)` 互不影响 | 改回 19 ⇒ 两模块台账合并 ⇒ 红 |
| 槽扩到 16 | 连续 `map_mmio` 16 次全成功、第 17 次返回 `NoSlots` | 不改常量 ⇒ 第 9 次就失败 ⇒ 红 |
| NVMe 队列合并 | 一台 NVMe 的 4 个环只用 2 个 `DmaHandle` | 每环一个 handle ⇒ 5 格 ⇒ 与扩容目标矛盾 |
| `MAX_TASKS` 12 | `tasks_active()` 上界 = 12 × 8 | 不改判据 ⇒ 上界仍是 9 ⇒ 红 |
| syscall 48–63 | 号序与族分配表一致，不跳号 | 跳号 ⇒ 表驱动检查红 |

**"第 17 次失败"这条判据需要先有 17 个真实 MMIO 使用者**——今天没有。
所以它只能先用"注入式"验证（造 17 个假设备），**这一点要在实施时确认可行**。

## 未决

1. **`.bss` 增量未量**：`MMIO_SLOTS` 8→16 与 `MAX_TASKS` 9→12 各让 `.bss` 涨多少，
   **没算过**。`.text` 已经撞过 128 KiB 上限（ADR-155），`.bss` 的上限没查过。
2. **16 格是否够到"完整"**：NVMe(1+2) + xHCI(1+2) + HDA(1+1) + AHCI(1+1)
   + 2×virtio-blk(2+2) + virtio-net(1+2) = **7 MMIO + 10 DMA**。
   MMIO 够，**DMA 10/16 只剩 6 格**。若再加一台 NVMe 就紧张。
3. **syscall 号段的族内顺序是设计而非实测**：TCP 的 8 个号是否够
   （`accept`/`listen` 要不要算进去）**未核**。
4. **`MAX_TASKS_TOTAL` 的判据改动面未清点**：凡读 `tasks_active()` 与
   `MAX_TASKS` 的用例都要过一遍，**没做**。
