# ADR-065：VA 保留表扩成 256 定长区间表 + 空闲位图，supersede ADR-041 的容量公式

状态：提议（2026-11-08，W2 内存分层 P3；证据来源 kernel/src/mm.rs 当前实现 + ADR-041）
关联：ADR-041（VA 容量归 memory、sched 编译期断言；本帖 supersede 其容量公式）、
ADR-026（用户/内核共用一张 va_res）、ADR-028（用户 VA 窗口）、完整化方案 §6 W2 条目 3、BACKLOG M2-b

> 写作纪律：已采纳 ADR 与有测试证据的事实优先于本文的目标设计。每条结论标「实测」或「推断」。
> 本帖决策先于实现：定区间表形状，实现与证红在 P3 切片。

## 背景

VA 保留表现状（实测，mm.rs）：`VaReservation{base,len,used}` 数组，容量
`MAX_VA_RESERVATIONS = MAX_CPUS * MAX_TASKS_SUPPORTED + 16 = 8*8+16 = 80`（mm.rs:76，ADR-041 决策 1）。
`register_va` 线性扫 `!used` 找空槽（mm.rs:528）；`reservation_count` 锁内扫 used 计数（mm.rs:523）；
表满时 `alloc_va_range_in` 打 `L4: VA 保留登记表已满` 并停机（mm.rs:673）。

方案 §6 W2 条目 3 要求："VA 保留表：定长 → 区间表（定长 256 + 空闲位图），保持「表满即拒绝并 L4 日志」"。
（方案写的"24 条"是 M2 旧值，代码已是 80；本帖目标 256。）BACKLOG M2-b 点名"VA 只增、表满拒绝"，
W3 每进程 VA 保留会进一步吃容量，80 条余量不足。

ADR-041 的两条遗产要分开对待：
- **容量公式**（`MAX_CPUS*MAX_TASKS_SUPPORTED+16` 派生）：本帖 supersede，改 256 定长。
- **所有权归 memory + sched 编译期断言**（`MAX_TASKS <= MAX_TASKS_SUPPORTED`，sched.rs:30）：保留。
- ADR-041 拒绝过"运行时动态表"：本帖仍是**静态数组**（256 定长 + 静态位图），不违背那条。

## 决策

1. **容量定长 256**：`const MAX_VA_RESERVATIONS: usize = 256;`（memory 拥有的固定常量，不再派生）。
   `MAX_TASKS_SUPPORTED=8` 与 sched 的编译期断言**保留不动**（ADR-041 决策 2 不变）；容量与它解耦。
2. **空闲位图作占用唯一真相**：State 加 `va_used: [u64; VA_BITMAP_WORDS]`（`VA_BITMAP_WORDS=256/64=4`，
   bit i=1 表示槽 i 已用）。**去掉 `VaReservation.used` 字段**（结构变 `{base,len}`），占用只查位图，
   避免"位图说空、used 说满"的两套真相漂移（与 ADR-063 refcnt 取代位图同律）。
   位图是普通 `[u64;4]`（非原子）：所有 va_res/位图访问都在 VMM(20) 锁内（register/release/reserved_end/
   reservation_count 全持 vmm()），互斥由锁提供。
3. **找空槽 O(1)**：`register_va` 扫 4 个 word 找 `!= u64::MAX`，`(!word).trailing_zeros()` 定位空位，
   置位 + 填 `{base,len}`；4 word 全满 ⇒ 返回 false（表满）。`reservation_count` 用 `count_ones()` 求和。
4. **释放/冲突查仍按区间包含**：`release_va_locked`/`reserved_end` 遍历槽，先查位图占用再按
   `[base, base+len)` 包含匹配（位图只告诉"哪个槽用了"，不告诉"哪段包含 va"，包含扫描保留）。
   释放清位图位 +  zero base/len。"按包含找不按基址相等"的既有纪律（ADR-027 / KT_TASK_EXIT）不变。
5. **表满语义不变**：`register_va` 返回 false ⇒ `alloc_va_range_in` 打 `L4: VA 保留登记表已满（256 条）`
   并 `exit::finish(ExceptionFatal)`（mm.rs:673 那条，只把数字 80→256）。
6. **登记面**：`MAX_VA_RESERVATIONS` 是私有常量（不进 public_api）；`MAX_TASKS_SUPPORTED` 已在 public_api。
   本帖不新增 pub 符号（位图/槽操作都是 mm 内部）。mm.rs 内改动是模块内（无边）；环内棘轮不动。
   不新增 unsafe（位图是普通数组索引，无裸指针）。

不涉及：VA 窗口划分（USER_VA_BASE/MMAP_BASE，ADR-028 不动）、用户/内核共表（ADR-026 不动）、
锁序数值、syscall 号、崩溃记录格式。日志契约：仅"表满"那条 fatal 的数字 80→256（判据按锚点不按数字）。

## 备选方案

- **保留 used 字段 + 另加位图加速**：拒绝。两套占用真相会漂移；位图作唯一真相与 ADR-063 同律。
- **动态/运行时分配的区间表（BTree/链表）**：拒绝（ADR-041 已拒动态表，本帖延续）。256 定长静态数组
  + 位图够用且无分配器循环依赖；W3 真要更大容量再另起草。
- **容量继续派生（MAX_CPUS*MAX_TASKS_SUPPORTED+余量）只抬余量到 256**：拒绝。派生公式把容量绑死在
  任务槽策略上；本帖要的是 memory 拥有的固定上限，与 sched 策略解耦（断言另管任务槽契约）。
- **位图用原子量**：拒绝。所有访问已在 VMM 锁内，原子只会误导"不用锁也行"（与 resource.rs 台账同律）。

## 影响

- 正面：VA 容量 80→256，W3 每进程保留有余量；找空槽/计数 O(1)；占用单一真相。
- 代价：State 多 32 字节位图（4×u64）+ va_res 数组从 80×24B 涨到 256×16B（去掉 used 后每条 16B，
  总 4 KiB，推断）；包含扫描仍 O(n)（位图不加速包含查询）。
- 对已有 ADR：supersede ADR-041 决策 1 的容量公式；保留其决策 2（断言）与所有权原则。
- 用例与矩阵：P3 新增区间表用例（分配 100 段 > 旧 80 容量证扩容 + 释放回基线），矩阵整轮复验。
  既有 driver/user/fs 的 reservation_count 往返用例自动覆盖新位图。

## 验收与负样本（P3 实现时兑现，本帖预注册）

- **扩容见证**：分配 100 段 1 页 VA（> 旧容量 80）全成功、reservation_count +100；逐段 release_va
  回基线、va_released +100。旧 80 容量下第 81 段会表满 L4 ⇒ 这条用例在改前必停机（扩容的直接见证）。
- **位图证红**：变异 `register_va` 填槽但**不清/置位图**（占用真相丢失）⇒ reservation_count 不涨、
  release_va 找不到槽 ⇒ 用例红。
- **表满证红**：变异 MAX_VA_RESERVATIONS 回 80 ⇒ 100 段用例第 81 段触发 `L4: VA 保留登记表已满` 停机（39）。
- **包含释放纪律**：既有 KT_TASK_EXIT/用户态回收用例（按包含找、guard 页不映射）继续绿。
- 第二台仪器：宿主机解析用例日志的 base/alloc后/release后/released 读数对账（P3 定行格式）。

## 迁移与回滚

- 迁移：P3 改容量 + 位图 + 去 used；既有用例自动覆盖。W3 用更大容量时本帖的 256 是基础。
- 回滚：容量改回派生公式、删位图、恢复 used 字段。回滚后 W3 容量余量回到 80。
- 不可回滚部分：无（不动盘上格式、不动 syscall）。

## P3 落地记录（2026-11-08，实测）

- **验收读数（build/run-001.log）**：`va区间表(P3): N=100 base=12 alloc后=112 release后=12 分配成=true
  释放成=true released 51->151`，`t_va_interval_table -> ok`，`ktests total=67 passed=67 failed=0`，PASS。
  100 段（> 旧 80）全成功 ⇒ 扩容到 256 成立；count +100、释放回基线、va_released +100。
- **负样本（两条都咬，实测）**：
  - MUT-P3-1（register_va 填槽但漏置位图）⇒ `base=0 alloc后=0 release后=0 释放成=false`、FAIL(35)
    （占用真相丢失，count 不涨、release 找不到槽）。
  - MUT-P3-2（MAX_VA_RESERVATIONS 缩到 64）⇒ 第 65 段 `L4: VA 保留登记表已满（64 条）`、EXCEPTION(39)。
  - 两条还原后均回 PASS。
- **编译期断言**：加 `const _: () = assert!(MAX_VA_RESERVATIONS % 64 == 0)`——位图按整 word 找空槽，
  容量非 64 倍数会让末 word 找出越界槽号（MUT-P3-2 用 64 而非 80 正是绕开 80/64 截断）。
- **环内棘轮收紧**：删掉容量派生公式里的 `cpu::MAX_CPUS` 引用 ⇒ `memory->arch` 67→64，登记同步收紧
  （ADR-044"少也红、收紧登记"）。这是 ADR-065 解耦的直接结构后果（memory 不再为 VA 容量依赖 arch）。
- **登记**：无新增 pub 符号（MAX_VA_RESERVATIONS 私有、位图内部）；无新增 unsafe（位图普通数组索引）。
  仅 module-interfaces.toml 的 memory->arch 棘轮值 67→64。
- **偶发备注**：P3 首跑默认档 t_preempt_round_robin 的"第二段窗口 tick 计数"格红一次（收到 2），
  定向复跑 3/3 全过——TCG tick 时序抖动，**与 VA 改动无关**（VA 表不影响 tick 数）；不松判据。

## 未决

1. **256 够不够 W3**：每进程多条 VMA × 多进程，256 可能仍紧。W3 起草时按实际进程数重算容量
   （本帖先把机制就位，容量是内存层拥有的常量，抬它只需改一处 + 位图 word 数）。
2. **包含扫描 O(n)**：release/reserved_end 仍线性扫 256 槽。热路径若成瓶颈再考虑按 base 排序/区间树
   （那是另一个里程碑，本帖不做）。
3. **位图与 va_res 的一致性**靠"同锁内一起改"保证，无独立影子对账（与 FrameInfo 引导期不同，
   这里运行期始终同锁）；负样本证 register 漏置位会红。
