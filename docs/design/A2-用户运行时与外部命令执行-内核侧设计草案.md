状态：**草案 / 提议，未采纳**（2026-11-16 起草）。本文不实现任何代码，不预分配 syscall 号；

## 1. 范围与边界

本文覆盖总设计 §9 阶段 A2 中**内核侧**要回答的四件事：

1. argv/envp 如何从 Shell（父进程）传到被启动的外部命令（子进程）；
2. stdin/stdout/stderr 三个标准句柄如何继承；
3. PATH 搜索放在哪一层做；
4. 退出码与父子等待——这一件经盘点**已经存在**（见 §2.1），本文只声明"不新增、不改动"。

**不碰的东西**（边界声明）：

- 块设备请求层、virtio-blk、`write_sectors`、23 号写方向、可写卷夹具——全部归 qoder 的
  ADR-110/111（BACKLOG §345/§346）。本草案的 stdout 重定向到**文件**那一半
  （而非控制台）显式推迟到 ADR-111 落地之后，见 §3.2。
- Shell 解析器、coreutils、`user/runtime` crate 本身——那是 A2 的用户态一半，本文只定义
  它要依赖的内核 ABI 形状。
- 已实测的中断、TLB、任务回收、调度语义——硬约束 1。

## 2. 现状盘点（每条标实测/推断，行号以当前 HEAD 为准）

### 2.1 等待机制：17/19 已经存在，A2 不需要为"退出码与父子等待"新增任何号

- **实测**：`SYS_PROCESS_WAIT = 17`（kernel/src/user.rs:874）与 `SYS_OBJECT_WAIT = 19`
  （kernel/src/user.rs:879）已定义、已实现、已接分派（user.rs:1881-1883）。
  共用实体 `wait_on_proc`（user.rs:896-927）：返回 `(observed << 32) | 退出码`，
  超时返回 0（"目标永远不收工"是业务事实，不升 L4）；`rsi=0` 时只查一次不阻塞
  （user.rs:915-921）。时限上限 `WAIT_MAX_MS = 60_000`（user.rs:885）。
- **实测**：退出码链路已闭环——`SYS_EXIT = 3`（user.rs:179）→ `EXITS` 计数（user.rs:1806）→
  `proc::proc_exit_code(pid)` 读回（user.rs:917）。退出码宽度是 `u32`（user.rs:917 的 `u64::from`）。
- **实测**：19 号是通用原语、17 号是它的薄壳（Q3 裁决，user.rs:876-879 注释）；今天只支持
  Proc 对象，拿别的 kind 来等回 `-4`（user.rs:878）。
- **对设计的影响（这是本次盘点最重要的发现）**：总设计 §9 A2 列的"退出码、wait、父子进程关系"
  在内核侧**不是缺口，而是已交付能力**。A2 的工作量集中在 argv/envp、标准句柄、PATH 三件；
  任何为"等待"新开 syscall 号的提案都是重复建设，应当直接拒绝。Shell 拿子进程退出码的
  完整序列今天就能写：`process_wait(proc_h, ms=0/阻塞)` → 高 32 位 observed、低 32 位退出码。
- **实测（配套限制）**：进程随最后一条线程收工被置 signal（user.rs:950-952 注释），
  `proc_reap` 收名额是既有路径——Shell 收尸不欠账。

### 2.2 StartupInfo 今天传了什么

- **实测**：布局与常量在 user.rs:101-142。头部 24 字节：`SI_MAGIC=0`（user.rs:104）、
  ABI major/minor 在 4/6（105-106）、`SI_OFF_NHANDLES=8`（108）、
  **`SI_OFF_ARGS_OFF=12` 与 `SI_OFF_ARGS_LEN=16`（user.rs:109-110）**、
  `SI_OFF_HANDLES=24`（111）。句柄描述符 `HandleDesc{role,kind,handle}` 16 字节（113-116），
  `MAX_STARTUP_HANDLES=16`（119）、调用方最多传 13 条（121）。
- **实测**：整页必须恰好 1 页 VMO（user.rs:714：`vmo_pages != Some(1)` ⇒ `-1`）；
  该页在子 AS 里**只读**（user.rs:722），内核经 VMO 帧的 HHDM 回填（user.rs:677 注释、794-838）。
  表头 + 16 条描述符 = 280 字节，一页内剩余约 3,816 字节目前无约定。
- **实测**：内核对 args 字段**只搬运、不解析**：`sys_process_start` 读 `hdr[0..SI_OFF_HANDLES]`
  共 24 字节只为校验 magic/ABI 版本/nhandles（user.rs:726-738），之后不再碰偏移 12/16。
- **实测**：全仓库 grep `SI_OFF_ARGS|args_off|args_len` 仅命中 user.rs:109-110 两行定义——
  内核无消费方，`user/` 下三个产物（hello/probe/fileprobe）也无引用。
- **推断**：这两个偏移是 ADR-075 决策 3 照设计 §10.2 布局抄下来的**预留字段**，
  语义（区在哪、内容格式、envp 放哪）从未定义。措辞纪律：这是"**偏移已声明、语义未定义、
  零消费方**"，不得写成"argv 已部分支持"。
- **实测**：role 表今天只有 SELF_PROC/SELF_ASPACE/SELF_THREAD/JOB/PARENT_CHAN/LOG/NS_ROOT/
  SI/CONSOLE_ECHO（user.rs:122-132）。**没有 stdin/stdout/stderr 角色**。
  `ROLE_CONSOLE_ECHO=8` 是 ADR-098 补记三的测试反例句柄，不是标准句柄机制。
  `ROLE_PARENT_CHAN=4` 与 `ROLE_LOG=5` 虽有编号，但 ADR-075 决策 3 明写：
  Channel 对象不存在、控制台对象今天以 `KIND_CONSOLE` 存在——`PARENT_CHAN` 一律不传，
  "没传的角色就是不存在"。
- **实测**：kind 表已有 `KIND_CONSOLE=7`、`KIND_FILE=1`、`KIND_DIR=8`、`KIND_VMO=2` 等
  （user.rs:134-142）。**没有 pipe/channel kind**——管道对象不存在，重定向与管道的内核前提
  今天为零。

### 2.3 控制台句柄与 F_CONSOLE

- **实测**：`SYS_CONSOLE_WRITE=20`、`SYS_CONSOLE_READ=21`（user.rs:51-52）；
  `CONSOLE_MAX=256`（user.rs:62）、`F_CONSOLE=256`（user.rs:63）——它是 **feature bit**
  （bit 8），不是句柄数：在 `abi_word()` 里随 `handles` 特性置位（user.rs:162），
  语义是"这份构建有控制台句柄族可调"。
- **实测**：`sys_console_io`（user.rs:1006-1061）按 `ObjRef::Console(sid)` 解析句柄，
  会话号在句柄里（user.rs:991-993 注释）；**读只给活动会话**（user.rs:1034：非活动会话读到
  0 字节），写经 `serial::write_bytes_sid` 按会话分流（user.rs:1025）。
- **推断**：Shell 与它启动的子进程同属一个会话时，子进程拿转移来的 Console 句柄
  直接打 20/21 即可与父进程同屏读写，无需任何新内核能力。跨会话行为（子进程被切到
  后台会话时读不到输入）是既有语义，不是本次要修的东西。

### 2.4 句柄继承：转移机制已存在，缺的是"标准句柄约定"

- **实测**：16 号 `process_start` 的第②步把调用方列出的任意句柄 `transfer` 给子线程
  （user.rs:767-792，`handle::transfer` 改 owner + bump 世代），失败有全套回滚
  （`undo_start`，user.rs:654-668）。转移对 kind 无白名单——Console/File/Dir/VMO 都能转。
- **实测**：回填流程保证"子进程读到的句柄值与内核回填的逐字相等"（ADR-075 P5c-3b 补记实测）。
- **结论（实测推出）**：**标准句柄继承的机制面（转移 + 回填 + 回滚）已 100% 存在**，
  缺的只是三件薄东西：①三个 role 常量的定义与传参约定；②"没传 std 句柄时子进程该看到什么"
  的口径（ADR-075 已有"没传的角色就是不存在"，够用）；③容量核算——三个 std 句柄 +
  内核 3 条 SELF_* = 6 条，占 `MAX_STARTUP_HANDLES=16` 的 6 格，Shell 还要转文件句柄，
  13 条转移额度的消耗要进负样本。
- **推断（缺口）**：stdout 重定向到**文件**需要"子进程对文件句柄可写"——今天 22 号只读
  （user.rs:54-55，flags 必须 0），写方向在 ADR-111 的盘子里。本草案不碰。

### 2.5 argv/envp：今天完全没有

- **实测**：见 §2.2——偏移字段零消费方；`spawn_user` 的首参 `rdi` 只装 SI 页 VA
  （user.rs:855-857），没有任何字符串区。
- **实测（约束）**：13 号 `vmo_write` 的单次长度受 `COPY_MAX=4096` 限制（user.rs:324-326、2019）；
  SI 页恰好一页 = 4096 字节，父进程写参数区只能按 ≤4096 分块写（与 13 号的分块手法一致）。
- **实测（内核侧约束）**：内核不得按用户给的长度开堆缓冲——堆上限 `LARGE_MAX=2048`
  （AGENTS.md 硬约束 6），且"按段开缓冲的写法会被当场打死"（ADR-018/026）。
  这决定了 argv 的**校验与搬运方案**必须用定长暂存或不动内核缓冲的形状（见 §3.1）。

### 2.6 ABI 版本与 feature bits 机制

- **实测**：`ABI_MAJOR=0`、`ABI_MINOR=12`（user.rs:67-68），号只追加不复用（user.rs:66）；
  feature bits F_FASTPATH=1 → F_FS_OPEN=512（user.rs:69-87），一律"读回真实状态，不读打算开"
  （user.rs:144 注释）。错误码 `AbiError` 只追加在末尾（user.rs:183-184）。
- **实测**：ADR-108 的先例——新增能力 = 升 minor + 新 feature bit + 逐号批准表。
- **推断**：A2 落地若动 StartupInfo 布局，应循同一成法：`ABI_MINOR` 12→13、
  新 feature 位（如 `F_STARTUP_V2`）读回真实状态；号表不动（本草案三个方案都不需要新号，
  见 §3）。

## 3. 三个设计问题的备选方案与推荐

### 3.1 argv/envp 如何传递

| | 方案 A：定义 SI 页内字符串区（扩展现有布局） | 方案 B：新 syscall 族（如 `process_set_args`） | 方案 C：独立参数 VMO（经 16 号转移） |
|---|---|---|---|
| 形状 | 在 SI 页 280 字节之后定义 argv/envp 区：偏移与长度写进头部（需把 `args_off/args_len` 从"预留"变成"有语义"，并为 envp 增加两个字段） | 15 与 16 之间新增"往停住的线程挂参数"的号 | 父进程 `vmo_create` 一页参数 VMO，作为一条 HandleDesc（新 role）随 16 号转移 |
| ABI 兼容性 | **不新增号**；头部若加 env 字段则是布局变更 ⇒ 升 minor + feature 位（循 ADR-108 成法）。argv 半边可先只赋予 `args_off/args_len` 语义，envp 半边再议 | **新增号** ⇒ 触发 AGENTS.md"停下来问"，必须重开号表裁决；ABI 面最大 | **不新增号**、不动头部；但 role 表要加条目（role 编号是 ABI） |
| 长度上限 | 一页内剩余 ≈3,816 字节，天然有界；超出**明确拒绝 `-3`**，不静默截断 | 上限即新号自己的校验规则，另定 | 上限最宽（多页 VMO），但首刀用不到 |
| 内核负担 | 校验形状（区不与句柄表重叠、长度和 ≤ 页内余量）即可，**内核不解析字符串内容**，零新缓冲 | 内核要在"停住"状态上暂存参数 ⇒ 新的中间态与新的失败回滚路径（ADR-075 决策 8 论证过"少一个中间态"的价值） | 内核只多转一个句柄，最薄；但**内核不校验内容** ⇒ "形状错误"不可判，负样本只能打在句柄层 |
| 负样本可测性 | 最好：子进程读回逐字节对账（两台仪器：父写入指纹 vs 子读回）；超长、区重叠、垃圾尾各有明确错误码 | 中：参数经内核中转，判据要同时盯内核暂存与子读回 | 弱：内容合法性完全推给用户态，内核判据只剩"转移成功/失败" |
| 与既有裁决的冲突 | `SI_OFF_ARGS_OFF/LEN` 已存在（user.rs:109-110），是"把预留变成实义"而不是新占地 | 与 15 号"建出来就停住、16 号回填完才放跑"的两段协议叠加出第三个状态 | role 表是 ADR-075 决策 3 冻结的布局，加条目同样要动 ABI 文档 |

**推荐：方案 A**，分两半裁决：

- **argv 半边（推荐采纳进 ADR-112）**：赋予 `SI_OFF_ARGS_OFF/ARGS_LEN` 实义——
  argv 区从页内固定偏移（建议 280，即句柄表之后）起，NUL 分隔、`args_len` 是区总长；
  内核只校验"区在页内、不与句柄表重叠、非零对齐到字节"，不解析内容。
  理由：不新增号、上限天然有界、负样本可测性最强、与"两侧独立声明同一组偏移"的既有成法
  （user.rs:101-101 注释、ADR-075 决策 3）同构。
- **envp 半边（本文倾向，留给 ADR-112 裁）**：头部 24 字节已满（0/4/6/8/12/16 都有主）。
  两个子形：①env 与 argv 共用一个区、按约定分节（不动头部，但分节约定较脆）；
  ②头部扩到 32 字节加 `env_off/env_len`（布局变更，升 minor）。本文倾向 **②**：
  一次把布局定干净，代价是所有现存用户产物（hello/probe/fileprobe）的独立偏移声明同轮改。
- **方案 C 保留为大参数的溢出路径**（未来命令行长参数、heredoc），首刀不做——
  "不为假想的未来需求设计"（AGENTS.md 硬约束 2 的精神）。

### 3.2 stdin/stdout/stderr 句柄继承

| | 方案 A：启动时经 16 号转移挂三个句柄 | 方案 B：Shell 代持、子进程经父转发 I/O |
|---|---|---|
| 形状 | 新增 `ROLE_STDIN/STDOUT/STDERR` 三个 role 常量；Shell 把自己的 Console（或未来文件）句柄列进 transfers | 子进程不持有句柄；I/O 请求经 `ROLE_PARENT_CHAN` 发回父进程代做 |
| 新增内核对象 | 无（复用 transfer） | 需要 Channel 对象——**今天不存在**（ADR-075 决策 3 实测口径），还要一套 IPC 号 |
| 每次输出成本 | 子进程直接打 20 号，一次 syscall | 两次 syscall + 父进程上下文切换，且父必须活着——子进程比父活得久就死锁 |
| 调试与问责 | 子进程的输出在句柄层自证（`bad_ptrs`/会话分流既有读数都在） | 中间多一层，"谁写的这行"对不出来 |
| 与既有裁决的冲突 | 无——正是 16 号②步设计好的用途 | `ROLE_PARENT_CHAN=4` 的存在恰恰说明这条路被想过并被"今天不传"冻结（ADR-075 决策 3） |

**推荐：方案 A。** 论证：

1. **机制已存在**（§2.4 实测）：16 号的转移 + 回滚 + 回填就是为"把能力交给子进程"设计的，
   标准句柄是它最直接的调用者。方案 B 要先造 Channel 对象与 IPC 号族（总设计 §6.3 的
   IPC 候选族明确写着"应在真实调用者出现时按 ADR 设计"——真实的第一个调用者应是管道，
   不是标准句柄转发）。
2. **语义口径**：std 三角色**未传时**，按 ADR-075 既有口径"没传的角色就是不存在"——
   子进程读自己的角色表发现没有 `ROLE_STDOUT` 就不写。**内核不做"默认挂控制台"的隐式行为**：
   隐式默认会让"Shell 忘了传"变成"看不出来忘没忘"，违背"少了什么必须看得见"（user.rs:72-73
   那条 F_SAFE_MODE 注释的同一条纪律）。把"缺省接 /dev/null 等价物"留给用户态 runtime 决定。
3. **今天的可交付范围（诚实边界）**：stdout/stderr 指向 **Console** 今天就能绿
   （20 号 + 会话分流实测在案）；指向**文件**要等 ADR-111 的 23 号写方向落地，本草案
   显式不承诺。stdin 指向 Console 受"只有活动会话能取输入"（user.rs:1034）约束——
   Shell 与子进程同会话时不构成问题，但判定行要有一格把这条既有语义钉住。
4. **容量核算（实测约束）**：全局句柄表 16 格、SI 页转移额度 13 条、内核 SELF_* 占 3 条
   （user.rs:119-121）。三个 std 句柄 ⇒ 调用方剩余额度 10 条。负样本要按这个数写，
   不能按"想传多少传多少"写。

### 3.3 PATH 搜索：内核不做，用户态 runtime 做

**论证（五条，全部可核对）**：

1. **组合性（实测前提）**：内核提供的唯一原语是 22 号 `open`，它只收绝对路径
   （`NotAbsolute ⇒ -1`，user.rs:1119 的映射在案）。PATH 搜索 = "对 PATH 里每个目录逐个
   拼接 + open 尝试"，用户态 runtime 用现有号**完全可组合**，不缺任何内核能力。
   按 AGENTS.md 硬约束 2，不造没有真实调用者的内核服务——这里连服务都不需要造。
2. **失败语义**：内核做搜索就要回答"逐个 miss 各报一次 `-8`，还是合成一个错误？"
   ——新错误码要进 `AbiError`（只追加，user.rs:183-184），还要定义"搜索中途盘失败（`-7`）
   与'没找到'（`-8`）怎么混"。用户态做则这些全是 runtime 的本地决策，ABI 不动。
3. **内核缓冲约束（实测）**：PATH 环境串可达数千字节，内核侧 `COPY_MAX=4096` 与
   `LARGE_MAX=2048` 两道墙（§2.5）意味着内核做搜索要么分块多次拷贝、要么拒绝长 PATH——
   两种都比"用户态自己拿着字符串循环"贵且脆。
4. **判据强度**：用户态做，"PATH 顺序"可由 ring3 探针直接判（同一名字放两个目录，
   断言先找到谁、宿主机侧独立对账）；内核做，这些判据全退化为内核日志行，
   "两台仪器对账"的成法变弱。
5. **策略归策略**：PATH 是 Shell/用户配置语义，不是内核机制；放用户态默认可配置、
   可按进程覆盖，也不会把"搜索顺序劫持"升格成内核语义问题。

**推荐**：内核零改动。`user/runtime` 提供 `resolve(name, path_env) -> 绝对路径`，
逐候选 22 号 open（成功即关掉试探句柄或直接复用）；全 miss 运行态报"命令未找到"，
Shell 把它映射成自己的退出码约定——都是 A2 用户态一半的事。

## 4. 判据与负样本（每条新判据配能变红的负样本）

按仓库纪律，以下每条判据在 ADR-112 落地时都要配变异证红；本草案只定义"要证什么"。

| # | 判据（落地时的正样本） | 负样本（变异证红） |
|---|---|---|
| J1 | argv 对账：父进程写 argv 区（含指纹），子进程读回逐字节相等；`args_len` 与子读到的串数一致 | 变异：内核回填时跳过 args 区 ⇒ 子进程读到空区/0 长度，红 |

| J3 | envp 对账：同 J1/J2，针对 env 字段（若 ADR-112 裁了子形②） | 同 J1/J2 变异手法 |
| J4 | std 句柄继承：子进程拿 `ROLE_STDOUT` 句柄打 20 号成功、父 Shell 同会话可见；`ROLE_STDIN` 打 21 号受活动会话分流约束 | 变异①：转移时 role 重复/伪造 SELF_* ⇒ `-1`（既有校验，user.rs:761）；变异②：16 号失败回滚路径砍掉 ⇒ 子进程拿到半套角色表，`undo_start` 格红 |
| J5 | "没传就没有"：不带 std 角色启动的子进程，读角色表确认对应槽不存在，runtime 走缺省路径且**内核零隐式授予** | 变异：内核给没传 std 的进程隐式塞控制台句柄 ⇒ "没传"格红（这条变异同时就是"不许做隐式默认"的门禁证人） |

| J7 | PATH 归属：ring3 探针证明 PATH 解析全程只用 22 号 + 用户内存；内核侧该链路零新增号、零新日志锚点 | 变异：在内核塞一个 PATH 解析入口 ⇒ `check` 的接口登记门禁红（新增 public API 未登记） |

## 5. 红线声明

1. **本草案不实现任何代码、不预分配 syscall 号。** §3 的三个推荐方案均不需要新号；
   若 ADR-112 评审后改选需要新号的方案（如 §3.1 方案 B），**必须停下来问**——

   按 AGENTS.md"要改 ADR 已定的语义"条款，落地前必须起草 ADR-112 并经使用者批准；
   批准前不动 `SI_OFF_*`、不动 role 表、不动 `abi_word()`。
3. **改日志契约同样属停下来问清单**——本草案若获批落地，新增取证行的锚点格式要在
   ADR-112 里先列出来，不得先打日志后补批准。
4. **与 ADR-110/111 的边界（qoder 的盘子，本草案不碰）**：块设备请求层、`Block::write_sectors`、
   virtio-blk、23 号写方向、可写卷夹具 `fat32-rw.img`、以及两块只读真卷的指纹判据——
   全部不在本草案射程内。本草案对文件 I/O 的唯一依赖是**只读 open（22 号，已交付）**
   与"写方向由 ADR-111 提供"这一句话；stdout 重定向到文件的具体判据推迟到 ADR-111
   落地后在 ADR-112 里补，不在本草案里预写。
5. 本文档状态为**草案/提议，未采纳**。文中所有"推荐"均未获裁决；引用它的后续文档
   不得把"本文推荐"写成"已决定"。
