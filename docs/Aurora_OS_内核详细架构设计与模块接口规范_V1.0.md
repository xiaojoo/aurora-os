# Aurora OS 内核详细架构设计与模块接口规范 V1.0

**文档编号：** AUR-KERNEL-API-1.0\
**适用仓库：** `aurora-os-main`\
**依据基线：** 用户提供的 `aurora-os-main.zip`，以及仓库内《Aurora OS
开发手册（企业级）V1.2》、ADR、`BACKLOG.md` 和当前源码\
**状态：** 设计基线 / 待架构评审\
**定位：** 总体架构文档的第二份配套文档\
**首期范围：** x86-64 内核，不包含桌面 UI

------------------------------------------------------------------------

# 0. 文档目的与使用规则

本文件不是重新设计一套内核，也不是替换《Aurora OS
开发手册（企业级）V1.2》。

V1.2
已经包含启动、CPU、中断、内存、调度、驱动、故障处理、系统调用、安全、测试和商业化等大量设计，并且其中相当一部分已经有代码和实测证据。本文件进一步解决四个问题：

1.  **模块边界：** 哪个模块拥有哪类状态，其他模块通过什么接口访问。
2.  **接口契约：**
    参数、返回值、资源所有权、上下文约束和失败语义是什么。
3.  **隔离边界：**
    如何限制错误传播，哪些故障可以恢复，哪些故障必须升级为内核致命错误。
4.  **渐进拆分：** 如何从当前单一内核 crate
    演进到组件化工程，而不进行大规模重写。

## 0.1 规范优先级

发生冲突时，按以下顺序处理：

1.  已采纳的 ADR 和已经由代码、测试证明的事实。
2.  本文件中明确标记为"已落地"的接口和行为。
3.  V1.2 中的强制规范。
4.  本文件中标记为"目标设计"的接口。
5.  尚未验证的建议和假设。

不得为了让文档看起来一致，修改已经验证的实现结论。发现冲突时，先记录差异，再通过
ADR 决策。

## 0.2 状态标记

-   **已落地：** 当前源码中存在实现，并有测试或实测记录支持。
-   **部分落地：** 主要路径存在，但边界、异常路径或测试仍不完整。
-   **目标设计：** 后续模块化或演进时需要达到的状态。
-   **未决：** 需要 ADR 或真实硬件证据才能决定。

# 1. 对当前代码基线的审查结论

## 1.1 当前仓库的实际形态

本次审查的 ZIP 中可以确认：

-   根 Cargo workspace 当前包含 `kernel` 和 `user/hello` 两个成员。
-   内核包名为 `aurora-kernel`。
-   内核采用 `#![no_std]`、`#![no_main]`。
-   内核源码主要使用 Rust 模块组织。
-   `kernel/src/main.rs` 通过 `mod` 声明组织多个模块。
-   当前 ZIP 中没有独立的 `.c`、`.h`、`.S` 或 `.asm` 源文件。
-   CPU 特殊操作通过 Rust `core::arch::asm!` 等方式实现。
-   当前 `unsafe` 白名单主要以整个 `aurora-kernel` crate 为单位登记。
-   `docs/architecture/crates.toml` 明确记录了垂直切片阶段暂不拆分 API /
    implementation crate 的原因。
-   `docs/architecture/lock-order.md` 已经维护锁等级和真实嵌套关系。
-   `docs/security/unsafe-whitelist.toml` 已经维护 unsafe 登记。
-   `tools/aurora.py` 已经承担统一构建、测试、检查和发布辅助工作。

因此，当前工程的准确描述是：

**Rust 为主的单 crate 内核，按源码模块组织；部分 CPU
指令以内联汇编实现；尚未形成 C + Rust 的独立混合编译结构。**

这不代表原先 C + Rust
的目标被取消，而是说明当前不应该为了"混合开发"而无理由引入 C。C
应在出现明确的硬件适配、外部代码复用或 ABI 需求时引入。

## 1.3 当前阶段不应进行的重构

以下行为禁止直接实施：

-   一次性把所有源码拆成几十个 crate。
-   为每个文件机械地创建一个 crate。
-   为了引入 C 而把已经稳定的 Rust 代码改写成 C。
-   把 `mm`、`sched`、`trap` 等成熟模块整体重写。
-   未经 ADR 改变已经实测的中断、TLB、任务回收和驱动资源语义。
-   为了抽象而创建没有真实调用者的空 Trait、空服务或空模块。
-   将当前所有 `unsafe` 简单移动到一个新的 `unsafe`
    crate，却不减少其权限和可访问范围。

# 2. 目标模块化架构

## 2.1 逻辑分层

目标架构分为六层：

``` text
┌──────────────────────────────────────────────┐
│            Kernel Integration                │
│      初始化编排 / 生命周期 / 故障协调          │
├──────────────────────────────────────────────┤
│            Kernel Services                   │
│  Scheduler / Process / IPC / VFS / Security  │
├──────────────────────────────────────────────┤
│            Kernel Core                       │
│  Memory / Resource / Sync / Time / Object     │
├──────────────────────────────────────────────┤
│            Driver Framework / HAL            │
│  Device Model / DriverCtx / MMIO / DMA / IRQ  │
├──────────────────────────────────────────────┤
│            Architecture Layer                │
│  x86_64 / CPU / Trap / Paging / APIC / SMP    │
├──────────────────────────────────────────────┤
│            Boot / Platform                   │
│      Limine / UEFI / ACPI / Platform Info     │
└──────────────────────────────────────────────┘
```

这是逻辑依赖图，不要求当前立刻拆成六个 crate。

## 2.2 依赖方向

依赖必须从高层指向低层接口，不允许低层反向依赖高层实现。

允许：

-   Driver 调用 Driver Framework。
-   Driver Framework 调用 HAL。
-   HAL 调用 Architecture。
-   Scheduler 使用 Memory、Sync、Time 提供的接口。
-   Kernel Integration 编排各模块初始化。

禁止：

-   `mm` 依赖 `ahci` 或 `virtio`。
-   `trap` 依赖 `user` 的业务实现。
-   `pci` 依赖具体 AHCI 驱动。
-   `driver` 依赖具体 `ahci.rs` / `virtio.rs`。
-   `resource` 依赖调度器的内部任务结构。
-   `serial` 依赖任意业务模块的私有状态。
-   低层模块调用 `main.rs` 中的集成测试函数。

## 2.3 依赖规则必须机器可检查

依赖约束不能只存在于文档。

逐步建立以下检查：

1.  crate 依赖图检查。
2.  禁止循环依赖。
3.  禁止高层 crate 被低层 crate 引用。
4.  `unsafe` 白名单与源码实际使用双向对账。
5.  驱动不得直接使用裸 MMIO / DMA 指针。
6.  架构相关指令只能出现在架构层或经批准的低层模块。
7.  每个新增 crate 必须登记到 `docs/architecture/crates.toml`。
8.  每个新增公开接口必须有模块归属和契约说明。

当前只有一个内核 crate 时，先用源码级门禁保护边界；真正拆 crate
后，再增加 Cargo 依赖图门禁。

# 3. 模块所有权与接口目录

本章定义每个模块"拥有的数据"和"对外提供的能力"。模块不得允许其他模块直接修改其私有状态。

## 3.1 Boot 模块

**当前实现：** `limine.rs`、`main.rs` 中的启动编排。

拥有：

-   启动信息快照。
-   Bootloader 交接信息的规范化表示。
-   启动阶段状态。
-   启动参数校验结果。

对外能力：

-   解析 Limine 响应。
-   返回经过验证的 `BootInfo`。
-   提供内存地图、HHDM、RSDP、MP 信息等只读快照。
-   报告缺失或不支持的启动能力。

约束：

-   只在启动早期读取 Bootloader 原始指针。
-   需要跨越页表接管阶段的数据必须先复制到内核拥有的存储。
-   不得把 Bootloader 可回收内存的裸引用长期传给其他模块。
-   Boot 模块不负责 PMM 的策略实现。

目标接口形态：

``` rust
pub struct BootInfo {
    pub hhdm_offset: u64,
    pub memory_map: BootMemoryMap,
    pub rsdp: Option<PhysAddr>,
    pub cpu_topology: CpuTopologySnapshot,
}

pub fn collect() -> Result<BootInfo, BootError>;
```

以上是目标接口形态，不能直接覆盖现有
`limine::collect()`，需要逐项映射现有字段并通过测试后再调整。

## 3.2 Architecture / CPU 模块

**当前实现：** `cpuid.rs`、`cpu.rs`、`trap.rs`、`apic.rs`、`smp.rs`。

拥有：

-   CPU 特性快照。
-   CPU Local 状态。
-   GDT / IDT / TSS 配置。
-   本地 APIC 状态。
-   CPU 上线状态。
-   架构相关 TrapFrame 和上下文布局。

对外能力：

-   查询 CPU 能力。
-   初始化当前 CPU。
-   查询当前 CPU 标识。
-   启动或登记 AP。
-   提供受控中断和上下文切换原语。
-   提供架构相关的页表和 TLB 操作。

约束：

-   通用内核不能直接操作 CR0、CR2、CR3、CR4、MSR、APIC MMIO。
-   通用内核不能假设 LAPIC ID 等于数组槽位。
-   CPU Local 数据必须通过受控访问器读取。
-   跨 CPU 读取其他 CPU
    的状态，默认只能作为快照，除非该字段具有明确的原子发布协议。
-   所有架构相关结构的布局变化必须更新 ABI / 汇编侧断言。

## 3.3 Memory 模块

**当前实现：** `mm.rs`、`heap.rs`。

拥有：

-   物理帧分配状态。
-   虚拟地址保留表。
-   页表结构。
-   映射所有权对象。
-   内核堆分配器状态。
-   TLB shootdown 请求与回执状态。

对外能力分成三组：

**物理帧接口**

-   分配物理帧。
-   释放物理帧。
-   查询物理内存统计。
-   管理 DMA 所需物理内存约束。

**虚拟内存接口**

-   建立映射。
-   解除映射。
-   查询映射。
-   申请和释放 VA 区间。
-   管理权限与缓存属性。

**堆接口**

-   内核对象分配。
-   可失败分配。
-   分配统计与诊断。

核心所有权规则：

1.  `map` 成功后返回拥有映射生命周期的对象。
2.  映射对象销毁时负责解除映射并按协议释放对应物理资源。
3.  解除映射必须等待需要的 TLB shootdown 回执。
4.  回执未齐不得归还物理帧。
5.  不能通过 `mem::forget`
    把资源所有权永久丢弃，除非有明确的静态生命周期论证和 ADR。
6.  任务栈、用户映射等资源必须跟随所属任务生命周期。
7.  当前任务仍在某 CPU 上运行时，不得释放它正在使用的栈和地址空间。

错误分级：

-   非法参数、地址未映射：返回明确错误。
-   资源耗尽：可失败接口返回 `OutOfMemory` / `ResourceExhausted`。
-   全局分配器无法满足不可失败分配：遵循现有 ADR-018 的 L4 策略。
-   DoubleFree、所有权破坏、shootdown 超时：属于内核完整性风险，按 V1.2
    对应规则升级。

特别约束：

`Drop`
不适合承载需要向调用者返回失败的复杂资源释放操作。若释放可能失败，必须使用显式
`close()` / `release()` 返回结果，并明确 Drop 的兜底策略。

## 3.4 Scheduler / Process / Thread 模块

**当前实现：** `sched.rs`、`user.rs`、`elf.rs`。

建议逐步明确三个逻辑子模块：

-   Task：调度实体和任务生命周期。
-   Scheduler：运行队列、抢占、选择下一个任务。
-   Process：地址空间、用户映像、进程资源和退出状态。

拥有：

-   任务槽位。
-   每 CPU 运行队列。
-   当前任务与 CPU 归属。
-   任务状态。
-   任务拥有的映射集合。
-   任务退出和待回收状态。

接口契约：

-   创建任务必须返回唯一任务标识。
-   任务状态变更必须通过 Scheduler / Task API。
-   外部模块不得直接修改 `on_cpu`、运行队列和状态字段。
-   任务退出先改变状态，再延迟回收资源。
-   资源回收必须发生在确认任务不再运行的上下文。
-   任务迁移必须同时解决两端运行队列同步、`on_cpu` 原子转移和地址空间
    TLB 处理。
-   不得把"读取到另一个 CPU 的 Running"当作无同步的决策依据。

当前已知边界：

-   每 CPU 队列和 AP 调度已落地。
-   任务迁移仍需单独设计。
-   用户任务退出与资源回账已有专门实现和 ADR。
-   不能在本文件中重新定义这些行为，必须遵循 ADR-027 等既有决策。

## 3.5 Synchronization 模块

**当前实现：** `sync.rs`，锁等级表位于
`docs/architecture/lock-order.md`。

拥有：

-   锁状态。
-   锁持有者信息。
-   每 CPU 锁序状态。
-   竞争统计。
-   等待超时统计。

约束：

-   新锁必须先登记锁等级和保护对象。
-   嵌套获取必须严格遵循锁等级递增。
-   持锁期间不得睡眠。
-   持锁期间不得执行未知回调。
-   中断上下文不得使用可能阻塞的锁。
-   shootdown 处理方不得获取请求方正在持有的 VMM 锁。
-   任何锁都必须说明是否允许在中断关闭状态下获取。
-   锁守卫不能跨 CPU 移交。
-   不能只凭"lockdep
    violations=0"宣称并发安全，必须证明测试确实产生过竞争。

新增锁必须同时修改：

1.  `docs/architecture/lock-order.md`
2.  代码中的 rank 定义
3.  相关单元或内核测试
4.  对应负样本或变异测试

## 3.6 Driver Framework 模块

**当前实现：** `driver.rs`，由 `ahci.rs`、`virtio.rs` 使用。

拥有：

-   驱动模块身份。
-   MMIO / DMA 能力句柄表。
-   句柄槽位和 generation。
-   资源授权与撤销状态。
-   驱动资源统计。

核心原则：

**驱动获得的是能力句柄，不是任意内核指针。**

句柄至少包含：

-   槽位编号。
-   世代号。
-   所属模块身份由内核侧记录。
-   资源类型和权限由内核侧记录。

所有访问都必须检查：

1.  句柄槽位存在。
2.  generation 匹配。
3.  调用方拥有该资源。
4.  访问类型被授权。
5.  偏移和长度在资源窗口内。
6.  访问上下文符合要求。

禁止驱动直接使用：

-   `read_volatile` / `write_volatile`
-   任意 `ptr::` 访问
-   `from_raw_parts` 构造任意映射切片
-   自行创建或释放内核管理的 DMA 映射

DMA
资源应通过受控访问器操作，设备总线地址以整数形式提供，不把可解引用指针交给驱动。

驱动接口应继续保持"只增加真实需要的方法"。不要预先定义没有调用者和测试的空接口。

## 3.7 PCI / Bus 模块

**当前实现：** `pci.rs`、`acpi.rs`、`hw.rs`。

拥有：

-   PCI 设备枚举快照。
-   BDF 标识。
-   BAR 资源描述。
-   PCI capability 解析结果。
-   总线访问后端。

约束：

-   PCI 枚举不依赖具体设备驱动。
-   驱动按 Vendor ID、Device ID、Class/Subclass/ProgIF
    和能力表识别设备，不得依赖"第一个 class 01 就是 AHCI"这类顺序假设。
-   BAR 映射必须经 MMIO 管理接口。
-   MSI/MSI-X 表位置必须按能力结构解析，并由设备读回验证。
-   设备配置写入必须有范围、对齐和访问宽度检查。
-   PCI 枚举结果是设备描述，不等于设备已经被驱动认领。

## 3.8 Interrupt / IRQ 模块

**当前实现：** `trap.rs`、`apic.rs`、`irq.rs`。

建议明确分为：

-   Architecture Trap：CPU 异常和硬件入口。
-   Interrupt Controller：APIC / IOAPIC / MSI 路由。
-   IRQ Registry：向量认领、所有者和目的 CPU。
-   Driver Completion：设备完成事件与驱动确认。

约束：

-   顶半必须短小、可界定、不得分配内存。
-   顶半不得睡眠。
-   顶半不能把"收到中断"当作"设备操作完成"。
-   设备源状态清除、控制器 EOI、驱动完成确认是不同账目。
-   中断认领、设备编程和服务完成必须分开记录。
-   中断亲和性变更必须由驱动/路由层完成实际设备编程，并验证回读。
-   共享电平 INTx 必须处理设备归属和源清除顺序。
-   MSI-X 和共享 INTx 未完成前，不得在文档中宣称中断模型已经全面完成。

## 3.9 Storage / Block Device 模块

**当前实现：** `ahci.rs`、`virtio.rs` 中已有设备路径。

目标上应分离：

-   Block Device Interface：统一块读写请求。
-   Controller Driver：AHCI、virtio-blk、未来 NVMe。
-   Buffer / DMA：由 Driver Framework 和 Memory 提供。
-   Filesystem：只依赖块设备抽象，不依赖具体控制器。

接口目标：

``` rust
pub struct BlockRequest {
    pub lba: u64,
    pub sectors: u32,
    pub operation: BlockOperation,
}

pub trait BlockDevice {
    fn capacity_sectors(&self) -> u64;
    fn submit(&mut self, request: BlockRequest) -> Result<RequestId, BlockError>;
    fn poll(&mut self, request: RequestId) -> Result<RequestStatus, BlockError>;
}
```

此处仅为目标接口示例。异步完成、缓冲区所有权、超时、取消和 DMA
生命周期必须先设计完整，不能直接把示例接口作为当前代码改造要求。

## 3.10 Diagnostics / Reliability 模块

**当前实现：**
`serial.rs`、`crash.rs`、`state_store.rs`、`boot_guard.rs`、`watchdog.rs`、`exit.rs`。

拥有：

-   内核日志缓冲。
-   崩溃摘要。
-   持久状态记录。
-   启动健康状态。
-   看门狗状态。
-   最终停机出口。

约束：

-   诊断模块不得依赖业务模块的私有结构。
-   故障路径不得依赖普通堆分配。
-   Panic / Fatal 路径不得等待一个可能已经损坏的锁。
-   停机路径必须有不排队的日志和资源处理策略。
-   持久状态写入失败不能再次触发不可恢复的故障。
-   任何崩溃记录都必须能与同一次启动的 ELF / build identity 对应。
-   不能把"检测到软锁死"写成"已经恢复软锁死"；检测、隔离、恢复必须分别验收。

## 3.11 Security / Update 模块

**当前实现：** `sign.rs`、`state_store.rs` 和启动相关逻辑。

拥有：

-   摘要算法。
-   签名验证原语。
-   信任锚。
-   更新包元数据。
-   安全启动决策状态。

约束：

-   密码原语测试必须由独立实现对账。
-   签名验证通过不等于已经建立安全启动。
-   生产密钥必须独立于测试密钥。
-   生产密钥必须有离线保管、轮换、吊销和泄露响应方案。
-   验签必须接入真正的启动决策后，才可宣称更新包被强制验证。
-   当前签名机制与启动决策之间尚有集成工作，不得在发布说明中夸大其保护范围。

# 4. 统一接口契约

每个跨模块接口必须包含以下契约信息：

  字段         要求
  ------------ ---------------------------------
  接口名称     唯一且语义明确
  所有者       唯一负责维护内部状态的模块
  调用者       允许调用的模块
  上下文       普通内核、关中断、ISR、启动期等
  输入约束     长度、对齐、范围、权限
  返回值       成功时返回什么
  错误         每种失败对应明确错误类型
  资源所有权   谁创建、谁持有、谁释放
  并发语义     可否多核并发调用
  阻塞语义     是否可能等待、等待上界
  故障升级     哪些错误返回，哪些升级为 L4
  测试         至少一个正样本和对应负样本

没有上述信息的接口，不允许作为稳定模块接口发布。

## 4.1 错误类型分层

错误分为四类：

**A. 业务/调用错误**

例如无效参数、文件不存在、句柄不存在。返回错误，不改变系统健康状态。

**B. 资源/设备错误**

例如资源耗尽、设备超时、设备离线。返回错误并由所属模块决定重试、重置或隔离。

**C. 契约违例**

例如句柄越权、generation
不匹配、非法上下文调用。拒绝操作，记录安全事件；是否升级由资源和完整性影响决定。

**D. 内核完整性错误**

例如 DoubleFree、页表结构损坏、锁重入导致不可恢复死锁、shootdown
无回执却准备释放页面。必须按既有故障等级升级，不能伪装成普通 `Err`
后继续运行。

## 4.2 禁止吞错

禁止：

``` rust
let value = operation().unwrap_or_default();
```

用于会影响系统状态、权限或资源所有权的关键路径。

禁止将以下情况统一映射为 `None` 或 `0`：

-   资源不存在。
-   读取失败。
-   权限拒绝。
-   超时。
-   设备未响应。

日志中的默认值不能冒充真实读数。

## 4.3 错误传播

模块内部可以定义细粒度错误，跨模块边界应映射到稳定的公开错误类型。

不得让底层私有错误枚举直接成为长期 ABI。

# 5. C / Rust / Assembly 混合边界

## 5.1 当前策略

当前内核以 Rust 实现，特殊指令通过 Rust inline assembly 完成。

**短期不强制引入 C。**

C + Rust
是目标能力，不是要求每个阶段都必须同时存在两种语言。只有存在明确收益时才增加
C 代码。

## 5.2 允许引入 C 的场景

-   需要复用经过审查的 C 硬件代码。
-   需要对接已有 C ABI 的固件或平台组件。
-   某些架构初始化代码在 C 中更容易维护，且有独立测试和边界。
-   未来移植经过许可证审查的第三方 C 驱动或协议实现。

不允许仅因"操作系统通常用 C"而新增 C 层。

## 5.3 C ABI 规则

跨 C / Rust 边界只允许传递明确布局的数据：

-   固定宽度整数。
-   `#[repr(C)]` 结构。
-   不透明句柄。
-   显式长度的缓冲区。
-   明确的错误码。

禁止跨 ABI 直接传递：

-   Rust `String`、`Vec`、trait object。
-   Rust 内部引用和生命周期。
-   未约定布局的枚举或结构。
-   Rust panic。
-   C 侧未定义行为。

内存释放必须由分配方提供的释放函数完成，禁止一边分配、一边用另一套
allocator 释放。

## 5.4 Assembly 规则

汇编仅用于：

-   启动和入口桩。
-   中断入口/出口。
-   上下文切换。
-   系统调用入口。
-   特殊寄存器和特权指令。
-   编译器无法表达或无法保证语义的少量操作。

每个汇编入口必须有：

1.  调用约定。
2.  寄存器保存清单。
3.  栈对齐要求。
4.  中断状态要求。
5.  可重入性说明。
6.  Rust 对应结构布局断言。
7.  正样本与负样本测试。

不得在汇编中实现普通内存分配、调度策略、文件系统和协议业务逻辑。

------------------------------------------------------------------------

# 6. 运行上下文与调用约束

内核接口必须明确在哪种上下文中调用。

定义以下上下文标签：

  标签         含义                  允许行为
  ------------ --------------------- --------------------------------
  BOOT         单核启动阶段          仅调用已初始化的早期服务
  KERNEL       普通内核上下文        可使用正常内核接口
  IRQ_OFF      本 CPU 关中断临界区   不得睡眠，不得等待不可界定事件
  ISR_TOP      中断顶半              不分配、不睡眠、不调用未知回调
  DEFERRED     中断延迟处理          可执行受控的较复杂处理
  USER_ENTRY   用户态进入内核边界    必须验证寄存器和用户参数
  PANIC        致命错误路径          仅使用无分配、无阻塞的诊断能力

每个公开接口的文档必须标记允许上下文。

例：

``` text
DriverCtx::map_mmio
允许：KERNEL
禁止：ISR_TOP、PANIC
可能阻塞：否
资源副作用：建立 MMIO 映射并占用一个能力槽
失败：Denied / WrongContext / ResourceExhausted / MappingError
```

接口不能仅靠调用者"知道不能在中断里用"来保证正确。能机器检测的约束必须通过运行时守卫或测试实现。

# 7. 故障域和最小影响设计

## 7.1 故障域定义

目标上至少划分：

1.  CPU / Architecture 故障域。
2.  Memory 故障域。
3.  Scheduler 故障域。
4.  Driver 单设备故障域。
5.  Filesystem 实例故障域。
6.  Network Interface 故障域。
7.  Diagnostics 故障域。
8.  User Process 故障域。

但必须明确：**当前宏内核中的普通 Rust 模块不是硬件保护域。**

同一内核地址空间中的任意模块仍可能通过越界写、错误 DMA、错误页表操作或
unsafe 代码破坏其他模块。

## 7.2 故障处理策略

  故障                     首选处理                       是否允许系统继续运行
  ------------------------ ------------------------------ ----------------------
  无效参数                 返回错误                       是
  文件不存在               返回错误                       是
  单个用户进程非法访问     终止该进程                     是
  单个设备超时             重试/复位/隔离设备             视影响而定
  网卡失效                 隔离网卡，保留其他设备         是
  文件系统损坏             卸载或只读保护该实例           视系统盘情况
  驱动越权访问资源         拒绝并记录，必要时隔离驱动     视完整性而定
  内核堆不可恢复 OOM       按 ADR-018 升级                否
  DoubleFree               L4                             否
  页表或内存所有权损坏     L4                             否
  shootdown 超时           不释放相关帧，按既有规则升级   否
  CPU / 内核栈完整性损坏   停止危险执行并 Crash Dump      否

## 7.3 驱动隔离演进

第一阶段：

-   所有驱动通过 `DriverCtx` 获取资源。
-   驱动不持有任意原始 MMIO / DMA 指针。
-   句柄带 generation 和 owner 校验。
-   驱动有明确生命周期。
-   单设备错误可在设备粒度重置或隔离。

第二阶段：

-   驱动执行上下文统一。
-   设备访问授权独立。
-   驱动健康状态可查询。
-   驱动可停止、撤销资源和重新初始化。

第三阶段：

-   将高风险驱动迁移到独立地址空间。
-   通过 IPC / capability 与内核通信。
-   驱动崩溃不直接破坏内核地址空间。
-   支持服务重启和设备重新绑定。

只有第三阶段才具备更强的运行时隔离。前两阶段主要是接口和资源隔离，不得宣传成完全故障隔离。

# 8. 初始化、销毁和生命周期

## 8.1 初始化原则

每个模块必须提供明确状态：

``` text
Uninitialized
    ↓
Initializing
    ↓
Ready
    ↓
Stopping
    ↓
Stopped

Initializing → Failed
Ready → Degraded
Degraded → Recovering → Ready
Degraded → Isolated
```

模块状态由模块自身拥有，其他模块只能通过状态接口读取。

## 8.2 初始化依赖

初始化顺序必须由依赖图推导，不允许在 `main.rs` 中随意堆叠初始化调用。

目标依赖顺序：

``` text
Boot Info
   ↓
Serial / Early Diagnostics
   ↓
CPU Tables / Trap
   ↓
Memory Takeover
   ↓
Kernel Heap
   ↓
CPU Protection
   ↓
ACPI / Platform Tables
   ↓
APIC / SMP
   ↓
PCI / Bus
   ↓
Driver Framework
   ↓
Storage / Network Drivers
   ↓
Scheduler / User Runtime
```

该图是逻辑顺序示意。实际启动顺序必须服从当前已经验证的先后约束，例如堆未就绪前不能执行依赖全局分配器的路径。

## 8.3 初始化失败

初始化失败必须明确属于：

-   必须启动前提不满足：拒绝启动。
-   可选模块不可用：标记 Degraded。
-   单设备初始化失败：隔离该设备。
-   内核完整性损坏：升级 L4。

禁止所有模块初始化失败都统一返回 `false`。

## 8.4 销毁顺序

销毁顺序与依赖顺序相反，但必须额外满足：

-   没有 CPU 正在执行该模块代码。
-   没有中断正在访问该模块状态。
-   没有设备 DMA 仍指向待释放内存。
-   所有能力句柄已经撤销。
-   所有映射已解除且 TLB 回执已齐。
-   所有异步请求已完成或取消。
-   所有资源已回到账本。

# 9. 组件拆分与 crate 演进路线

## 9.1 不按文件数量拆 crate

当前一个文件不等于一个组件，一个组件也不必然等于一个 crate。

拆分条件：

-   有稳定的公开接口。
-   有明确的资源所有权。
-   有独立测试价值。
-   依赖方向明确。
-   能减少 unsafe 的传播范围。
-   拆分后不会迫使大量内部实现暴露为 public。

## 9.2 建议拆分顺序

### 第一步：先拆分 `main.rs` 的职责

将启动编排、测试注册、测试判定和模块实现分离。

目标：

-   `main.rs` 只保留内核入口和启动编排。
-   ktest 的注册、运行和报告独立。
-   各模块测试不再依赖 main 中的私有实现。
-   不改变现有启动顺序和测试输出契约。

### 第二步：提取低耦合基础组件

优先评估：

-   `aurora-boot-protocol`
-   `aurora-diagnostics-api`
-   `aurora-test-support`
-   `aurora-arch-x86_64`

其中只有在接口真实稳定后才建立
crate。早期可以先在源码目录中建立逻辑边界。

### 第三步：提取内存与同步组件

评估：

-   `aurora-memory-api`
-   `aurora-memory-x86_64`
-   `aurora-sync`
-   `aurora-resource`

内存模块拆分时必须保持 `Mapping`、`OwnedFrames`、VA reservation 和
shootdown 的现有所有权契约。

### 第四步：提取设备框架

评估：

-   `aurora-driver-api`
-   `aurora-driver-core`
-   `aurora-pci`
-   `aurora-ahci`
-   `aurora-virtio`

先保持驱动只能通过 `DriverCtx` 访问 MMIO / DMA 的约束，再拆 crate。

### 第五步：提取系统服务

后续再考虑：

-   `aurora-scheduler`
-   `aurora-process`
-   `aurora-vfs`
-   `aurora-network`
-   `aurora-security`

## 9.3 目标 crate 结构

这是目标结构，不是要求本轮立即创建的空 crate：

``` text
crates/
├── interfaces/
│   ├── boot-api/
│   ├── memory-api/
│   ├── driver-api/
│   ├── process-api/
│   └── syscall-abi/
│
├── arch/
│   └── x86_64/
│       ├── cpu/
│       ├── trap/
│       ├── paging/
│       ├── apic/
│       └── context/
│
├── core/
│   ├── memory/
│   ├── sync/
│   ├── resource/
│   ├── scheduler/
│   └── diagnostics/
│
├── drivers/
│   ├── pci/
│   ├── ahci/
│   ├── virtio/
│   └── common/
│
└── services/
    ├── filesystem/
    ├── network/
    └── security/
```

# 10. Unsafe 与 TCB 管理

## 10.1 Unsafe 的使用原则

`unsafe` 不是普通实现细节，而是需要明确安全论证的边界。

每个 unsafe 块必须说明：

-   为什么必须 unsafe。
-   指针来源。
-   地址范围。
-   对齐要求。
-   生命周期。
-   并发访问规则。
-   CPU / 中断上下文约束。
-   由谁保证安全不变量。

## 10.2 Unsafe 分级

建议登记为：

-   U1：架构入口和特殊寄存器。
-   U2：页表、物理内存和 MMIO。
-   U3：DMA 与设备共享内存。
-   U4：并发共享状态和 UnsafeCell。
-   U5：用户指针和地址空间访问。
-   U6：诊断路径的有限现场读取。

每项登记必须指向具体模块和代码范围，不能只写"内核需要"。

## 10.3 拆 crate 后的策略

当前 `aurora-kernel` 单 crate 的 unsafe 白名单是阶段性现实。

拆分后目标：

-   普通业务 crate 默认 `#![forbid(unsafe_code)]`。
-   只有确实需要底层能力的 crate 才登记 unsafe。
-   unsafe 尽量集中在小型 arch / memory / hardware adapter 中。
-   安全抽象 crate 对上层提供安全接口。
-   CI 对账必须能发现白名单虚报和未登记 unsafe。

禁止通过把 unsafe 从一个 crate 搬到另一个 crate，就宣称内核安全性提高。

# 11. 测试契约与模块验收

## 11.1 每个模块的最低测试集合

每个模块至少具备：

1.  正常路径。
2.  边界值。
3.  非法参数。
4.  资源不足。
5.  重复调用。
6.  并发调用（若支持）。
7.  生命周期结束。
8.  故障注入。
9.  回归测试。

## 11.2 必须具备独立证据

测试不能只验证模块自己说"成功"。

涉及硬件、存储、网络、签名等功能时，应尽可能建立第二台独立仪器：

-   内核侧记录执行结果。
-   宿主机或独立实现验证外部可观察结果。
-   两边对同一事实给出一致结论。

不得将同一份数据复制两次称为独立验证。

## 11.3 故障注入

每条关键安全规则都应有能让它失败的负样本。

示例：

  规则              故障注入
  ----------------- --------------------------
  句柄 owner 校验   使用其他模块的句柄
  generation 校验   撤销后继续使用旧句柄
  内存所有权        重复释放
  TLB shootdown     不发送 ACK
  锁重入            同 CPU 重复获取同一锁
  SMEP/SMAP         清除保护位
  DMA 边界          越界访问缓冲区
  驱动隔离          注入设备超时或初始化失败
  状态区            破坏记录头或校验和
  签名              修改载荷或签名

## 11.4 模块合并门禁

任何模块接口或内部实现变更必须满足：

-   编译成功。
-   静态检查通过。
-   相关单元测试通过。
-   内核集成测试通过。
-   QEMU 启动和回归通过。
-   相关负样本仍然能够命中。
-   性能基线没有无法解释的劣化。
-   ADR 和文档已同步。

# 12. 接口版本和兼容性

## 12.1 内核内部接口

内部模块接口可以随开发演进，但每次破坏性变化必须：

-   更新调用方。
-   更新接口文档。
-   更新测试。
-   记录 ADR（若影响架构、安全或性能）。
-   保留必要的迁移说明。

## 12.2 用户 ABI

用户 ABI 必须独立于内核内部 Rust 类型。

禁止把 Rust 内部结构直接作为系统调用 ABI。

系统调用 ABI 使用固定宽度字段、明确布局和版本信息。

## 12.3 驱动 ABI

未来驱动 ABI 必须与内核内部实现解耦，采用能力句柄和版本化消息。

用户态驱动出现后，驱动 ABI 应能够独立升级和协商能力。

# 15. 架构评审结论

本项目当前最重要的任务不是继续扩大功能数量，而是把已经实现的能力逐步沉淀为稳定、可审计、可测试的模块。

最终目标不是"文件很多"或"crate 很多"，而是：

1.  每个模块只拥有自己应该拥有的状态。
2.  模块之间只能通过明确接口协作。
3.  资源具有唯一所有者和可追踪生命周期。
4.  unsafe 被限制在可审计的边界。
5.  设备驱动不能任意访问内核内存。
6.  故障能够按影响范围分级处理。
7.  关键模块具有正样本、负样本和独立验证。
8.  未来可以把高风险驱动和服务迁移到独立执行域。
9.  架构调整可以逐步完成，不需要推翻已验证的实现。

**本阶段最终原则：先稳定接口和所有权，再拆组件；先建立可验证的隔离边界，再追求更复杂的内核架构。**
